# SHAJON-404/re-extera — отдельная ветка DEX-плагина re:extera

Источник: [SHAJON-404/re-extera](https://github.com/SHAJON-404/re-extera), закреплённый snapshot `c188c00821e1b9fbdc020c7d2080ce2699416eac` (`master`, сохранён 2026-09-27). Лицензия по [метаданным репозитория](https://github.com/SHAJON-404/re-extera/blob/c188c00821e1b9fbdc020c7d2080ce2699416eac/LICENSE) — GPL-3.0. README на этом SHA показывает loader/plugin `2.8.9` и target exteraGram `12.9.0` и называет репозиторий custom fork, отдельно поддерживаемым SHAJON; при этом GitHub repository metadata в snapshot имеет `fork: false`. Роль источника — большой Android-плагин, показывающий конкретные Kotlin/Java DEX hooks поверх Python `BasePlugin` loader, настройки и обходы внутренних классов host-приложения. Относится к прикладной реализации/реинжинирингу, а не к общей документации ExteraGram SDK. Код использует `libs/exteragram.jar` как `compileOnly` stub и Aliuhook; отдельной документации публичного SDK в этом репозитории нет.

## Архитектура и lifecycle

В Python ExteraGram-плагине `Plugin(BasePlugin)` `on_plugin_load()` создаёт `Loader` и вызывает `load_and_start()`; при выгрузке Python вызывает `Loader.unload()`, который отражением вызывает `Main.onUnload()`. DEX загружается с classloader приложения как parent: сначала `InMemoryDexClassLoader(ByteBuffer.wrap(bytes), appClassLoader)`, затем при ошибке — `DexClassLoader` из локального файла кэша. Перед загрузкой байты сохраняются как `cached.dat`/`classes.dex` по каналу. Entry вызов — reflection `Main.initAndStart()`; loader оставляет fallback на старые DEX с `getInstance().start()`.

`Main.initAndStart()` использует два уровня защиты: static `hooks != null` внутри classloader и общесистемное JVM property `re_extera_hooked` между разными classloader-ами. При выгрузке `HookInit.onUnload()` снимает собранные `Unhook`, сбрасывает `isActive`, а `Main.onUnload()` очищает property, разрешая настоящую повторную загрузку. Это важно, потому что в-memory и file loader могут создать разные копии статических полей.

`HookInit.startIntercepting()` служит единым реестром. `tryHook(name, clazz, methodName, hook, parameterTypes...)` ищет объявленный метод по точной сигнатуре, вызывает `XposedBridge.hookMethod` Aliuhook и сохраняет `Unhook`; исключение отдельного registration логируется, чтобы отсутствие одной host-сигнатуры не останавливало остальные hooks. Классы host, отсутствующие в stub JAR (например внутренние классы и `ExteraConfig`), разрешаются через `Class.forName` и регистрируются в изолированном `try/catch`. Это кодовая реализация данного плагина, не рекомендация считать Aliuhook наличным Xposed/LSPosed framework: сам проект описывает его как библиотеку hook API внутри exteraGram plugin.

## Loader, settings и сборка

Loader metadata на снимке: `__id__ = "re_extera_loader"`, имя `re:extera Extended`, версия `2.8.9`, минимальная версия plugin engine `12.8.1`. `loader/__init__.py` задаёт порядок фрагментов, а `loader/build.py` склеивает их в единый `build/plugin/loader.plugin`, проверяет синтаксис и запускает `ruff` если он доступен. `.plugin` — отдельный deliverable от `classes.dex`.

`Loader` ищет DEX по порядку local sideload path → channel cache → fresh download; in-memory загрузка имеет file-classloader fallback. Update flow разделён на `Release` и `Dev`; Python settings экран переключает канал, выбирает версию, запускает update check, принимает install-from-file, export logs и открывает Java settings. Это описывает кодовый путь snapshot; никакие HTTP downloads, plugin actions и device reload в этой работе не запускались.

`build.gradle` задаёт AGP 9.3.2, compileSdk 35, minSdk 26 и Java source/target 11; Aliuhook `1.1.3` подключён как `compileOnly`. Версия DEX берётся regex-ом из `loader/metadata.py` при отсутствии release git tag. Собственная Gradle `aarToDex` задача находит Android SDK через `ANDROID_HOME`, `ANDROID_SDK_ROOT` или `local.properties`, затем вызывает `d8` с Android `android.jar` и compile classpath, чтобы собрать DEX из release AAR. README по-прежнему пишет JDK 17, тогда как AGP-9 note, `.agent/AGENTS.md` и Actions workflow закрепляют JDK 21; для этого SHA build workflow — более точное свидетельство CI среды. Workflow запускает ruff, `./gradlew buildDex`, `python3 loader/build.py`, сохраняет `classes.dex` + `loader.plugin` как artifacts и на master создаёт release.

**Recipe по коду:** для нового hook сначала проверить `ExteraConfig` на уже встроенную настройку; добавить отдельный `XC_MethodHook`, зарегистрировать точную перегрузку в `HookInit.startIntercepting()` через `tryHook`, создать getter/setter в `Settings` и строку/row в fragment UI; для host-only класса использовать `Class.forName` с локальным try/catch. Версионно-хрупкие reflection-поля/внутренние классы оборачивать fail-soft и иметь отдельный kill switch там, где патч затрагивает отрисовку. Это практическая схема из docs/code этого fork, не универсальный публичный SDK contract.

**Integration notes из документации проекта:** Python fragments `loader/*.py` склеиваются в общий namespace в `BUILD_ORDER`; импорты сосредоточены в `imports.py`, поэтому фрагмент может ссылаться только на определения из более ранних частей. Для Java UI `.agent/architecture.md` и `settings-ui.md` описывают `BasePreferencesActivityExtended`, `fillItems(UItem...)`, `onClick`/`refreshCheckBox`, `enum Ids` и регистрацию top-level fragment в `Main.fragments`; при decompiled `$SwitchMap` документация советует добавлять enum в конец и обрабатывать новые значения до generated switch. Это авторские инструкции snapshot, не независимо runtime-проверенный контракт.

## Ограничения и пробелы

- Ни сборка, ни тесты, ни проверка на Android устройстве не выполнялись. Наличие CI workflow — это описание автоматизации, не green CI evidence. `runtime-verified` фактов нет. По `AGENTS.md` pinned SHAJON snapshots прежние placeholder tests удалены; полное дерево не содержит `src/test` или `src/androidTest`, а workflow не запускает test suite.
- README говорит target exteraGram `12.9.0`, хотя отдельный upstream snapshot `fossSquad/re-extera` на `3be81ef0…` имеет более широкий/другой набор путей. Совместимость с более новым клиентом из текущего кода не выводится.
- В `libs/exteragram.jar` лежит бинарный compile stub, его API здесь не декомпилировался. Внешний host source/decompiled `draft/extragram` дерево, на которое ссылаются `.agent` notes, не входит в покрытие. Поэтому истинность внутреннего контракта Telegram/exteraGram, доступность приватных полей и сохранение hook signatures на иных версиях не подтверждены независимо.
- Не просматривались построчно все ~100 hook/helper реализаций и все UI-компоненты; scope ограничен curated `.agent` feature notes, lifecycle/build/settings/loader и выбранными fork-specific feature paths. В частности, точные menu option IDs/условия и обработчики, re:forward/Local Premium/Work in Background, `PathIconDrawable`, profile-menu ID, protected-story/call-button hooks, полный Settings fragment tree, все таблицы/TTL/путь вложений DB и полная семантика Ghost Mode, Shadowban, filtering, message-forwarding за пределами перечисленных точек остаются вне этой страницы; подробные заявления остаются в feature notes как docs, пока их код не разобран.
- У `.agent/translate-button.md` и `.agent/archive.md` есть заявления об on-device tracing/iteration; это сохранённые заметки проекта, а не результат проверки в текущем ingest. Не повышать до `runtime-verified`.
- Сравнение с upstream выполнено по двум pinned file manifests и наличным файлам; cross-repository compare REST запрос вернул 404. Точную ветку предков/коммит, в котором SHAJON отделился, не установлено.
