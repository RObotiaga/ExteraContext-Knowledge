# vcvkk/extCLI — оболочка и консоль разработчика внутри exteraGram

Источник: [vcvkk/extCLI](https://github.com/vcvkk/extCLI), зафиксированный снимок `0eafced3fc14dd7ffd534b103b62f4041fff6339` (ветка `main`, дата снимка 2026-09-27). Основной код лицензирован Apache-2.0. Это Android-плагин exteraGram с Python-оболочкой, клиентскими командами и терминальным UI; он полезен прежде всего как конкретный пример совместимого доступа к клиенту через SDK и отражение, а не как нормативная спецификация SDK. Все API ниже подтверждены исходным кодом именно этого SHA. Ни одна команда на устройстве и ни один загруженный бинарник здесь не запускались; runtime-поведение плагина не проверено.

## Подтверждённые контракты и техники

### Плагинный lifecycle и диагностика SDK

`BasePlugin` оставляет тонким класс загрузчика; реализация в `main.py` разделяет ранний дешёвый `start_init(plugin)` и `load_plugin(plugin)`. При load создаются каталоги, логируются сведения о клиенте, добавляются drawer/chat menu entries через `MenuItemData`, регистрируется send-message hook и запускается фоновая проверка возможностей. Длительная подготовка rootfs ставится после probe на очередь `client_utils.run_on_queue`; UI-переходы делаются через `android_utils.run_on_ui_thread`. При unload пункты меню удаляются и долгоживущая сессия закрывается/detach-ится. Хороший прикладной шаблон: не делать тяжёлую инициализацию синхронно в конструкторе и явно завершать принадлежащие плагину listeners/session.

`host status` собирает версию самого плагина, версию клиента из `BuildVars.BUILD_VERSION_STRING`, версию SDK из безопасных полей `_sdk_version` (`__version__`, `version_str`, `version`) плюс Android release/API, модель и ABI. SDK-модуль намеренно не вызывается как callable: рядом находятся внутренние lifecycle hooks `setup_hooks()`, `__start__()` и `check_safemode()`. `host class <fqcn> [filter]` использует compat reflection для вывода реальных полей/сигнатур загруженного Java-класса на самом устройстве — практический способ проверить Kotlin/Java ABI клиента вместо угадывания по старому decompile. Это функция исходника, не наблюдавшийся вывод на устройстве.

`host paths` показывает фактические пути. `compat.paths` получает private paths из `ApplicationLoader.applicationContext` (`getFilesDir`, cache, no-backup, external files/cache, nativeLibraryDir), root plugin определяет проверкой `meta.yml` и кандидатов включая `elyxcore._importer.importer.get_caller_root()`. Исходник поясняет, что `__file__` может отсутствовать в loader runtime, тогда code filename из frame остаётся запасным сигналом. Для сравнения путей Android `/data/user/0/...` и `/data/data/...` нормализуются через `realpath`, чтобы совпадали с именами ядра при syscall path mapping.

### Команды plugin и безопасная адаптация к PluginsController

Команды `plugin list [--enabled|--disabled]`, `plugin info <id>`, `plugin path <id>`, `plugin enable|disable|reload <id>`, `plugin config [list|get|set|unset] <id> ...` зарегистрированы в `shell/builtins/plugin.py`. Имена плагинов можно разрешать по точному ID либо единственному совпадению подстроки; неоднозначность возвращается ошибкой со списком совпадений, не выбирается молча. Состояние меняют через единый compat adapter к `com.exteragram.messenger.plugins.PluginsController`: предпочтительно `setPluginEnabled(id, bool)`, при отсутствии — `togglePlugin(id)` только после чтения текущего статуса, чтобы избежать лишнего переключения. Reload — `unloadPlugin(id)` затем `loadPlugin(id)`.

`plugin info` извлекает name/version/author/description/path/enabled/pinned с несколькими вариантами accessor-имён и tolerates отсутствующие поля. Список получает через `getPlugins()` либо поле `plugins`, а единичный объект через `getPlugin(id)` с fallback к карте. Все Java interop вызовы идут через compat reflect и диагностические ключи; это снижает сцепление с одним вариантом API, но не означает гарантии совместимости любого будущего клиента.

`plugin install file.eaf [--force]` сначала проверяет файл и содержимое ZIP: читает `refmap.yml`, поле `metainfo`, затем YAML-метаданные с обязательным `id`. Если ID уже установлен, без `--force` обновление отклоняется. Только после валидации вызывается реальный client installer: сначала `loadPluginFromFile`, далее fallback `copyArchiveToPluginsDirectory` / `openPluginFile`; аргумент пробуется как `java.io.File`, затем как строка пути. Это кодовая стратегия compat и список имён кандидатов, не runtime-доказательство, какая сигнатура сработала на установленной версии. Поиск `HISTORY.md`/commit history подтверждает появление install-flow в коммите `9ba2a3d7f5f8` 1 сентября и отдельную фиксацию installer method name по реальному клиенту в `6f3611ec310e`.

Для config `plugin_settings.get_all_settings/get_setting/set_setting/clear_settings` — первый путь, контроллер `getAllPluginSettings` — fallback для чтения; запись/очистка через controller в этом адаптере не заявлена. CLI преобразует `true/false`, `yes/no`, `on/off`, `null/none`, целые и float в типизированные значения, иначе сохраняет строку. Включение/выключение/reload/install/config mutations проходят через `policy.require`; однако этот снимок — development build с `MODE_ALLOW_ALL`, так что gate сейчас журналирует чувствительное действие, но не спрашивает пользователя. README не обещает production confirmation.

### Telegram: account routing, загруженные чаты, read/get/send

Compat messaging маршрутизирует через `client_utils.get_selected_account()`; `UserConfig.selectedAccount` также используется для собственного user ID. `get_messages_controller()` даёт выбранный MessagesController. Диалоги берутся из уже загруженного клиентом `getAllDialogs()`/`getDialogs()` или поля `dialogs`: `tg chats <query>` — локальный поиск по title, username и ID, не сетевой username lookup. Разрешение принимает `me/self/saved`, числовой dialog ID, `@username` или уникальную часть названия; неоднозначность вызывает понятную ошибку. Положительный ID трактуется как user, отрицательный — как chat/channel style dialog id.

`tg read <chat> [-n count] [--before id] [--oneline|--json]` использует `TLRPC.TL_messages_getHistory`, задаёт `request.peer = controller.getInputPeer(peer_id)`, `limit` ограничивает диапазон 1…100, `offset_id` получает `--before`. `send_request(request, callback)` ждёт callback через `threading.Event` максимум 20 секунд; поддерживается альтернативный `send_request(request, callback, account)`; полученные Java/TLRPC messages сразу нормализуются в простые dict (`id/date/text/author/author_id/out/media`), разворачиваются oldest-first. Старые-first упрощает shell pipelines вроде `tg read ... | grep ... | tail`.

`tg get` ищет attachment в `attachPath`, затем `FileLoader.getInstance(selected_account).getPathToMessage(raw)`; если локальной копии нет, просит `loadFile` / `loadFileFromMessage` / `loadMessageFile`, опрашивает путь раз в 0.4 секунды максимум 120 секунд, затем копирует обычный файл в целевой каталог. Имена берутся из `document.attributes[].file_name`, иначе `<message_id>.jpg`. Результат — запись на каждое вложение, поэтому частичные успехи не теряются. Команда ограничивает историю тем же аргументом количества; запись каталога проходит policy gate.

Уточнение по fallback имени: ID-с именем `.jpg` используется для фото, у которых нет имени файла; документы берут `file_name` из атрибута. Запись ведётся в указанный каталог, и одинаковые имена вложений могут перезаписать друг друга — стабильность уникальности имён снимок не гарантирует.

`tg send` разделяет текст, `--photo` и `--file/--document`; путь интерпретируется через shell Env. Destination резолвится только по загруженным диалогам. Для отправки отправителю/себе и стороннему адресату используются разные policy action (`send.message` vs `send.foreign`). `send_text/send_document/send_photo` пробуют несколько SDK-вариантов с учётом отличий параметров аккаунта и parse mode; первый TypeError принимается за несовпадение сигнатуры только если его текст выглядит как binding/signature error. Успешная форма кэшируется; внутренний TypeError клиента не приводит к повторной отправке, чтобы исключить возможное двойное действие.

### `.cli <command>` как редактируемое сообщение

Hook `on_send_message_hook(plugin, account, params)` распознаёт строго `.cli` или `.cli ` с командой, извлекает peer из `peer/dialog_id/peer_id/dialogId`, возвращает `HookResult(CANCEL)`, а работу команды ставит на `run_on_queue`. Пустой `.cli` открывает консоль на UI thread. Для команды relay сначала отправляет сообщение `$ <command>\n…`; если API не возвращает ID только что отправленного сообщения, открывает консоль как fallback, потому что обновлять нечего. Если console session уже есть, команда использует ту же сессию и переменные/cwd; иначе создаёт временный context с текущим плагином, собранными сервисами и backend chain.

Промежуточный вывод поступает в `LiveText`, который перерисовывает терминальные управляющие символы, оставляет хвост вывода не длиннее лимита Telegram 4096 символов, опускает head и добавляет ellipsis. Edit не выполняется при неизменном тексте и раньше пользовательского интервала. Нижняя граница — 3 секунды; settings предлагают 3/5/10/30 секунд, default 5. Если ошибка edit содержит `FLOOD_WAIT_n`, интервал и ближайшее время обновления поднимаются на серверный n. После завершения финальный текст принудительно отправляется; исключение команды превращается в текст ответа.

Commit `9ce4c2429101` от 1 сентября ввёл ответ `.cli` непосредственно в чат. Текущий снимок подтверждает relay, callback/ID fallback, обработку FLOOD_WAIT и редактирование output; я не нашёл временных файлов в самом relay/streaming path. Отдельно rootfs guest задаёт собственный `/tmp` (см. `rootfs/guest.py` и `rootfs/layout.py`) для гостевой среды: не следует переносить это на коммуникационный relay как его temporary-file механизм.

### Shell, host backends и rootfs/proot

`extCLI` — не только emulator: lexer/parser/AST/executor реализуют shell subset (pipes, redirection/heredoc, `&&/||`, assignments/expansion, command substitution, arithmetic, glob, loops/conditionals, functions, alias/source); command registry и context/services отделены от Android UI. Built-ins включают Unix-like shell tools, `plugin`, `host`, `tg`, `config`, `log` и rootfs/toolbox operations.

Фактические runnable backend выбираются по проверкам устройства. `host check [--refresh]` показывает shell, toybox, pty, exec из data dir, linker, доступные backends и rootfs verdict; `--self` гоняет читаемый `selftest.sh` через сам shell, `--window` описывает текущее Android окно. Probe результат кэшируется в `probe.json` и инвалидируется при смене app version. Без rootfs `backends.chain.build` выбирает system shell, затем native dynamic linker для bundled executables, затем in-process Python fallback. С активным rootfs цепочка состоит из rootfs backend и in-process fallback; backend без guest-path translation отбрасываются. Нельзя считать `proot` runnable только по факту наличия ELF в data dir: README и код указывают на Android SDK 36/SELinux и необходимость проверять ограничения запуска.

При этом текущий код и README уже содержат Alpine rootfs subsystem: bundled minirootfs resource, native loader/probe/pathmap binaries, rootfs setup/toolbox/guest modules. Rootfs execution использует измеряемые стратегии запуска, guest path mapping и настройки mount. Mount-настройки скрывают отдельные host paths при пользовательском обращении, но `rootfs/mounts.py` прямо говорит, что это не граница безопасности: сам код плагина сохраняет доступ к данным по замыслу. CI описывает тесты и сборки, но не подтверждает успешный запуск на Android.

Перед распаковкой встроенный архив проверяется по закреплённому SHA-256. `rootfs/install.py` вручную проверяет имена элементов архива, пропускает device/FIFO и снимает setuid/setgid. Статическое чтение выявило ограничение: `_inside()` применяет `normpath`, но не разрешает symlink-компоненты через `realpath`; если архивный элемент ранее создал ссылку на путь вне rootfs, последующая запись по дочернему пути может пройти лексическую проверку. Это анализ кода, не runtime-проверка или подтверждённый exploit; поэтому извлекатель не следует описывать как полностью защищённый от symlink обходов без дополнительной проверки. [Код распаковщика на зафиксированном SHA](https://github.com/vcvkk/extCLI/blob/0eafced3fc14dd7ffd534b103b62f4041fff6339/extcli/src/rootfs/install.py#L100).

История `HISTORY.md` описывает раннюю разработку до августа и не покрывает изменения сентября. GitHub commit pages подтверждают `tg read` (`132c8333f89b`), `tg get` (`ad3ee99af368`), `plugin install` (`9ba2a3d7f5f8`), уточнение имени install method (`6f3611ec310e`) и чатовый relay (`9ce4c2429101`) от 1 сентября. Коммит `2ebcada9c464` от 5 сентября меняет rootfs backup export: абсолютные rootfs symlink targets переводятся в относительные, чтобы архив был переносим и принимался безопасным фильтром распаковки. Это изменение backup export, а не доказательство безопасности каждого extraction path.

Группа `config` относится к настройкам клиента в preference stores и отличается от `plugin config`: она включает `list/get/set/unset/search/stores/export/import`, чтение типов из `SharedPreferences` и typed writes, чтобы не менять тип уже существующего ключа. Новые ключи по умолчанию не записываются без `--new`; изменения проходят `CLIENT_CONFIG` policy gate, а CLI напоминает о необходимости перезапуска клиента. Это контракт кода, а не проверка результата на устройстве.

### Kotlin terminal renderer

`TerminalNative.kt` реализует Android `View` с режимом scrollback stream и режимом character-grid TUI (`blit`). Python `term.bridge` загружает `extcli/dex/terminal.dex` через `InMemoryDexClassLoader(ByteBuffer.wrap(bytes), appClassLoader)` и вызывает static методы reflectively; мотивация в комментарии — writable plugin dir + Android W^X делает обычный `DexClassLoader` unsuitable для writable dex, а Chaquopy не импортирует класс напрямую. Bridge проверяет наличие dex и версию renderer, преобразует Python int arrays в Java `int[]`, предоставляет metrics/describe/release. Stream renderer обрабатывает `\n`, `\r`, `\t`, `\b`, ANSI SGR цвета и bounded scrollback; grid принимает три массива символов/цветов. README говорит, что готовый dex включён и для обычной сборки Kotlin toolchain не нужен; менять Kotlin source требует ручной `scripts/kotlin-build.sh`.
