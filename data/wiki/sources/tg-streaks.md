Источник: [n08i40k/tg-streaks](https://github.com/n08i40k/tg-streaks), snapshot `e9fa83619480964ccd3b8565af8c1301318ac7ad` (`master`, сохранён 2026-09-27). В `repository.json` GitHub не указывает лицензию; `LICENSE` и `LICENSE.md` в этом SHA отсутствуют (оба запроса вернули HTTP 404). Это не SDK: Python entrypoint использует ExteraGram Plugin API, загружает собственный Kotlin DEX в процесс клиента, а Kotlin-код напрямую связывается с Telegram-классами, Aliuhook/Xposed API и рядом изменяемых внутренних методов клиента.

## Архитектура, callbacks и lifecycle

`tg-streaks.py` — точка входа ExteraGram: объявляет ID `tg-streaks`, имя `Streaks`, версию `2.20.1` и `__min_version__ = "12.1.1"`. Этот ключ относится к metadata plugin-файла и сам по себе не доказывает совместимость всех использованных Telegram internals с каждой версией клиента.

Файл плагина — Python-обвязка с текстовыми областями для `classes.dex` и `resources.zip`. `EmbeddedAssets.read()` читает отмеченные строки-комментарии, декодирует Base64 и LZMA/XZ; `JvmPluginBridge` загружает DEX через `InMemoryDexClassLoader(ByteBuffer, ApplicationLoader.applicationContext.getClassLoader())`. Python вызывает Kotlin static entrypoints reflection-ом (`inject`, `finalizeInject`, callbacks, настройки и `eject`). На сохранённом отслеживаемом `.py` payload-блоки пусты; `just ci-release` и `tools/embed_assets.py` создают итоговый файл со встроенным DEX и архивом ресурсов. Поэтому наличие рабочего embedded payload в этом raw-файле не заявляется.

Порядок запуска: Python подготавливает DEX и ресурсы; вызывает Kotlin `Plugin.inject(version, logReceiver, resourcesRootPath)`; затем регистрирует Python menu/settings controls; вызывает `Plugin.finalizeInject()`. Финализация инициализирует кэш эмодзи/стриков, устанавливает hooks, регистрирует badges view factory, ставит задачи и запускает цикл backup. Kotlin отбрасывает повторную инъекцию в текущем loader-е; меж-loader-экземпляры согласуются через `System.getProperties()` и ожидаемый `eject`. При eject снимаются все Xposed unhook handles, отменяются background scopes и очередь, закрываются UI и badges, база checkpoint-ится и закрывается через `EjectNotifier`.

Python добавляет элементы меню `CHAT_ACTION_MENU` через `add_menu_item(MenuItemData(...))`, хранит ID и снимает их при выгрузке. Для click callback оно пытается извлечь dialog ID из нескольких именованных ключей payload или объекта fragment, затем вызывает Kotlin `invokeChatContextMenuCallback(String, Long)`. Settings controls строятся из `Header`, `Selector`, `Switch`, `Text`; действия идут через `invokeSettingsActionCallback(String)`. Kotlin реестры action/callback регистрируются до `freeze()`. Это конкретный двусторонний контракт данного `.plugin`, не доказательство общего поведения всех версий ExteraGram callback payload.

Параметры update-check и автосоздания стриков сохраняются через host settings API и по умолчанию включены; размер pet FAB выбирается из 64/80/96/112/128 dp с исходным значением 80 dp. Переключатель update-check включает/останавливает Python checker; изменения автосоздания и размера после сохранения передаются Kotlin через setters `setAutoStreakCreationEnabled(Boolean)`/`setPetFabSizeDp(Int)` и также применяются при загрузке. Settings actions отдельно открывают emoji packs, запускают пересчёт всех личных чатов и создают ручной backup. Это поведение сверено с Python entrypoint и Kotlin action registry; описания пользовательского руководства являются docs evidence, а defaults и вызовы — code evidence.

## Hooks и жизненный цикл данных клиента

`Plugin.hookMethods()` ставит before/after handlers через XposedBridge, оборачивает callback в `Logger.tryOrFatal` и хранит каждый `XC_MethodHook.Unhook` для teardown. Устанавливаются `AccountSwitchHookBundle`, `ForegroundHookBundle`, `PetFabHookBundle`, `ServiceMessagesHookBundle` и `UpdatesHookBundle`.

- `AccountSwitchHookBundle` after-hooks reflection-находку `LaunchActivity.switchToAccount` (вариант с максимальным числом параметров), сравнивает `UserConfig.selectedAccount`, останавливает очереди других аккаунтов и планирует prune/rebind/update для выбранного.
- `ForegroundHookBundle` отслеживает `LaunchActivity.onPause/onResume`; после возвращения в foreground запрашивает проверку актуальных streak/pet данных.
- `PetFabHookBundle` обновляет плавающий FAB при resume чата и dismiss-ит при pause.
- `UpdatesHookBundle` до `MessagesController.processUpdates(Updates, Boolean)` разбирает короткие и обычные Telegram update objects, выделяет сообщения private user peers и ставит обработку в account queue. До `SendMessagesHelper.sendMessage(SendMessageParams)` обрабатывается текст исходящего сообщения. Для обоих путей код читает поля host controller через reflection и игнорирует account, который не выбран в данный момент.
- `ServiceMessagesHookBundle` меняет отображение сообщений плагина, заменяя специальные текстовые маркеры на host service/gift message presentation; перехватывает нажатия по нескольким таким карточкам для restore, приглашения питомца, принятия sync и импорта emoji pack.

Host-типы `LaunchActivity`, `MessagesController`, `SendMessagesHelper`, `ChatActivity`, `TLRPC`, `NotificationCenter`, `ChatActionCell`, поля/методы, найденные reflection-ом, и методы Aliuhook — **implementation dependencies этого репозитория**. Внешний ExteraGram SDK в snapshot представлен только в точке Python entrypoint и Gradle-зависимостях; внутренние host symbols нельзя переносить как заявленный публичный SDK API.

## Аккаунты, очереди и локальная база

Одна Room database называется `tg-streaks`, создаётся с контекстом host-приложения, имеет WAL и migration chain до schema version 14. Таблицы включают streak/restores/popups, pet/tasks, per-peer timezone, plugin relation, категории сервисных сообщений и emoji packs. Для данных чатов ключ обычно `(owner_user_id, peer_user_id)`. Controller получает `owner_user_id` как `UserConfig.getInstance(accountId).clientUserId`; поэтому пользовательские данные внутри общего файла различаются фактическим ID владельца, а не только порядковым account slot клиента.

Для фоновых операций есть `AccountTaskExecutor`: конкурентная map `accountId -> runner`, каждый runner — `Dispatchers.IO` + `SupervisorJob` и собственный `TaskQueue`. Очередь последовательно вызывает suspend tasks, ждёт foreground через `RuntimeGuard` и логирует/останавливается при uncaught failure. Основная plugin scope также отменяется при eject. Методы controllers обычно получают явный `accountId`; поверхностные click paths берут текущий `UserConfig.selectedAccount`. Это важное допущение проекта при переключении нескольких аккаунтов.

`Streak` считает день в выбранной для relation timezone, если есть сообщение и от владельца, и от peer. Видимость включается при длине 3; состояние `frozen/ended/canRestore` рассчитывается по датам последнего сообщения каждой стороны. Обычная логика обновлений может автоматически создать новый streak, если настройка включена; сообщения с `tg-streaks:` исключаются из обычной активности, кроме отдельной логики restore. Rebuild проходит дни назад и сопоставляет локальный/кэшированный диалоговый cache с `TL_messages_getHistory` при необходимости. Rebuild всех переписок выбирает личные пользовательские peers, пропуская ботов и группы.

Pet создаётся на relation и содержит daily задачи `EXCHANGE_ONE_MESSAGE` (+1), `SEND_FOUR_MESSAGES_EACH` (+2), `SEND_TEN_MESSAGES_EACH` (+4); выполнение требует обе стороны. Rebuild берёт cache, а при пустом результате запрашивает Telegram history; payload хранит направления, counts и message IDs, не текст переписки. Уровни питомца заданы thresholds 100/300/500/900 points. Питомец создаётся через контроллер, после чего немедленно запускается его rebuild (эта связь подтверждается кодом независимо от упомянутого в радаре конкретного commit).

## Сеть, синхронизация и сервисные сообщения

В Kotlin `ConnectionsManager.sendRequestBlocking(req, timeout, minRetryDelay)` оборачивает callback `ConnectionsManager.sendRequest` в coroutine outcome (`Success`, `Failure`, `RateLimit`, `TransientFailure`, `TimeOut`) и при timeout отменяет request. `RemoteChatHistoryFetcher` использует `TL_messages_getHistory` по выбранному `accountId`, пагинирует историю блоками, останавливается по границе локального дня/старейшему подходящему сообщению и фильтрует сервисные маркеры. При rate limit/transient error есть повтор с pause-aware задержкой. Это внутреннее использование Telegram RPC-клиента, а не generic network API для плагинов.

Python update checker отдельно делает HTTP GET к GitHub Releases `/repos/n08i40k/tg-streaks/releases/latest` с шестисекундным timeout и сравнивает `tag_name` с `__version__`. По результату он показывает bulletin со ссылкой на закреплённый Telegram post; автоматического download/install новой версии этот код не выполняет. У пользователя есть настройка отключения проверки.

Сервисные действия представлены отправляемыми текстовыми marker-ами `tg-streaks:*`, которые другой экземпляр плагина распознаёт и визуально переоформляет. Включая пет-приглашение/принятие/переименование, lifecycle streak, restore, sync offer/applied и экспорт emoji pack. Для отправки Kotlin `MessageSender` reflection-ом выбирает сигнатуру `SendMessagesHelper.prepareSendingText`/`prepareSendingDocuments` по ревизии клиента; это version-compatibility shim над приватными/изменяемыми внутренними методами.

Синхронизация — намеренная передача данных: из локальной базы создаётся отдельный `.sqlite3` snapshot только по паре текущего чата; source-side relation keys и направление участников меняются местами. В него кладутся relation/timezone/category, streak/restores, pet/tasks, затем snapshot отправляется как Telegram document через host `SendMessagesHelper`. Получатель нажимает кнопку, скачивает документ через `FileLoader`, импортирует relation в транзакции, заменяя совпадающие restore/task rows, обновляет cache и отправляет подтверждение. Это не передача всей локальной базы, но контент этой записи базы уходит собеседнику через Telegram. Обычный вычислительный путь локально читает метаданные истории через host Telegram API.

Поэтому формулировку FAQ «переписку никуда не отправляет» [следует читать узко](https://github.com/n08i40k/tg-streaks/blob/e9fa83619480964ccd3b8565af8c1301318ac7ad/docs/content/faq.mdx): код не показывает загрузку текстов переписки на собственный backend, но обращается к GitHub для update-check, к серверам Telegram для истории/отправки служебных сообщений, а при согласованном sync пересылает снимок состояния одного чата peer-у. В pet-task payload по коду остаются IDs/counts, не тела пользовательских сообщений.

## UI и HTML/WebView

Чат меню и settings controls остаются Python host UI; Kotlin отображает `StreakControlFragment`, timezone/category screens, streak info/calendar overlays и emoji-pack UI. В панели одного peer доступны timezone, plugin-installed relation flag, sync offer, категории сервисных сообщений, FAB visibility, create/rebuild/restore/delete и переход к началу streak; код проверяет private valid peer при создании панели.

Экран питомца и FAB используют локальные HTML/CSS/JS из `resources/streak-pet/{sheet,fab}.html`, выдаваемые через `ResourcesProvider`; Kotlin state serializes в JSON и передаётся `window.applyState(...)`. `StreakPetDialog` включает JavaScript/DOM storage и `allowFileAccess`, отключает content access, грузит документ `loadDataWithBaseURL` с локальным resource base URL и регистрирует `AndroidBridge` (`close`, `rename`, `log`, `error`). `rename` trim-ит значение и ограничивает 20 символами. Наблюдаемый bridge узкий, однако это не изолированный WebView sandbox audit; разрешение file access и конкретное поведение host WebView в runtime не проверялись.

## Сборка, артефакты и распространение

Gradle-проект применяет Android library, `io.github.exterastuff.plugin`, i18n4k и KSP; Kotlin/Java target 11, `minSdkMajor=26`, `targetSdkMajor=36` minor 1 в checked settings. `build.gradle.kts` компилирует Room/coroutines/datetime и i18n, привязывает compileOnly Aliuhook, Lifecycle ViewModel, RecyclerView, annotation classes, добавляет JDK desugaring и передаёт Kotlin classes/Dependencies в Extera DEX/R8 plugin config. `proguard-rules.pro` сохраняет `ru.n08i40k.streaks.**`, отключает obfuscation и сохраняет metadata, необходимые reflection bridge-у. `settings.gradle.kts` требует отдельный Badges SDK composite build, путь которого приходит из property/local.properties; GitHub release workflow скачивает его по repository/ref variables.

`just resources` пакует `resources/` в zip, `just embed` вызывает `tools/embed_assets.py`, который сжимает payload LZMA/XZ preset 9 extreme, кодирует Base64 и помещает строками-комментариями между маркерами. `just ci-release` готовит временную копию Python/pyproject с версией и `DEBUG_MODE=False`, запускает `buildDexRelease`, затем встраивает DEX и resources в `<id>.plugin`. Workflow запускается вручную с версией `x.x.x`, требует Telegram.jar, использует Java 21/Python 3.14/Android SDK, создает provenance attestations для `.plugin` и `classes.dex`, коммитит metadata/tag, публикует GitHub Release и обновляет media в Telegram channel post через bot token. Это чтение конфигурации; ни workflow, ни build здесь не запускались.

В source tree на SHA нет `AndroidManifest.xml` в составе исходника плагина и нет описанного отдельного plugin permission manifest. Код использует host application context, app database, Downloads path, Android document picker/ContentResolver, Telegram file APIs и network APIs; проверку фактических разрешений и поведения host-клиента нужно выполнять на конкретной сборке клиента. Релизный workflow имеет GitHub `contents: write`, `attestations: write`, `id-token: write`; это CI permissions, не permissions установленного Android-клиента.

## Практические выводы для разработки плагинов

1. **Разводить host entrypoint и основную логику:** Python регистрирует ExteraGram menu/settings controls и вызывает JVM static methods; Kotlin реализует domain logic. Каждый callback key и reflection signature образуют вручную поддерживаемый контракт — сверять обе стороны.
2. **Явно разделять account slot и стабильный user ID:** `accountId` нужен для host `getInstance(accountId)`/очередей, а таблицы relation используют `UserConfig.getInstance(accountId).clientUserId` и peer ID. Не хранить только индекс выбранного аккаунта как identity долгоживущей записи.
3. **Ограничить область истории:** использовать peer/type validation, owner/peer pair, дневную timezone и cursor progress; кэш читать первым, удалённую Telegram историю вызывать только когда cached fetcher не дал подходящих сообщений.
4. **Ставить teardown вместе с hook setup:** `Plugin` хранит handles централизованно и снимает их при eject; фоновые scopes/очереди отменяются до закрытия Room database.
5. **Отдельно продумывать privacy синхронизации:** здесь peer получает explicit `.sqlite3` snapshot только своей relation, сформированный как отдельная БД, а не ссылку на весь local DB. Обязательно описывать заменяемые данные и показывать действие применения пользователю.
6. **Разделять user backup и sync backup:** обычный backup копирует SQLite-файл после `wal_checkpoint(FULL)`, хранится под Downloads, auto interval 24h, максимум 30; восстановление заменяет текущие database/WAL files и требует переинициализации plugin.
7. **Кэшировать распакованные ресурсы по checksum и проверять zip paths:** source валидирует префикс `resources/` и что итоговый absolute path остаётся внутри staging directory до `extractall`.
8. **Не считать reflection и build references стабильным SDK:** hooks/send-message call-sites опираются на internal host class names/signatures, runtime support конкретных ExteraGram/AyuGram версий этим snapshot не доказывается.
