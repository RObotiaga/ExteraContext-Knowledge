## Технические факты

### Подтверждение отправки

`MediaConfirmHelper` возвращает `true` только когда для соответствующего типа включена настройка и доступны fragment, callback и parent Activity. При `false` штатный call-site продолжает отправку сразу. Положительная кнопка вызывает переданный `Runnable`; отрицательная закрывает диалог без callback. Для sticker можно показать превью документа через `BackupImageView`; для одного выбранного photo/video helper берёт `path`, а при его отсутствии `imagePath`; для пачки показывает число элементов.

Фактическая интеграция шире одного примера из радара: `ChatActivity` оборачивает выбор photo/video и отправку sticker; `ChatActivityEnterView` оборачивает GIF и ещё один путь отправки sticker. В GIF-пути сначала проверяется `MediaConfirmHelper.checkConfirmGif(...)`, затем — штатный `showConfirmAlert(...)`; helper можно поэтому использовать как пример добавления guard с сохранением штатного продолжения через Runnable. Проверенные call-site не доказывают, что этим покрыты все способы пересылки или отправки медиа.

### Жесты в просмотрщике видео

`isVideoGesturesAvailable(PhotoViewer, isCurrentVideo)` требует одновременно ненулевой viewer, включённую `NekoConfig.videoPlayerGestures` и признак текущего видео. `PhotoViewerWindowView.dispatchTouchEvent` первым отдаёт событие helper; пока жест активен, контейнер перехватывает дальнейшие события через `onInterceptTouchEvent` и обрабатывает их в `onTouchEvent`. Обнаружение жеста отменяет штатные жесты viewer и посылает `ACTION_CANCEL` дочерним View, чтобы seek bar/controls не продолжили старый touch.

После движения больше `16dp` направление выбирается по большей абсолютной дельте. Горизонталь становится seek, только если duration видео положителен; вертикаль выбирает brightness на левой половине окна и media volume на правой. Brightness ограничивается диапазоном `0.01..1.0` и применяется к `Window` Activity. Громкость меняется через `AudioManager.STREAM_MUSIC`. Seek вычисляется от начальной позиции с масштабом `90 000 ms` на полную ширину окна, ограничивается `[0,duration]` и вызывается на `ACTION_UP`; во время drag показывается целевое время и разница. Эти численные детали — реализация именно данного снимка, а не API контракты ExteraGram.

Состояние helper статическое (`currentGesture`, координаты начала, overlay); `PhotoViewer` вызывает `onReset()` при закрытии/сбросе просмотра. Это полезная подсказка для перехвата touch, но порт требует согласовать reset с реальным lifecycle окна и жестами основного клиента.

### DNS и WebProxy

В источнике два разных DoH пути, которые нельзя считать одним клиентским API:

1. `DnsFactory.lookup()` обслуживает DNS callback Telegram `ConnectionsManager`; при выключенном `useSystemDNS` сначала использует DoH, выбирает A/AAAA по IP strategy и при неудаче пробует системный resolver. `ConnectionsManager.DnsTask` передаёт результат обратно в native часть через `native_onHostNameResolved`. `DnsFactory.getTxts()` отдельно запрашивает TXT для DC-домена и подключается к `native_applyDnsConfig`.
2. `WebProxyManager` задаёт отдельный `okhttp3.Dns`: сначала пробует `Dns.SYSTEM`, затем последовательно опрашивает DoH JSON endpoints с timeout 5 секунд на HTTP connection. Этот resolver используется только созданным здесь OkHttpClient WebProxy. HTTP-транспорт плагинов из этого не следует.

`DnsFactory.providers()` поддерживает Auto и пять именованных групп (DNS.SB, AdGuard, Google, Cloudflare, AliDNS) плюс Custom. Именованный режим содержит несколько endpoints одного провайдера; Auto использует шесть резервных адресов, но непустой custom URL перекрывает список Auto. Запросы строятся как GET с `Accept: application/dns-json` и параметрами `name`/`type`. Код запускает запросы провайдерам параллельно в `Dispatchers.IO` и принимает первый непустой ответ. Затем системный DNS остаётся последним fallback. По коду не подтверждались доступность endpoint, приватность конкретного провайдера или задержка на устройстве.

Внутренние `cache` и `txtCache` — приватные `mutableMapOf`, ключ только hostname; в `DnsFactory` не видно TTL или пути инвалидации. Поэтому новая настройка provider/IP strategy может продолжить получать ранее сохранённый ответ в рамках процесса. Дополнительно `ConnectionsManager` выполняет DNS tasks через thread pool (минимум два потока), а эти карты не синхронизированы: конкурентный доступ возможен. Это статический вывод из кода, не воспроизведённая runtime-ошибка; при переносе задайте явную политику TTL/invalidation и потокобезопасности.

Для переноса DNS-кода критичен пропуск: вызываемый `NetworkRequestBuilder`/`NetworkResponse` есть в импорте `DnsFactory.kt`, но файлы с таким именем не находятся в полном закреплённом tree. Поэтому неизвестны настройки транспорта, политика timeout/retry/cancellation и его TLS/DNS поведение. Видимый `launch { delay(5000L) }` сам по себе не задаёт timeout сетевого запроса; timeout мог бы находиться в пропущенном builder.

`WebProxyManager.start(proxyAddress)` поднимает локальный `ServerSocket` на случайном порту, привязанный к `127.0.0.1`; `ConnectionsManager` передаёт этот loopback адрес native proxy API. Менеджер использует OkHttp для HTTP/WebSocket bridge, а DNS fallback вложен в его клиент. Не копируйте его как plugin transport без учёта loopback lifecycle, протокольного bridge и зависимости от native proxy-пути.

### Состояние радарных утверждений

- Радар о `MediaConfirmHelper`, `checkConfirmSticker`, `confirmSendSticker` подтверждается текущим кодом. При этом helper также имеет реальную GIF-точку в `ChatActivityEnterView` и photo/video-точку в `ChatActivity`.
- Радарное описание свайпов подтверждается текущим helper и интеграцией в `PhotoViewer`; реализация содержит ограничения для панели управления, режима редактирования, sticker/avatar и обычной навигации галереи.
- Радар описывал strict ECH/Cronet как сетевой эксперимент, затем в commit `2ef1033` зафиксирован `restore stable okhttp engine` и очистка сломанного Cronet. В закреплённом snapshot DoH не равен strict ECH: WebProxy использует OkHttp + DoH fallback. Считать прежний ECH стек текущей реализацией или готовым плагинным транспортом нельзя.
- README обещает Android SDK 33 / Build Tools 33, тогда как `TMessagesProj/build.gradle` в закреплённом snapshot использует compile/target SDK 36. Для точного build ориентируйтесь на build script конкретного SHA; README не подтверждает актуальность перечисленных SDK.

## Практические рецепты

1. **Добавить подтверждение к уже существующему send path:** вынесите проверку в helper `boolean check...(..., Runnable proceed)`. Возвращайте `true` только когда показан диалог; call-site тогда делает `if (!check(...)) proceed.run()`. Сохраняйте текущие schedule/reply/pay/caption-параметры в `proceed`, чтобы подтверждение не меняло смысл операции. Проверьте все точки отправки одного типа: код разделяет sticker/GIF entry view и photo picker.
2. **Добавить жест поверх сложного viewer:** сначала фильтруйте тип текущего элемента, edit mode и области controls; в dispatch фазе лишь распознавайте направление после touch slop. При захвате отправьте `ACTION_CANCEL` дочерним View, не допускайте повторной навигации галереи, обрабатывайте `ACTION_UP` и `ACTION_CANCEL`, сбрасывайте state при закрытии viewer. В рассматриваемой реализации эти части находятся в helper плюс `PhotoViewerWindowView`, а не в отдельном плагинном hook API.
3. **Проверить DNS поведение по слоям:** отдельно проследите `DnsFactory.lookup` → `ConnectionsManager.DnsTask` → `native_onHostNameResolved` и `WebProxyManager` → свой `OkHttpClient.dns`. Не подменяйте одним утверждением, что «клиент использует DoH»: здесь различаются порядок fallback, набор адресов и область применения.
4. **Собрать именно клиент-форк по документации snapshot:** README предлагает `git submodule update --init --recursive`, `./run init libs`, `./run libs native`, заполнение app id/hash и ключа в локальной конфигурации, затем Gradle. CI подтверждает важность submodules/NDK/JDK/native stages; точную задачу `assemblePublicRelease` и секреты смотрите в workflow выбранного SHA. Применение этих команд для сборки KPM-плагина не подтверждено.

## Build, debug и ограничения доказательств

- README (`README.md`, `README-EN.md`) документирует Linux/WSL/macOS, native tools, Android SDK/Build Tools 33, NDK `27.2.12479018`, submodules и последовательность `./run init libs` → `./run libs native` → `./gradlew assembleRelease`. Gradle-модуль на закреплённом SHA задаёт `compileSdkVersion 36`, `targetSdkVersion 36`, `minSdkVersion 21`, NDK из root property. Это клиентская сборка.
- PR workflow игнорирует изменения `*.md` и `*.xml`; правка только документации или XML-локализаций не запускает его. Debug workflow выставляет `DEBUG_BUILD=true`, вырезает `signingConfig signingConfigs.release` через `sed`, но всё равно вызывает `TMessagesProj:assemblePublicRelease`. Release workflow использует secrets `KEYSTORE_BASE64` и `LOCAL_PROPERTIES`, собирает native стадии и APK; это описание конфигурации файлов, а не проверка успешности CI.
- Единственный найденный целевой тест `DnsFactoryTest.testDns()` печатает результат `DnsFactory.lookup("google.com")`; assertions отсутствуют, и сам тест требует сети. Мы его не запускали. На исходниках нет измерений производительности/надёжности, проверок UX на устройстве или независимой валидации заявленного privacy.
- Исторический commit `2ef1033` заявлен как `restore stable okhttp engine ... clean up broken cronet`, содержит 16 файлов с +200/−1768 строк и удаляет Cronet strict-ECH артефакты/код. Для закреплённого последующего snapshot DoH/OkHttp есть в `WebProxyManager` и `DnsFactory`; strict ECH нельзя считать текущей реализованной функцией.
- В pinned tree не найден исходник импортированного `NetworkRequestBuilder`/`NetworkResponse`. Не исследованы все изменения форка относительно Telegram/NekoX, полный lifecycle каждого экрана и всех media send flows, runtime-разрешения DNS или совместимость методов с конкретной ExteraGram/AyuGram версией. Вся обработка остаётся `code`/`docs`, не `runtime-verified`.
