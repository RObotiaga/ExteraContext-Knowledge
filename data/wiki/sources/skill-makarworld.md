## Роль и границы

Skill предназначен для написания и отладки плагинов exteraGram на Python: описывает `BasePlugin`, lifecycle и hooks, UI/settings, клиентские и Android helpers, reflection/Xposed, Java class proxy, Elyx, файлы, intents, multi-account, dev server и соглашения `awesome-plugins`. README перечисляет слова и API, при появлении которых skill должен срабатывать, и просит при расхождении SDK-поведения отдавать приоритет текущей живой документации, а при соглашениях `awesome-plugins` — самому skill. Эти сведения отражают заявленное назначение источника; здесь не проверялись текущие официальные docs, SDK или клиент.

README предлагает установить сам skill командой `npx skills add makarworld/exteragram-plugin-skill -g -y`; это инструкция установки skill, а не SDK или плагина.

Границы покрытия: изучены `README.md`, `SKILL.md`, все 15 файлов `reference/*.md`, все 4 файла `examples/*.py` и MIT `LICENSE` из полного дерева снимка. Пакет не содержит исходников SDK, автоматизированных тестов, build pipeline или реализации описанных API. Примеры — учебные образцы, а справочные сигнатуры и lifecycle-контракты остаются утверждениями документации (`docs`), не runtime-подтверждениями.

## Технические сведения

### Базовая модель плагина и hooks

Для обычного плагина skill задаёт Python 3.11 / Chaquopy v16, базовый SDK `1.4.4.3` и практический минимум exteraGram `12.5.1+`; metadata должна быть плоскими top-level константами, поскольку loader, по документации, разбирает её через AST. Нужен класс-наследник `BasePlugin`. В `on_plugin_load` регистрируются hooks/listeners и запускаются фоновые задачи; `on_plugin_unload` отвечает за очистку собственных потоков, сокетов и observers. Документация описывает запуск load при включении/восстановлении приложения и unload при выключении/завершении. 

Сетевые event hooks подключаются `self.add_hook(request_name)` и `self.add_on_send_message_hook()`. Callback signatures включают `account`: `pre_request_hook(self, request_name, account, request)`, `post_request_hook(self, request_name, account, response, error)`, `on_update_hook(self, update_name, account, update)`, `on_updates_hook(self, container_name, account, updates)`, `on_send_message_hook(self, account, params)`. `HookResult` несёт поле, соответствующее типу события (`request`, `response`, `update`, `updates`, `params`). `DEFAULT` оставляет операцию без изменений, `CANCEL` останавливает её, `MODIFY` применяет изменённый объект, а `MODIFY_FINAL` также прекращает дальнейшую обработку плагинами. Само объявление метода не подключает outgoing hook: нужен вызов `add_on_send_message_hook()` в load callback.

События приложения представлены `AppEvent.START`, `STOP`, `PAUSE`, `RESUME`. `BasePlugin` предоставляет `get_setting`, `set_setting`, `export_settings`, `import_settings`; `reload_settings=True` пересобирает открытую страницу настроек и рекомендован только когда меняется её структура/видимость. Menu item объявляется через `MenuItemData`, добавляется `add_menu_item`, удаляется вручную `remove_menu_item`; документация говорит, что при unload меню очищается автоматически.

### UI, потоки, accounts и client helpers

`create_settings() -> List[Any]` возвращает строки `Header`, `Divider`, `Switch`, `Selector`, `Input`, `EditText`, `Text`, `Custom`. `SimpleSettingFactory` делит создание Android View (`create_view`) и привязку данных (`bind_view`), может принимать click/long-click callbacks и обёртываться в `Custom`. `run_on_ui_thread(func, delay=0)` предназначен для изменений UI. `run_on_queue(func, queue=PLUGINS_QUEUE, delay=0)` — для сети, файлов, тяжёлого разбора и вычислений; описанные очереди включают `stageQueue`, `globalQueue`, `cacheClearQueue`, `searchQueue`, `phoneBookQueue`, `themeQueue`, `externalNetworkQueue` и `pluginsQueue`.

Документация подчёркивает, что фоновые аккаунты остаются подключёнными и вызывают hooks. В обработчике следует передавать полученный `account` в account-scoped helpers или использовать `self.client(account)` (`AccountClient`); без явного аккаунта helpers используют выбранный в UI аккаунт и, по документации, предупреждают при несовпадении. Multi-account API (`account=`, `AccountClient`, `get_client`, `get_hook_account`, `get_selected_account`) указан для SDK `>=1.4.5.0`; методы `get_hook_account()` и `self.client()` без аргумента используют текущий hook scope, который распространяется также на вызванную из hook работу `run_on_queue` и callbacks `send_request`. `NotificationCenterDelegate.didReceivedNotification` получает `account`, но scope автоматически не задаётся. `get_media_controller()` указан как исключение: один глобальный instance без account аргумента.

`client_utils` описывает `send_request(TLObject, callback)` через `ConnectionsManager` выбранного/явно заданного аккаунта; callbacks получают response/error. `send_text`, `send_photo`, `send_document`, `send_video`, `send_audio` формируют параметры отправки и принимают `parse_mode`; `send_message(params, parse_mode=None)` — низкоуровневый helper поверх `SendMessageParams`. `edit_message(message_obj, ...)` ожидает реальный `org.telegram.messenger.MessageObject`; может заменить текст/подпись и медиа, а неподдержанный `parse_mode` вызывает `ValueError`. Для ручного преобразования HTML/Markdown в текст и `TLRPC.MessageEntity` есть `parse_text(text, parse_mode="HTML", is_caption=False)`.

Помимо controller helpers, `client_utils` предоставляет `get_last_fragment`, account-scoped controllers/storage/config/connection/file/download/notification helpers, `NotificationCenterDelegate` и `get_notification_center`; точное имя getter и требуемый account следует брать из соответствующей функции, а `get_media_controller()` остаётся глобальным исключением. Notification delegate не наследует hook account scope.

Android-facing helpers включают `R(fn)` как proxy для Java `Runnable`, `OnClickListener(fn)`, `OnLongClickListener(fn)`, `log(data)` и `copy_to_clipboard(text)`. Long-click callback должен вернуть bool: `True` потребляет событие. `log` передаёт простые значения как текст, сложные объекты — в Java-side inspector; clipboard helper показывает bulletin при успехе. `run_on_ui_thread` уже оборачивает callable в Runnable; `R` нужен, только когда принимающий API требует объект Runnable напрямую. `BulletinHelper.show_*` по документации сам показывает bulletin в UI thread; `AlertDialogBuilder` предоставляет message/loading/spinner dialogs, callbacks кнопок/элементов, lifecycle (`create/show/dismiss`) и progress; dialog mutations из фоновой работы требуют `run_on_ui_thread`.

### Установка, отладка и DevServer

`dev-workflow.md` предписывает включить plugin engine и developer mode в Preferences → Plugins. Пример предлагает держать файл `hello_world.py` с именем по `__id__`, использовать SDK `src/` для IDE и устанавливать файл копированием в app plugins directory либо DevServer. Для remote debugging документированы отдельный порт debugger (пример `5678`) и DevServer `42690`, ADB forwarding, платформы `vscode`/`pycharm` и IDE path mappings.

DevServer обменивается последовательными UTF-8 JSON объектами; `@` содержит команду, `#` — клиентский request ID, ответ повторяет ID. Описаны `ping`, `get_plugins`, включение/выключение/reload, `write_plugin`, удаление и запуск/останов debugger; Elyx дополняет их ping/list/hash-compare/change commands с compressed JSON в base64 `data`. Документированный robust client сначала проверяет соединение, ставит socket timeouts, сохраняет IDs, показывает полные ошибки, игнорирует caches/VCS dirs, debounce-ит события редактора и reconnect-ится после перезапуска приложения. Это протокол из документации; его auth/ACL не описаны.

Для Python 3.11 источник перечисляет предустановленные `beautifulsoup4`, `debugpy`, `lxml`, `packaging`, `pillow`, `requests`, `PyYAML`. PIP-подобный manager требует сеть, скачивает только universal `*-none-any.whl`, использует общую папку библиотек и допускает version conflicts; ограниченная поддержка markers не гарантирует работу сложных `extra`/условий. Доступность встроенных библиотек в конкретной версии приложения отдельно не проверялась.

### Reflection, Xposed hooks, Java proxy и intents

`hook_utils.find_class(fully_qualified_name)` возвращает Java `Class` или `None`; приватные поля читаются/меняются через `get_private_field` / `set_private_field` и static-варианты. Документированный safety advice — проверять `None`, оборачивать reflection в обработку ошибок и учитывать хрупкость к изменениям app-кода.

Важная reflection деталь: `find_class` уже возвращает `Class`; документация прямо запрещает вызывать на нём `getClass()` перед `getDeclaredMethod`/`getDeclaredConstructor`. Поля ищутся по иерархии class; instance и static helpers раздельные.

`MethodHook` даёт `before_hooked_method(param)` и `after_hooked_method(param)`; `MethodReplacement.replace_hooked_method(param)` заменяет исходную реализацию. `param.args` модифицируем; `param.setResult(...)` в before-hook пропускает оригинальный вызов. `hook_method` принимает callback или handler, priority и filters; есть `hook_all_methods`, `hook_all_constructors`, `unhook_method`; заявлено автоматическое снятие hooks на unload. Для перегрузок важны точные Java-типы аргументов. `HookFilter` покрывает null/true/false/equality/type для результата и аргументов, MVEL `Condition` и `Or`.

`@java_subclass(JavaClass, *interfaces)` строит Java subclass посредством DexMaker. `new_instance()` возвращает Python peer, а `.java` — Java instance для API с проверкой точного Java-типа. Декораторы `@joverride`, `@joverload`, `@jmethod`, `jfield`, `@jpreconstructor`, `@jconstructor`, `jMVELmethod`/`jMVELoverride` задают override/overload, новые методы/поля и constructor lifecycle. Класс должен быть subclassable; `final`-класс не подходит. Встроенные Chaquopy modifiers `.JA`, `.JGS`, `.JIR`, `.JS` и их отключающие варианты меняют доступ к членам, getter/setter preference, fluent return и safe chaining.

`IntentsManager.new_global_before_handler(...)` и `new_global_after_handler(...)` регистрируют глобальные обработчики с фильтрами scheme/host/path/query/action/type/categories/flags; callbacks получают только явно запрошенные параметры. Handle снимается через `.unhandle()` или `IntentsManager.unhandle(id)`. До-handler может вернуть ровно `True`, чтобы остановить последующие Python handlers и исходную Java обработку; after-handler этого сделать не может. Документированная нижняя граница — exteraGram build `66999` (`12.6.4+`). Параметр `required_path_args_names` вопреки названию перечисляет обязательные query-параметры.

### Файлы, Elyx и workflow

`file_utils` описывает каталоги плагинов/cache/files/images/videos/audio/documents, операции чтения/записи текста и bytes, list/filter и `FilesController`. У `FilesController.register(FileInfo(...))` возвращается secret, нужный вместе с расширением для `unregister`; `whitelist_places` и `blacklist_places` нельзя задавать одновременно, `get_icon` требует `SUPPORT_ICONS`. Описанные callback args включают origin place, file/path/name, message, activity и parent fragment.

Elyx — многомодульный ZIP-совместимый архив `.elyx`, `.eaf` и вариантов `.zip`; содержимое проекта должно быть в корне архива без дополнительной wrapper-директории. Reference называет поддерживаемые корневые файлы `refmap.yaml`, `refmap.yml` и `refmap.json` и рекомендует YAML. Для Elyx заявлен SDK `>=1.4.5.3`. `refmap` настраивает entry module, metadata, assets, strings и wheels; `metainfo.yml` хранит metadata. Плагин получает изолированное namespace `ElyxPlugins.<plugin_id>.*`; для локальных импортов документация рекомендует `elyx.import_module`. Entry module должен содержать concrete `BasePlugin` subclass; документация советует держать там один plugin class, поскольку loader создаёт первый найденный. Assets объявляются read-only; пользовательские изменяемые данные следует хранить через file utilities. Локализация поддерживает YAML/JSON/Python и fallback locale → English → key; документация просит поставлять английский каталог. `strings.pluralize` описан как три Slavic-style формы, не как полноценный CLDR.

Для зависимостей описаны три подхода: `requirements` через встроенный PIP-подобный менеджер, wheels внутри Elyx, либо namespaced локальные source packages. Shared PIP-папка рассчитана на universal `*-none-any.whl`; native extensions для Android ABI не поддерживаются этим механизмом, а конфликты версий между плагинами возможны. Bundled wheels идентифицируются по filename stem: изменённый wheel нужно пересобрать/переименовать. Required plugins проверяют наличие/версию, но не обещают стабильный Python API между плагинами.

Приведённая ElyxBuilder-рецептура: создать проект `elyb new`; запускать `elyb build --ast --verbose --no-folder` для source/AST build либо `elyb build --compile 2 --verbose --no-folder` для bytecode build (Python 3.11), из каталога с `refmap.yml`/refmap. `--ast` и `--compile` взаимно исключаются; результат помещается в `builds/`. CLI также описывает ignore-list (`add-ignore`/`del-ignore`), build stats и параметры отключения assets/build-info. `elyb watch` пересобирает, но не устанавливает архив. Для dev sync источник называет внешний `elyx_dev_client.py`, не включённый в SDK; ADB forward ведёт к dev server на `127.0.0.1:42690`. Elyx reload очищает локальные модули/hooks/menu items, но plugin обязан остановить созданные им threads/sockets/observers в unload и не оставлять process-global mutations. Release checklist требует clean archive install, locale/network/dependency проверок, disable/enable и upgrade проверки, сверки путей и корня архива, удаления caches, `.git`, virtualenvs и секретов.

Дополнительно Elyx публикует готовые proxies `OnClickListener`, `Runnable`, `Callback`/`Callback2`/`Callback3`, `CallbackReturn`; `gen` создаёт proxy одного Java interface method, `gen2` — multi-method proxy, а `mvel_execute(script, data, to_type=None, java_instance=None)` компилирует/кэширует MVEL и может преобразовать dict в `HashMap`. Troubleshooting отдельно перечисляет чувствительность Android paths к регистру, обязательный один concrete `BasePlugin` в entry module, правила imports/assets/strings и типовые причины stale behavior после reload (неостановленные потоки, listeners, monkey patches и кэши сторонних modules).

Для обычного `awesome-plugins` репозитория `.plugin` объявлен единственным source file плагина; отдельный build step не нужен, Ruff — единственная обязательная проверка до commit. Обновления `releases/vX.Y.Z/`, каталогов и Pluggy/security report выполняются только при публикации release; `pluggy_analyze.ps1` обращается к Pluggy API и требует `PLUGGY_SESSION` и `PLUGGY_CSRF`. Рекомендации по Pluggy и публикациям здесь являются правилами этого репозитория, не универсальным SDK workflow.

`repo-conventions.md` также требует прочитать `PluginFolder/docs.md` до edits; разделяет пользовательский README и developer docs; при изменении hook/architecture/settings обновлять per-plugin docs, при UX — README, а при изменениях репозитория — соответствующие корневые каталоги и страницы. Внешние публикации плагина на gist/file hosts запрещены: допускаются git и указанный локальный Telegram delivery path; raw GitHub link — только после commit в репозиторий. «Оформить релиз» в этом источнике перечислено как триггер полного flow; это описание правила репозитория, а не авторизация в иных задачах.

## Практические рецепты из источника

1. **Обычный плагин:** задать постоянные top-level metadata, создать ровно один `BasePlugin` subclass, зарегистрировать необходимые hooks в `on_plugin_load`, строить UI rows из `create_settings`. Для outgoing hook проверять, что `params.message` — строка; возвращать `HookResult()` для неизменённого payload.
2. **Ответ на update/request:** использовать переданный `account` в `self.client(account)` или `account=`. Для медленной сети/файлового I/O передавать работу в `run_on_queue`; UI-перерисовку — в `run_on_ui_thread`.
3. **Работа с Java:** сначала проверить `find_class` на `None`, выбрать точную перегрузку метода и types, затем зарегистрировать hook; ограничить эффект фильтром; сохранить handle и снять его вручную при необходимости. Отражение и замены могут сломаться при изменении приложения.
4. **Elyx:** выбрать multi-file формат при наличии модулей/resources/localization/wheels; положить в корень поддерживаемый refmap (`refmap.yml` рекомендован в документации) и держать entry module с одним concrete plugin class. Сначала выполнить source AST build, для bytecode использовать Python 3.11; перед release проверить именно clean archive install и исключить секреты/кеши.
5. **Разработка через DevServer:** только dev режим, endpoint `127.0.0.1:42690`; протокол включает изменяющие команды. Клиент должен использовать timeout, request id и показать полную серверную ошибку. Материал сообщает о способностях протокола, но не задаёт аутентификационный механизм или ACL.
6. **Релиз `awesome-plugins`:** обычная итерация меняет `.plugin` напрямую и запускает Ruff; release создаёт версионированную копию, changelog, обновляет каталоги и только тогда запускает Pluggy. Эти шаги — repository-specific workflow.

## Ограничения, безопасность и расхождения

- Базовая версия skill — SDK `1.4.4.3` / app `12.5.1+`, но отдельные features имеют более высокий порог: multi-account — SDK `1.4.5.0+`; Elyx — SDK `1.4.5.3+`; intents — app build `66999` (`12.6.4+`); custom Java class name требует app code `>=66690`. Нельзя считать все API доступными на базовом минимуме.
- README прямо отдаёт приоритет live docs для SDK поведения и самому skill для `awesome-plugins` conventions. Историческая дата scrape не указана; снимок говорит только о зафиксированном состоянии репозитория. Современные сигнатуры и client compatibility здесь не подтверждены.
- DevServer документирован как способ устанавливать, переписывать, включать, выключать, перезагружать и удалять plugin code. Источник помечает его development-only, но не описывает auth/ACL; это существенный предел сведений по безопасной границе.
- Reflection/Xposed способны менять приватные поля, аргументы и результаты или пропускать исходные методы; источник предупреждает о хрупкости, но не задаёт общий permission/consent model для такого кода.
- `requirements`/PIP полагается на сеть и общую папку библиотек; разрешены только universal pure-Python wheels в описанной схеме, version conflicts возможны. Bundled wheel — отдельный Elyx механизм, но native wheel должен быть совместим с Python 3.11, Android и ABI.
- `repo-conventions.md` описывает запрещённые сторонние публикации, допустимые git/local delivery, release-only Pluggy API calls и sensitive env vars. Это политика `awesome-plugins`, а не техническое ограничение самого SDK.
- В примерах встречаются безвредные демонстрации, а также hooks, меняющие Telegram request/outgoing-message flow. Примеры не выполнялись; они доказывают содержание снимка, но не реальное клиентское поведение.

## Пробелы

Не установлены фактические SDK сигнатуры, поведение callbacks на устройстве, compatibility конкретных версий клиента, точный scrape commit живой документации, runtime последствия hooks/reflection, реальный protocol security model DevServer, поведение PIP resolver в актуальной версии, и точные детали ElyxBuilder/dev client как инструментов. Никаких команд из skill, сборок, установок, обращений к DevServer/Pluggy или runtime тестов не запускалось.
