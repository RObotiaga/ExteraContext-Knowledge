# exteraless/exteraless

[Репозиторий](https://github.com/exteraless/exteraless) — Android-клиент на базе NagramX с перенесёнными возможностями exteraGram и собственным Python SDK/runtime. README подчёркивает модель разрешений плагинов и прямо называет проект beta: полнота переноса функций exteraGram не заявлена. Для разработки плагинов ценность источника — не только SDK, но и конкретная реализация его хоста: Chaquopy, Java bridge, hooks, permission gates и очистка ресурсов.

Снимок: ветка `main`, commit `5929d469d5dbda65da219361fa67b9b79ff31fb2`, получен 2026-09-27T15:47:28Z. Все ссылки ниже ведут в этот SHA. Лицензия по метаданным репозитория и LICENSE — GPL-3.0. README указывает package name `com.exteraless.app`, Chaquopy/Python 3.12 и ABI `arm64-v8a`/ `x86_64`. Сборка и приложение здесь не запускались.

## Архитектура и подтверждённые контракты

### Загрузка и lifecycle

- Java `PythonPluginsEngine` запускает Chaquopy `Python.start(AndroidPlatform(appContext))`, загружает `extera_utils.plugin_loader` и сериализует работы своим executor'ом ([PythonPluginsEngine.java:72-74, 103-135](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/java/app/exteraless/plugins/PythonPluginsEngine.java#L72-L135)). Загрузка вызывает `PluginSinkGate.install()`, затем loader; выгрузка вызывает Python unload и снимает ссылки на instance ([там же:227-260, 284-327](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/java/app/exteraless/plugins/PythonPluginsEngine.java#L227-L327)).
- Контроллер сканирует каталог плагинов с расширениями `.py`, `.plugin`, `.elyx`, `.eaf`, читает метаданные и хранит enabled по ID; Safe Mode прекращает автозагрузку. Повторная загрузка сначала unregister/unload, затем читает свежие метаданные и загружает снова ([PluginsController.java:339-405, 608-620, 742-775](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/java/app/exteraless/plugins/PluginsController.java#L339-L405)).
- Python SDK требует наследника `BasePlugin`. Основные callbacks: `on_plugin_load()`, `on_plugin_unload()`, `on_app_event(event_type)`, `create_settings()`, `pre_request_hook(request_name, account, request)`, `post_request_hook(request_name, account, response, error)`, `on_send_message_hook(account, params)`, `on_update_hook(update_name, account, update)`, `on_updates_hook(container_name, account, updates)` ([base_plugin.py:483-525](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/base_plugin.py#L483-L525)).
- Loader вызывает load callback в plugin context; unload удаляет registry entry, вызывает unload callback, запускает SDK cleanup, удаляет импортированный module, забывает class ownership и очищает callbacks/custom views ([plugin_loader.py:2002-2047, 2088-2128](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/extera_utils/plugin_loader.py#L2002-L2047)).
- `PluginRuntime` держит активный plugin ID и глубину Python-callback на `ThreadLocal`; `enter/exit` восстанавливают прежний scope, а `enterPython/exitPython` позволяют Java sink определить, что callback идёт из Python ([PluginRuntime.java:21-79](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/java/app/exteraless/plugins/PluginRuntime.java#L21-L79)). Python hook dispatcher отдельно ставит plugin ID и account в thread-local scope и восстанавливает оба в `finally` ([plugin_loader.py:2200-2229](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/extera_utils/plugin_loader.py#L2200-L2229)).

### Метаданные, разрешения и доверие

- Метаданные считываются статически: parser строит AST и извлекает только top-level literal constants, не исполняя импорт/код плагина. Поля включают `__id__`, `__name__`, версии, `__requirements__` и `__permissions__`; неверный ID или неизвестное право дают ошибку метаданных ([metadata_parser.py:19-43, 86-125, 188-257](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/extera_utils/metadata_parser.py#L19-L43)).
- Список разрешений: `messages.read`, `messages.send`, `network`, `files`, `intents`, `settings`, `hooks`, `native`; `ui` всегда включается отдельно и не сохраняется как запрашиваемое. `hooks` и `native` отмечены как опасные права ([PluginPermissions.java:39-85, 174-190](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/java/app/exteraless/plugins/PluginPermissions.java#L39-L85)).
- При установке сканер анализирует capabilities, затем экран согласия передаёт выбранные grants в preferences. Без obfuscation предложенные права строятся по обнаруженным возможностям; если scan пуст или код обфусцирован, берётся объявление плагина либо весь requestable список. Поэтому scan формирует рекомендацию/объяснение, а не независимое доказательство безопасности ([PluginInstallHelper.java:238-275, 289-330](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/java/app/exteraless/plugins/PluginInstallHelper.java#L238-L275)).
- Уровни доверия — `ISOLATED`, `GATED`, `TRUSTED`; по умолчанию новый уровень isolated. При isolated эффективные права сводятся к UI, gated лишается `hooks/native`, trusted может их иметь. Сохранённые grants и trust level представлены отдельно ([PluginTrustLevel.java:33-40, 59-107, 110-125](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/java/app/exteraless/plugins/PluginTrustLevel.java#L33-L40)).
- Permission checks есть на публичных Java bridge-сервисах, например перед method hooks, proxy class generation, файловыми handlers и intent handlers ([PluginServices.java:34-59, 84-119, 146-187](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/java/app/exteraless/plugins/PluginServices.java#L34-L59)). Дополнительные Python audit hooks фиксируют и ограничивают часть файловых, сетевых и native событий ([audit_gate.py:487-580, 595-612](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/extera_utils/audit_gate.py#L487-L580)); Java `PluginSinkGate` пытается перехватывать shell/process, network, class resolution, Telegram send/request и code-loader sinks ([PluginSinkGate.java:122-142, 164-186, 390-457](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/java/app/exteraless/plugins/PluginSinkGate.java#L122-L142)).
- Ограничение модели: комментарии `PluginSinkGate` прямо признают, что gate действует только пока Java может определить plugin execution context и что Java `FileInputStream` полностью не закрыт; Python audit hook лишь дополняет его ([PluginSinkGate.java:15-44](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/java/app/exteraless/plugins/PluginSinkGate.java#L15-L44)). Python import/open guards и audit install содержат best-effort/error fallback, в том числе fail-open при отдельных ошибках определения caller/permission ([plugin_loader.py:815-884, 1076-1106, 1677-1716](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/extera_utils/plugin_loader.py#L815-L884)). Это permission-gated runtime, не OS sandbox.

### SDK-поверхность и интеграции

- `BasePlugin.add_hook(name, match_substring=False, priority=0)` подключает request callbacks; исходящий message hook подключается явно через `add_on_send_message_hook(priority=0)`. Реализация запроса передаёт ID, pattern mode и priority Java bridge; эти callbacks автоматически не активируются лишь от override метода ([base_plugin.py:512-525, 634-676](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/base_plugin.py#L512-L525)).
- `HookResult`/стратегии дают hook-ам контролируемый контракт исходного/изменённого результата; dispatcher трактует DEFAULT как отсутствие модификации и передаёт MODIFY-поле обратно вызывающему Java слою ([base_plugin.py:43-65](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/base_plugin.py#L43-L65), [plugin_loader.py:2200-2229](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/extera_utils/plugin_loader.py#L2200-L2229)).
- Xposed-style SDK API: `hook_method(method, handler=None, priority=50, filters=None, before=None, after=None, before_filters=None, after_filters=None)`; `method` может быть Java Method/Constructor или пара `(clazz, name)`. Несколько overloads приводят к списку unhook IDs. Есть `hook_all_methods`, `hook_all_constructors`, `unhook_method`; hooks требуют `hooks` permission через PluginServices ([base_plugin.py:817-903](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/base_plugin.py#L817-L903), [PluginServices.java:34-58](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/java/app/exteraless/plugins/PluginServices.java#L34-L58)).
- `client_utils.AccountClient` позволяет связывать helper-операции с account: явный account имеет приоритет, затем hook scope, иначе UI-selected account. Обычные module-level helpers при отсутствии account выбирают UI-selected account и могут залогировать warning внутри hook; при hook dispatch account scope ставится и восстанавливается ([client_utils.py:69-142, 745-855](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/client_utils.py#L69-L142)).
- `send_text` и `send_message` требуют `messages.send`, отправку переводят на Android UI thread, преобразуют Python dict/list в Java map/list и поддерживают набор полей SendMessageParams. Нельзя передавать сырой integer как replyToMsg: в этом клиенте ему неоткуда получить dialog context ([client_utils.py:461-525](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/client_utils.py#L461-L525)).
- Для callback/UI SDK предоставляет `android_utils.run_on_ui_thread(func, delay=0)`, создаёт Java Runnable-compatible proxy и оборачивает вызовы в `safe_call`; permission/error исключения логируются и превращаются в отсутствие результата, чтобы исключение не вышло через Java callback ([android_utils.py:85-133, 165-185](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/android_utils.py#L85-L133)).
- `BasePlugin.get_setting/set_setting/export_settings/import_settings` мостят сериализованные JSON значения в plugin-keyed Java preferences; локальный Python cache инвалидируется на write/error. Это настройки SDK-плагина, отдельно от произвольных файлов ([base_plugin.py:567-630](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/base_plugin.py#L567-L630)).
- `file_utils.get_plugin_dir(plugin_id)` предоставляет plugin-owned `.data/<id>` каталог; SDK helper проверяет, что target path принадлежит этому каталогу, иначе требует `files`. Для чтения/записи вне каталога нужно явное право ([file_utils.py:62-78, 108-186, 296-342](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/file_utils.py#L62-L78)).
- `IntentsManager.new_global_before_handler(fn, priority=0, **filters)` и `new_global_after_handler(...)` регистрируют фильтруемые обработчики из plugin context; возвращается handle с `unhandle()`. Java bridge проверяет `intents`, а выгрузка должна снимать handlers владельца ([intents.py:140-195, 199-213, 232-249](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/intents.py#L140-L195)).
- `.elyx/.eaf` проходят отдельную структурированную загрузку: archive/refmap/metainfo читаются и проверяются до импорта, строится plugin-specific namespace и environment (settings/metainfo/refmap, optional assets/strings), а unload удаляет namespace, environment и загруженные модули ([elyx_runtime/loader.py:228-247, 256-337, 340-356](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/elyx_runtime/loader.py#L228-L247)).

## Практические выводы и рецепты

1. Для нового Python плагина начинай с одного `BasePlugin` наследника и константных module-level `__id__`/`__name__`; объявляй права в `__permissions__`, но воспринимай экран установки и фактически сохранённые grants как решающий пользовательский выбор. Метаданные читаются AST-парсером до выполнения plugin module.
2. Реализуй lifecycle cleanup явно: сохраняй handles для menu/intents/hooks, снимай их при unload при необходимости и не полагайся на Python module eviction как замену закрытию собственных потоков/ресурсов. Loader выполняет предусмотренный SDK cleanup для отслеживаемых hooks/callbacks, но произвольные ресурсы должны иметь свой lifecycle.
3. Для TL request и outgoing-message hooks сначала override соответствующий callback, затем зарегистрируй hook через `add_hook`/`add_on_send_message_hook`; проверь стратегию `HookResult`. Для Android UI отдавай работу через `android_utils.run_on_ui_thread`; для сетевых/файловых операций указывай account и явно требуемое разрешение.
4. В hook callback используй `self.client`/ `get_client()`, если нужны операции для того же аккаунта. Module-level helpers при `account=None` используют UI-selected account, даже внутри callback; явный account снимает неоднозначность.
5. DEX/Java hook — мощная операция с правом `hooks`; зафиксируй unhook IDs и проверяй результат `None`/пустого списка, поскольку bridge может отклонить операцию или runtime hook engine может быть недоступен.

## Developer support и зависимости

- `dev_server` — TCP/JSON интерфейс разработчика на `127.0.0.1:42690`: только `ping` проходит без токена, прочие команды требуют session token. Он даёт list/enable/disable/reload/install/remove и debugger commands ([dev_server.py:190-225](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/dev_server.py#L190-L225)); `write_plugin` передаёт файл штатному installer callback. Токен публикуется в `.devserver_token` и в app log. Комментарий к коду подчёркивает, что loopback не является межприложенческой границей Android, поэтому сервер следует считать доступным с устройства ([dev_server.py:22-56, 134-173, 244-269, 324-344](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/dev_server.py#L22-L56)).
- `pip_controller.ensure_requirements(plugin_id, requirements)` читает PyPI JSON API и выбирает только совместимые pure-Python wheel; native wheel отклоняется. Зависимости распаковываются в общие для плагинов каталоги и учитываются в manifest; при снятии последней plugin reference файлы удаляются и путь чистится из `sys.path` ([pip_controller.py:1-12, 269-314, 377-467](https://github.com/exteraless/exteraless/blob/5929d469d5dbda65da219361fa67b9b79ff31fb2/TMessagesProj/src/main/python/pip_controller.py#L269-L314)).

## Связь с радаром и оставшиеся пробелы

Радар называет exteraless совместимым ExteraGram/NagramX-клиентом и отмечает изменения PluginRuntime, UI thread, reload, Python↔Java proxy и keep-alive cancellation. README и код подтверждают наличие собственного SDK/runtime и NagramX-производность, но предоставленный `radar-urls.json` пуст; конкретный commit из исторических заметок и перечисленные там исправления не сопоставлены отдельным permalink/patch, поэтому они не считаются подтверждёнными фактами этой страницы. Аналогично идеи «перенести» функции клиента — не существующие plugin API.

Непокрыты: полный перечень helpers/UI widgets/media API и меню; весь поток сериализации/приоритета Xposed hooks и request hooks в host клиенте; все permission sinks и обходы; детальные edge cases всех команд dev server и package installer; сборка по GitHub Actions не проверялась; взаимодействие с системными Android-процессами на реальном устройстве; реальные сценарии установки, unload, reload и watchdog. Статические тесты из snapshot не запускались, runtime не проверялся. В текущем снимке README описывает безопасность как модель разрешений/изоляции, но код явно best-effort внутри процесса и содержит fail-open обработчики; не следует описывать это как строгую песочницу.
