# Link Guard: проверка ссылок и очистка меток в ExteraGram/AyuGram

Источник: [L0lopop/Link-Guard](https://github.com/L0lopop/Link-Guard), закреплённый снимок `b9cd180c83b47a724970e026f64ec8039cc0f650` (ветка `main`, сохранён 2026-09-27). В `repository.json` указана лицензия MIT. Это один Python-файл плагина с использованием ExteraGram Plugin API и Telegram-классов, а не SDK или официальный контракт клиента. Проверена только версия исходника; установленное приложение и runtime не проверялись.

## Что подтвердилось и что устарело в радаре

Радар от 12 сентября называет Link Guard версией 1.4.1 и сообщает о локальной базе примерно из 2,84 млн адресов. В pinned tree entrypoint уже объявляет **1.7.0** и минимальную версию приложения `>=12.1.1`; `update.json` также указывает 1.7.0. В сохранённом `state/manifest.json` от 12 сентября записано 2 984 804 элемента после семи успешных feeds. README того же снимка говорит «больше 3 млн» и перечисляет одиннадцать публичных списков, а `build_db.py` содержит девять открытых feeds и три дополнительных feed с API-ключами. Это разные временные срезы/режимы доступности: число из старого радара нельзя выдавать за состояние pinned code или гарантированный объём следующей сборки. Источник действительно содержит локальный формат базы и ежедневный GitHub Actions workflow; текущий manifest — только сохранённый исторический результат, а не live-счётчик.

## Механика проверки и URL-фильтрации

`analyze(url, aggressive=False, whitelist=(), anchor=None)` разбирает scheme/hostname, возвращает объект `Verdict` с host, отображаемым IDNA-доменом, флагами уровня риска, очищенным адресом и удалёнными query-параметрами. Неразбираемый URL помечается как высокий риск; схемы `javascript`, `data`, `file`, `intent`, `content`, `jar` также немедленно получают высокий риск. Для проверки код принимает пустую схему и `http`, `https`, `ftp`; любая другая схема, включая `tg`, возвращает пустой verdict до разбора host. При этом `URL_RE` отдельно распознаёт `tg://`, поэтому такая ссылка может попасть в меню или outgoing-cleaning, но анализатор не проверит её как URL назначения. До lookup базы проверяется whitelist: совпадение по host/registrable domain/IDNA display form завершает анализ без любых risk flags, в том числе blocklist, но URL всё равно очищается от tracker parameters. Затем код применяет список вредоносных доменов с обходом родительских suffix-ов до границы общих hosting-платформ, популярность, confusable/смешение письменностей, опечатки известных брендов, бренд в поддомене, расхождение видимой подписи anchor entity с destination, IP/port, слова-приманки, исполняемые расширения, репутацию TLD и свежерегистрированные имена. Это plugin-specific эвристики, не универсальный URL validator.

`clean_url(url, aggressive=False)` разбирает query через `urlsplit`, сравнивает percent-decoded имена параметров без учёта регистра с набором точных tracker names и префиксами (`utm_`, `pk_`, `mtm_`, `piwik_`, `hsa_`, `at_custom`, `stm_`, `matomo_`, `sc_`). Агрессивный режим расширяет список (`ref`, `si`, `spm`, `from` и др.). Сохраняемые query segments, path и fragment остаются исходными; malformed URL при исключении возвращается без изменений. Проверка `analyze` отдельно помечает опасные схемы и расширения `.apk`, `.exe`, `.msi`, `.scr`, `.bat`, `.cmd`, `.jar`, `.vbs`, `.apks`, `.xapk`.

При открытии плагин перехватывает `org.telegram.messenger.browser.Browser.openUrl` через `MethodHook.before_hooked_method`. Он ищет аргумент, похожий на URL, проверяет временный bypass, анализирует ссылку и либо тихо заменяет аргумент очищенным URL, либо подавляет исходный вызов через `param.setResult(None)` и показывает диалог с решением пользователя. При высокой опасности положительная кнопка — Cancel; для остальных уровней — Open. Если UI недоступен, высокорисковая ссылка блокируется toast-ом в завершённом async-flow; обычный `on_open_url` без диалога оставляет переход и применяет только чистку, если аргумент можно заменить. После согласия ссылка повторно открывается через `Browser.openUrl`, reflection `method.invoke` или Intent fallback; URL помещается в десятисекундный bypass, чтобы рекурсивный hook не мешал.

Источник и подпись ссылки берутся из Telegram update payload: подписки на шесть имён `TL_update*` записывают пары URL→source и destination→видимый anchor entity. Для entity offset/length код конвертирует UTF-16 code units, как ожидается для Telegram Java text offsets. Сообщения канала/чужого пользователя дают более строгий источник `unknown`, собственные сообщения и контакты — `trusted`; trust ослабляет показ лишь слабых замечаний, но опасные verdict продолжают предупреждать. Эти `TL_update*`, `Browser.openUrl`, `android.net.Uri`, `ApplicationLoader`, `MessagesController` — client internals, которые проект может менять; `BasePlugin`, `MethodHook`, `HookResult`, `HookStrategy`, `MenuItemData`, `MenuItemType`, settings controls и методы регистрации hooks/menu — импортируемый plugin API по коду этого проекта.

Пункт меню **Проверить ссылки** собирает URL из текста сообщения и `messageOwner.entities[*].url`, дедуплицирует, проверяет первые пять и показывает список verdict-ов. **Копировать без трекеров** очищает каждую найденную ссылку и копирует newline-separated список, не редактируя исходное сообщение. Автоматическая исходящая чистка имеет отдельный switch и работает только по `URL_RE` в `params.message`; при наличии непустого `params.entities` функция возвращает обычный `HookResult()` без модификации, чтобы не рассинхронизировать entity offsets. В конце она сообщает `HookResult(strategy=HookStrategy.MODIFY, params=params)`. Сопоставление menu и send callback в снимке показывает, что именно меню отдельно получает `entity.url`, а outgoing hook его не обрабатывает; исходящий hidden-text destination не очищается этим hook.

## Сеть, настройки, storage и безопасность

Сам `analyze` использует локальную базу. Исключения видны явно по call-sites: раскрытие shortener делает HTTP HEAD с redirect-following, а при статусе ≥400 или отсутствии истории пытается GET с `stream=True`; опциональная проверка возраста отправляет registrable domain на `rdap.org`; проверка обновления раз в шесть часов читает `update.json`; база каждые три часа опрашивает release `manifest.json` и загружает `full.lgdb` только при необходимости/в ручном режиме. База ограничивает manifest 64 KiB и сам файл 24 MiB, проверяет magic/format/структуру, загружает и разбирает файл до установки, затем пишет временный `.part` и атомарно заменяет активный файл. При испорченном локальном файле код удаляет его. Запись ищется по `get_plugins_dir`, `get_cache_dir`, `get_documents_dir`, Android app cache и `tempfile.gettempdir()`; при нескольких каталогах плагин счищает дубли DB из остальных.

Обновление плагина вручную требует согласия на диалоге. Загруженный файл ограничен 2 MiB и предварительно проверяется лишь по первым 4096 байтам: в них должны быть `__id__ = "link_guard"` и `__version__`; это распознавание собственного формата, не криптографическая подпись. Затем код проверяет, что `PluginsController.getPluginEngine(JavaFile(path))` распознаёт файл, и открывает standard install dialog. Источник сети имеет триггеры/переключатели в UI; доменный возраст выключен по умолчанию. Автоматического запроса системного permission в коде нет; репозиторий не содержит Android manifest или отдельного permissions declaration, поэтому точную модель выдачи доступа host-клиентом этот источник не устанавливает.

Параметры живут в `BasePlugin.get_setting`/`set_setting`: switches для проверки, режима показа, очистки на открытии/исходящей отправки, агрессивной очистки, whitelist, database, update, RDAP, языка, статистики и debug log. README и строки UI описывают настройку; код показывает значения по умолчанию (`check_enabled=True`, `show_mode=0`, `expand_short=True`, `check_age=False`, `clean_on_open=True`, `clean_outgoing=False`, `aggressive=False`, `use_database=True`, `check_updates=True`). README описывает ограниченный режим старых клиентов и невозможность удалять доверенные домены без long press; текущий plugin metadata одновременно задаёт `__app_version__ = ">=12.1.1"`, поэтому реальный доступ старых сборок к plugin engine этим snapshot не подтверждается. В репозитории нет собственной БД пользовательских настроек: их persistence делегирован host API. Локальные временные кэши verdict/source/anchor/ages — обычные Python dict в памяти процесса; они очищаются по лимиту (200/300) и время жизни verdict 300 секунд, возрастной cache максимум 200 записей.

## Build, CI и проверяемость

GitHub Actions `feeds.yml` запускает `scripts/build_db.py` ежедневно в `02:30 UTC` и вручную, с `contents: write`; optional `ABUSE_CH_KEY` и `PHISHTANK_KEY` передаются secrets, а публикация загружает/заменяет `full.lgdb` и `manifest.json` в release `feeds`. Сборщик объединяет девять feeds без ключей и до трёх keyed feeds, требует минимум три живых источника и 500 000 итоговых адресов. Также загружает Tranco, Public Suffix List и cenk/nrd; формирует восемь секций `MALW/WHIT/BRND/TLDR/PLAT/SUFX/FR10/FR30` и публикует JSON manifest. В конкретном алгоритме 50 000 самых популярных имён удаляются из threat membership, следующие решения эвристик для известных доменов подавляются для верхних 200 000, а отдельные common-service hosts и tenant-hosting platforms фильтруются по своим наборам правил. Если адрес всё же есть в MALW, lookup базы имеет приоритет над популярностью. Это описывает построение этой базы, а не гарантию её точности. `keepalive.yml` ежемесячно копирует последний release manifest в `state/manifest.json` и делает commit (либо пустой commit при совпадении). Эти workflow относятся к сборке/доставке базы, а не компилируют плагин.

`tests/test_link_guard.py` загружает плагин под Android/host stubs и содержит проверки URL cleanup, типов угроз, dialog/hook flows, whitelist, counters, updater, database, entities, языка и старого SDK без UI/menu/hooks. `tests/test_db_format.py` проверяет формат/разделы базы и предполагает ранее созданный файл; его тесты включают реальные файлы данных (популярные сайты, эвристики false-positive и производительность). README предлагает `python tests/test_link_guard.py` и `python scripts/build_db.py && python tests/test_db_format.py db`, но в рамках этого исследования их не запускали и результат прохождения не заявляется.

## Пробелы

- `radar-urls.json` содержит только URL репозитория, поэтому historical commits вокруг 12 сентября отдельно не привязывались; radar-context — пересказ, а не первичное доказательство.
- Нет runtime/device-проверки host API, всех `Browser.openUrl` overloads, update/entity hooks, разрешений, сетевых endpoint-ов, безопасной установки и фактической совместимости с любой конкретной версией APK.
- Update callbacks получают `account`, но не используют его; `_message_source` обращается к `get_messages_controller()` без явного account. Выделение источника доверия в multi-account client поэтому описано только по call-site, а account-scoped поведение helper-а и отсутствие смешения аккаунтов не установлены.
- `URL_RE` включает `tg://`, но `analyze` не проверяет схемы вне empty/http/https/ftp; результат для таких URI — пустой verdict. Реакция клиента на открытие этой схемы не проверялась.
- Whitelist имеет приоритет перед blocklist и эвристиками. Это следует из раннего return в коде; ожидаемая policy-роль исключений пользователем в runtime не проверена.
- Нет тестового запуска/сборки в этом ingest. Описаны только tests/workflows, сохранённые в snapshot.
- Число и состав feeds/entries меняются: `state/manifest.json` — сохранённый срез от 2026-09-12, текущий build source описывает потенциальные feeds, а README — продуктовую формулировку. Точное состояние release на дату ответа не запрашивалось.
- README утверждает, что старые сборки работают в reduced mode, но metadata указывает минимальную версию `>=12.1.1`; фактическая доступность settings/long press вне этого порога не проверялась.
