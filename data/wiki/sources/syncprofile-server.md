## Фактический HTTP-контракт клиента

`sync.plugin` задаёт base URL `https://sync.efn.mom`, cookie name `sync_access`, User-Agent `SyncProfile/<version>` и три операции: `GET /api/profiles/all`, `GET /api/profiles/updates?since=<timestamp>`, `POST /api/profile`. Для обновления одного пользователя используется `GET /api/profile/<user_id>`. Все эти маршруты и форматы — наблюдаемые ожидания клиента, а не доказанные серверные endpoints: реализации сервера в snapshot нет.

Для GET-клиент отправляет `Cookie: sync_access=<значение настройки>`; POST дополнительно посылает JSON и `Content-Type: application/json`. Код различает HTTP 403 («неверный auth_key») и 401 («доступ заблокирован / Cookie»), поэтому `auth_key` включён в профильный JSON, а cookie передаётся отдельно в заголовке. Это лишь клиентская интерпретация ошибок; точные правила авторизации сервера неизвестны. `auth_key` читается из plugin setting, но для него нет поля ввода в `create_settings()`. В исходнике присутствует статическое значение cookie по умолчанию, но настройки адреса и cookie скрыты условием `ALLOW_CUSTOM_SERVER_CONFIG = False`; сам факт размещения значения в публичном snapshot следует учитывать при самостоятельном развёртывании и смене секретов.

Полный sync добавляет `If-Modified-Since` из `_last_sync_timestamp`, если вызван с `force_clean=False` и сохранён timestamp. Ответ `304` трактуется как отсутствие изменений. При `200` код принимает `profiles` как dict или list, выбирает `sync_time`, затем `server_time`, затем `timestamp`, и лишь при отсутствии всех трёх использует локальное текущее время. Delta-запрос передаёт timestamp параметром `since`; его обработчик ожидает `profiles` как mapping `user_id -> profile`, применяет только изменившиеся ID и обновляет timestamp даже при пустом mapping. Серверный смысл, сортировка, границы timestamp, удаление профилей и гарантия монотонности из клиентского кода не выводятся.

При публикации профиль строится по одному слоту аккаунта. Поля: `user_id`, `premium`, `emoji_status_id`, `name_color`, `name_bg_emoji_id`, `profile_color`, `profile_bg_emoji_id`, `client_type`, `auth_key`. Код фиксирует `client_type` как `AyuGram`; README при этом называет плагин предназначенным для AyuGram и exteraGram, так что единый протокол для обеих платформ данным файлом не доказывается. Один аккаунт и последовательная отправка активных аккаунтов делают `POST /api/profile` в daemon thread; таймауты — 6 и 5 секунд соответственно. Пакетный сценарий допускает частичный успех и сохраняет профиль только для получивших HTTP 200.

## Lifecycle, локальное применение и storage

`on_plugin_load` загружает локальный cache, импортирует доступные поля официального Premium, инициализирует TLRPC, строит snapshot и ставит hooks. Первичная синхронизация ждёт одну секунду: пустой cache или нулевой timestamp ведёт к полному fetch, иначе к delta. Периодический опрос выполняется раз в 60 секунд, пока `_is_running`; при установленной ZwyLib задачи идут через `async_manager`, иначе используются daemon threads. `on_plugin_unload` выключает loop, просит async manager отменить задачи плагина, снимает hooks и сохраняет cache.

Cache хранит maps `profiles` и `chats`: с ZwyLib используется `JsonCacheFile("sync_profiles_cache.json", default={}, compress=True)`, затем fallback к JSON-файлу с тем же именем, затем строка настройки `_local_profiles_json`. Загрузчик также принимает legacy flat map. Радар говорит о восстановлении после очистки кэша: в коде есть ручной clear и полный fetch по следующему циклу/действию, но автоматическое обнаружение очистки файлового кэша и гарантия восстановления при любой потере данных не установлены.

Кэш profiles читается быстрым путем из копируемого snapshot, с fallback под `threading.Lock`. Delta worker пытается частично обновить snapshot затронутых UID, но в `_update_snapshot_partial()` после записи профилей вызывает `self._patch_cache.pop(...)`, хотя поле нигде в этом SHA не создаётся и changelog v10.2.34 сообщает об удалении patch cache. Поэтому при непустом delta код доходит до обновления основного cache, затем прерывается до публикации нового snapshot, обновления timestamp и сохранения cache; это статически подтверждаемая ошибка кода, а не runtime-проверка. Hook после `MessagesController.getUser()` патчит загруженный user из локального snapshot; отдельные hooks обрабатывают `getUserFull`, `getChat`, `getChatFull`. Локальные reply-color hooks для `MessageObject.getReplyColorId()` и `getReplyColor()` вычисляют цвет по UID автора цитируемого сообщения. Cache также содержит `chats`, и chat getters умеют применять такую запись, но сетевые handlers этого плагина не заполняют map; HTTP schema для chat profiles не установлена. При сетевом применении delta TL-доступ в callback передан через `run_on_ui_thread`; полный fetch из кнопки Settings, однако, вызывает blocking `_sync_database()` прямо из `on_click` и сам себя в worker не отправляет. Реальный UI-thread эффект следует проверять в клиенте; исходник показывает прямой вызов и синхронный `urlopen`.

## Практические техники и ограничения

1. При реализации совместимого сервера сначала зафиксировать контракт клиента из данного SHA: cookie `sync_access`, методы/пути, `profiles` response shapes, возможные поля времени и поведение 304. Затем получить или изучить фактический backend; клиентская догадка не отвечает на вопросы о схеме данных, валидации, удалениях, конфликте записей и авторизации.
2. Сетевой запрос держать в фоне, а изменение Java/TLRPC/UI состояния направлять на UI thread; для cache hot path использовать snapshot и ограничивать блокировку короткими операциями.
3. Для multi-account не сводить слот-конфигурацию в одну запись до сериализации: клиент формирует отдельный профиль и делает запрос на каждый активный account. Успех одного запроса не означает успех остальных.
4. `_clear_cache_action()` очищает `profiles`, но не `_chats_cache` и `_last_sync_timestamp`; затем `_apply_all_to_all_accounts()` повторно добавляет профили своих слотов в память. На старте пустой cache запускает full request с `force_clean=False`; при ненулевом старом timestamp он добавляет `If-Modified-Since`, поэтому серверный `304` может оставить остальных профилей не загруженными. Отдельная кнопка Settings запускает force-clean fetch, но напрямую вызывает blocking `_sync_database()` из callback; код не переводит этот сетевой вызов в фон.
5. Payload берёт `auth_key` из настройки, но в `create_settings()` нет поля для её ввода. При `ALLOW_CUSTOM_SERVER_CONFIG = False` также скрыты URL и cookie controls; способов штатно ввести эти значения этот plugin snapshot не показывает.

Ограничения и расхождения с радаром:

- Радар и README представляют репозиторий как self-hosted server; pinned tree не содержит серверного кода или инструкций развертывания. Это наиболее существенный пробел: факты о серверной стороне нельзя извлечь из этой записи.
- README заявляет поддержку AyuGram и exteraGram, тогда как единственный включённый `sync.plugin` записывает `client_type="AyuGram"`; наличие отдельного клиента для exteraGram в этом репозитории не подтверждается.
- Дельта с непустым ответом сломана на статически видимом пути: `_update_snapshot_partial()` обращается к отсутствующему `_patch_cache`; cached entries уже записаны, но новый snapshot/timestamp/write не выполняются. Пользовательская кнопка полного fetch напрямую вызывает blocking HTTP-функцию; потокобезопасность именно UI callback не runtime-проверялась.
- Очистка кэша не сбрасывает `_last_sync_timestamp` и сама не делает fetch. Startup затем запрашивает полный список условно с прежним timestamp, так что `304` может сохранить неполный кэш.
- `auth_key` читается при формировании payload, однако Settings UI не объявляет соответствующий ввод. Успешная настройка auth key вне показанного plugin-кода не установлена.
- `_chats_cache` имеет локальный read/write и TL patch path, но в просмотренных HTTP handlers нет его сетевого заполнения; наличие полей или маршрутов chat API нельзя выводить из cache shape.
- «Синхронизация в реальном времени» из README кодом конкретизирована как периодический опрос каждые 60 секунд плюс действия пользователя; push/WebSocket не обнаружены в изученном плагине.
- Тестов и серверной проверки в дереве нет. CI лишь проверяет, что два bundle-файла присутствуют; tagged release загружает их. Совместимость с сервером и обеими клиентскими платформами требует отдельной проверки.
- Авторский safety-файл предупреждает не обращаться из worker к `MessagesController`/`MessagesStorage`; в сетевых применениях дельты и multi-account code чтение/изменение `MessagesController` помещено в `run_on_ui_thread`. Это подтверждение структуры кода, но не device/runtime proof.
