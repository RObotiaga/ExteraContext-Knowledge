## Роль и границы доказательств

Amegram — полноразмерный Android-клиент на основе Telegram. Действующая поверхность расширений в этом snapshot — унаследованный Python/Chaquopy/Xposed runtime `app.exteraless.plugins`. Рядом с ним лежат MioHook для внутренних функций и экспериментальные WASM/Rust core/SDK файлы, но пользовательский `MiogramPluginsActivity` прямо помечает WASM manager как никогда не поставлявшийся; production engine construction/call path в проверенном дереве не найден. Это не самостоятельная библиотека ExteraGram SDK, и SDK из репозитория не следует автоматически считать совместимым с `.plugin`/`.eaf` форматом других клиентов.

Изучены точки, имеющие отношение к plugin API/runtime, WASM SDK, генерации и сборке плагинов, startup wiring hotpatch/anti-block, а также упомянутые радаром local AI. Большой Telegram-клиент целиком не просматривался. Код не запускался; runtime-проверки нет. Документационные обещания, исходный код и выводы об интеграции помечены раздельно.

## Фактические plugin-интерфейсы

### Унаследованный Python/Xposed runtime

В дереве остался `app.exteraless.plugins`: Java-модель `Plugin` наследуется от `com.exteragram.messenger.plugins.Plugin`, а Python SDK находится в `TMessagesProj/src/main/python`. Это наиболее конкретный исходный пример API расширения, но его надо сверять с ExteraGram/Exteraless, а не переносить как новый Amegram WASM API. В `ApplicationLoader` инициализируется `PluginsController`; Gradle подключает Aliuhook. Сборщик не проверял, как каждая функция из этой обвязки вызывается из UI клиента.

`BasePlugin` использует `on_plugin_load`, `on_plugin_unload`, `on_app_event`, `create_settings` и request/update hooks. Наличие метода hook-а ещё не регистрирует обработчик: для outgoing-message callback есть отдельный `add_on_send_message_hook(priority=0)`, для request hooks — `add_hook(name, match_substring=False, priority=0)`. `hook_method(method, handler=None, priority=50, filters=None, before=None, after=None, ...)` принимает reflection Method/Constructor либо `(class, name)`; при совпадении нескольких объявленных overload-ов он хукает все и возвращает список unhook id. Есть отдельные `hook_all_methods`, `hook_all_constructors` и `unhook_method`.

`hook_utils.find_class(name)` разрешает class aliases, затем спрашивает `guard_java_class`; отказ/ошибка поиска возвращает `None`. Но ошибка самого guard поглощается и продолжает поиск через `jclass`, так что это fail-soft helper, а не надёжная граница безопасности. Private-field helpers обходят superclass chain и ловят ошибки `setAccessible`; на новых Android hidden-API ограничения могут дать `None`/`False`.

Java `XposedHooks` лениво поднимает Aliuhook/LSPlant, сохраняет unhook handles по plugin id и снимает их через `unhookAllForPlugin`. В комментарии и коде есть fail-closed на повторном process death во время native-hook setup: persisted `PENDING` превращается в `BROKEN`, и native hooks выключаются для следующего запуска. Это надёжнее описывать как защиту конкретного bridge от повторных падений, а не гарантию стабильности любых reflection hooks.

### Внутренняя MioHook событийная шина

`MioHook` — отдельный Java event bus, не Xposed API и не Rust SDK. В исходнике объявлены points `MESSAGE_PRE_SEND`, `MESSAGE_RECEIVED`, `FEED_ITEM`, `AI_TEXT_RESULT`, `AI_TOOL_CALL`, `AUDIO_TRACK_CHANGED`, `PRESET_CHANGED`, `VAULT_FILE_EVENT`, `DIALOG_VISIBILITY`, `UI_CONTAINER`. `onPreSend` и `onFeedItem` могут запретить событие возвратом `false`; `AiText` позволяет последовательно переписать текст; `AiToolCall` может veto-нуть tool call; `UiContainerListener` получает уже созданный контейнер с тегом. В production есть dispatch call-site-ы из AI service/toolbox, Smart Feed, Vault, preset engine, Apple Music UI и уведомлений. Userbot регистрирует `onPreSend` listener, однако `dispatchPreSend` в проверенном дереве вызывается только из неиспользуемого `MiogramHookManager` facade method. Это внутренние Amegram вызовы: production binding от plugin runtime к MioHook не найден.

Регистрации имеют `owner`, `name`, `priority`, возвращают `Handle` с pause/resume/unregister; выше приоритет исполняется раньше, равный — по порядку регистрации. Вызов идёт синхронно в потоке вызывающей стороны, UI points требуют main thread. Исключение из одного listener не выходит наружу; после трёх failures запись отключается/quarantine, а `dumpStats()` выдаёт счётчики/время/ошибки по point. `MiogramHookManager` — compatibility facade: связывает прежние message/UI/audio интерфейсы с MioHook и умеет снимать handles. Это code-level API; инвентаризация всех его production dispatch call-site не входила в покрытие.

### Rust/WASM runtime

SDK задаёт guest exports `miogram_abi_version()`, `miogram_alloc(len)`, `miogram_guest_free(ptr,len)`, `miogram_call(ptr,len)`; один `Plugin::handle(&mut self, op: &str, payload: &[u8]) -> Result<Vec<u8>, i32>` экземпляр создаётся лениво `register!(Type)` перед первым вызовом. Все вызовы одного экземпляра сериализуются. Envelope v1 в коде имеет magic `MIOG`, little-endian header, UTF-8 op, implicit payload; op ограничен 128 байтами, весь frame — 4 MiB. Декодер проверяет magic/version/reserved bytes, длину и UTF-8.

`MiogramPluginEngine.install(manifestBytes, codeBytes)` сначала проверяет бинарный manifest, trust anchor, Ed25519, точный размер и SHA-256 кода, затем требует возрастающий `versionCode`; включение создаёт instance, а upgrade закрывает прежний. Manifest кодек ограничивает WASM distribution 64 MiB и фиксирует capabilities с возрастающими уникальными wire IDs. `OpPolicy` default-deny: известные операции — message events/history, send, HTTP fetch, private storage, notifications, render decorator; неизвестный op отсекается до guest call. На trap счётчик faults ведёт к quarantine по умолчанию после трёх с ручным `reEnable`; capability denial fault-ом не считается.

Контракт остаётся несогласованным, а не просто имеет разное имя: Rust SDK декодирует собственный `MIOG` frame; `docs/ARCHITECTURE.md` называет протокол `HYPR`; `host_api.fbs` задаёт FlatBuffers `CallRequest/CallResponse`; C JNI bridge при этом лишь копирует произвольный byte array в guest и обратно, без FlatBuffers parser/serializer. `WasmRuntime.kt` — общий byte-array интерфейс и сам не подтверждает FlatBuffers. Дополнительно `MiogramPluginEngine.dispatch(pluginId, op, payload)` использует `op` для capability lookup, но передаёт в guest только `payload`, не сериализуя `op`. Поэтому end-to-end host/guest контракт не установлен; подписанный manifest и unit tests на FakeWasmRuntime не доказывают работающий плагинный runtime.

Граница поставляемого продукта здесь существенна: по полному поиску по main/test source `MiogramPluginEngine` создаётся только в unit tests; production caller для `WamrWasmRuntime` не найден; `MiogramPluginsActivity.java` прямо говорит, что прежний WASM manager не был поставлен и текущий экран делегирует к Python `PluginsActivity`. Legacy `PluginsController` принимает файлы `.wasm`, показывает их как plugin и выставляет `loaded = true`, но его special-case не вызывает WAMR или `MiogramPluginEngine`; Forge передаёт собранный `.wasm` именно этому controller-у. Таким образом 64-MiB manifest, подпись и quarantine — свойства кода/тестируемой модели, но не подтверждённая поверхность исполняемого пользовательского WASM plugin.

Рантайм имеет дополнительные незакрытые ограничения: `WamrWasmRuntime.loadModule` принимает `SandboxConfig`, но native load не получает config; `consumedFuelMs()` всегда возвращает 0, а комментарии C отмечают отсутствие preemption/fuel/epoch. Манифестная подпись в core engine — конкретный код, но подключение WAMR зависит от submodule/build guard, а шифрование сохранённого кода отнесено к реализации `PluginRepository`. Нельзя трактовать все обещания sandbox/сверхбыстрого запуска из README как runtime-проверенные гарантии.

## Radar-релевантные интеграции

### Hotpatch

`ApplicationLoader.onCreate()` вызывает `AmegramPatchManager.init(context)`. Он на global queue ждёт 5 секунд, проверяет GitHub manifest не чаще раза в шесть часов; `checkForPatches(callback)` скачивает `hotfix/patches.json` по HTTPS с 8s connect/read timeout. `config`-patch записывает пары rules в SharedPreferences-backed active map; `bytecode`-patch скачивается во внутреннюю папку и открывается через `DexClassLoader`, затем рефлексивно вызывает `entrypoint.apply(Context)`.

Это code-confirmed механизм удалённой загрузки и исполнения DEX. Проверка подписей/хеша/доверенного ключа в `AmegramPatchManager` не обнаружена; `hotfix/patches.json` содержит `min_version`/`max_version`, но соответствующей проверки в менеджере нет. IDs применённых патчей сохраняются, правила повторно загружаются. `config` rules reader exposes only Boolean and String getters, поэтому другие JSON types в карте менеджера не имеют соответствующих typed accessor-ов. Использование механизма для безопасного plugin update требует отдельной supply-chain модели; сам факт DEX load не подтверждает безопасность.

### Anti-block engine

`MiogramAntiBlockEngine.start()` вызывается из `ApplicationLoader`, подписывается на connection changes всех аккаунтов и глобальные proxy-события; при зависшем прямом соединении делает deep check, а при зависшем proxy может ротировать сервер. Deep check асинхронен на global queue: сначала пробует TCP контрольные endpoints, затем четыре Telegram DC на 443, результат возвращает на UI thread. Код включает таймауты probes до 2.5/3s и decision rule по доступным DC. В README утверждаются локальные зонды/автоматический fallback, но конкретные утверждения о том, какие сети «не фильтруются», и успешность обхода требуют runtime/сетевой проверки.

`MiogramAntiBlockActivity` — UI для настроек/серверов; использует тот же singleton для ручной активации, custom server-ов и диагностики. Не следует смешивать её с `MioHook`: это внутренняя функция клиента, а не plugin callback, доступный внешнему автору.

### AI и build/debug

Радар и README отмечают LiteRT-LM и локальные generative models, но реализации LiteRT в просмотренном snapshot не найдено. В коде присутствуют два отличающихся Whisper/STT пути: `LocalSttEngine` с ONNX `SttBackend`/`OnnxWhisperTranscriber` контрактами и отдельный `AmegramLocalTranscriber`, который при существующей модели сразу запускает ONNX, иначе использует Android `SpeechRecognizer`; при ошибке предусмотрен Gemini fallback. Однако production wiring неполно: `MiogramAiRuntime` создаёт `LocalSttEngine`, но фабрика не вызывает `attachBackend`; `OnnxWhisperTranscriber` нигде в main source не создаётся, и поиск call-site для обоих transcriber-ов не нашёл. Поэтому эти классы/roadmap не доказывают работающую локальную STT функцию. В каталоге `LocalSttEngine` SHA-256 равен null, а `registerDownloadedFile` проверяет размер; отдельная `AmegramLocalTranscriber` смотрит на иной `files/models/whisper-tiny-int8.onnx` путь.

`MioForgeBuilder.probeAndBuild(projectDir, language, ...)` выполняется в фоне; для Rust вызывает `cargo build --release --target wasm32-unknown-unknown`, для Go — TinyGo, имеет timeout, потоковый лог и сообщает desktop-команду при отсутствующем toolchain. Код forge честно говорит, что на Android обычно нет Rust toolchain. `docs/BUILD.md` указывает JDK 21, Android SDK 37/build-tools 36.0.0, NDK и Python для Chaquopy; приводит `assembleDebug`, `assembleAfatRelease`, `testReleaseUnitTest` и проверку ELF `Align=0x4000`. Эти команды — документы, сборщик их не выполнял.

Forge UI также предлагает Python, Lua, Go и Rust. Python save/build path создаёт Python plugin и передаёт его active Python controller; Lua путь делегирует в userbot manager. Go/Rust build создаёт `plugin.wasm`, после чего `installBuiltWasmIntoCatalog` вызывает legacy `PluginsController.installPlugin(File)`. Тот копирует `.wasm` и создаёт catalog entry, а runtime special-case лишь помечает его загруженным без guest instantiation. Forge UI install success, следовательно, не подтверждает выполнение WASM; Lua engine/runtime также не подтверждён.

## Противоречия, ограничения и практические рецепты

* Не копировать Rust-пример из `docs/PLUGINS_DEV_GUIDE.md` без сверки: он импортирует `prelude::*`, `ops::ON_MESSAGE_SEND`, `PluginError` и использует `op: u32`, тогда как snapshot SDK экспортирует `Plugin::handle(op: &str, payload: &[u8]) -> Result<Vec<u8>, i32>`; кодовый пример SDK в `sdk/.../examples/echo.rs` совпадает с реальной сигнатурой.
* Не считать Python примеры plugin guide действующим API: guide использует `from miogram.plugins import Plugin`, `on_load`, `HookResult.modify/block/pass_through`, а исходная Python SDK — `base_plugin.BasePlugin`, `on_plugin_load` и строковые `HookStrategy` constants. Это расхождение docs/code.
* Не считать `.zip/.mioplugin` manifest из guide форматом signed WASM engine: внутренний manifest engine — свой бинарный `HYPE` codec, а Python `.plugin` pipeline — отдельная унаследованная реализация.
* Для расширения внутренней UI-функции изучать MioHook points, но отдельно доказать production dispatch path и внешний registration path; наличие interface/dispatcher не равняется опубликованному SDK.
* Для DEX hotpatch учитывать отсутствие подписи/хеша и версионного enforcement на стороне менеджера до любого повторного использования; в коде это удалённое исполнение кода из manifest URL.
* Не проектировать WASM plugin по одному из трёх несовпадающих протокольных артефактов (`MIOG`, `HYPR`, FlatBuffers): C bridge byte-copies только, `dispatch` теряет отдельный `op`, а engine не подключён к product UI.
* Не считать локальную LiteRT или Whisper/ONNX STT production-ready: LiteRT implementation не найдена, newer backend не подключается фабрикой, а legacy transcriber не имеет найденного call-site.

Источник не демонстрирует тесты на устройстве, фактическую сборку APK, benchmark холодного старта, успешность anti-block на конкретной сети или установленный production plugin distribution flow. Часть документов выглядит как roadmap/пример: отделяйте эти сведения от подтверждённых объявлений и вызовов в коде.
