## Роль источника

Это локальный Node.js **MCP-сервер** для автоматизации собственного Telegram user account через GramJS/MTProto, дополненный чтением архива AyuGram Desktop и Windows-утилитами питания/планирования процессов. MCP здесь — протокол для структурированного обмена запросами `tools/list` / `tools/call`; `@modelcontextprotocol/sdk` — серверная Node-библиотека, реализующая этот протокол. `telegram`/GramJS — отдельный Telegram MTProto client SDK, а не MCP-клиент. Проект не является ExteraGram/AyuGram Android plugin, SDK или plugin API. Его ценность для базы — примеры каталога внешних инструментов, Telegram-сценариев, локального архива и границ автоматизации. Совместимость с ExteraGram plugin API из него не следует.

README и сгенерированный `TOOLS.md` заявляют 200 инструментов: 146 read и 54 write. Changelog делит набор на Telegram (179), AyuGram archive (15) и Windows power (6); названия и нумерация в `TOOLS.md` согласуются с таким делением. Это статически зафиксированная документация, не runtime-проверка этого ingest.

## Архитектура и вызовы

`src/server.js` создаёт MCP `Server` с capability `tools`, обслуживает `tools/list` через `toolList()` и `tools/call` через `callTool()`, использует `StdioServerTransport`. Логи stdout перенаправлены в stderr, чтобы не засорять stdio-протокол; на SIGINT/SIGTERM и закрытии stdin вызывается `tg.client.disconnect()`. `src/tools.js` собирает доменные модули, смешивает их `methods` в `TgClient.prototype`, и регистрирует tools с JSON Schema и функцией `run`. `callTool` отправляет помеченные `mutating` вызовы через единственную очередь, read вызовы выполняет непосредственно; результат сериализуется в текст, bigint/GramJS TL/bytes преобразуются в JSON-представление.

## Извлечённые факты и техники

1. **Чат — строковая ссылка, а не только ID.** Каталог `TOOLS.md` определяет `chat` как `@username`, числовой ID, `+phone`, `t.me/...`, `me` или часть заголовка диалога. Для форума `replyTo` в чтении трактуется как ID корня темы; в отправке отдельное поле `topicId` превращается в `topMsgId`. При переносе подобной схемы полезно отделять публичный пользовательский идентификатор от внутреннего peer/entity и проверять разрешение перед вызовом.
2. **Историю и обычную страницу сообщений следует ограничивать отдельно.** `tg_read_messages` поддерживает offset/min/max ID, текстовый поиск в чате, отправителя, фильтр media и topic. `tg_load_history` имеет maxMessages (документация: default 5000), опционально пишет JSON на диск, а inline-ответ ограничивает последними 500 объектами. Наличие export не означает неограниченную выдачу в одном ответе.
3. **Telegram- и AyuGram-слои имеют разные источники истины.** `tg_*` работает через отдельную MTProto-сессию пользователя, а `ayu_*` читает локальную `ayudata.db`; разрешение имен может связать локальный архив с активной live-сессией. Данные об удалённых/отредактированных сообщениях не следует смешивать с историей, доступной Telegram API.
4. **Разделение read/write привязано к реестру инструмента.** Только вызовы с `mutating: true` проходят общую FIFO-очередь. Это прозрачный шаблон защиты массовых пользовательских действий, но он не классифицирует побочные эффекты в реализации автоматически; правильность зависит от флага каждого инструмента.
5. **Учётки изолируют сессии, но выбранная учётка глобальна для процесса.** `TG_ACCOUNT` может переопределить `activeUserId`; у записи учётки свой sessionFile или `session-<userId>.txt`. Это не модель параллельных независимых клиентов в одном вызове: API выбирает одну активную учётку.
6. **`tdata` можно импортировать двумя несовместимыми режимами.** Документация предлагает `qr` для новой независимой авторизации и предупреждает, что `shared` переиспользует desktop auth key и конфликтует при одновременной работе с Telegram Desktop/AyuGram. Также указано ограничение `opentele` для ключей `lskType` в Desktop 5.x/AyuGram 7.x; предложенный workaround — внешняя модификация upstream-пакета, поэтому это не следует считать поддерживаемым свойством MCP.
7. **Приватные данные требуют обращения как с credential-bearing state.** `config.json` хранит `api_id/api_hash`, а `session-<id>.txt` — полный вход в аккаунт. Документация запрещает показывать/выгружать/коммитить файлы и рекомендует отзыв сессии из другого клиента. `tg_sessions` только читает активные сессии; в коде заявлен запрет на завершение сессий.
8. **Windows power helper имеет отдельный lifecycle процесса.** `ayu_keep_responsive` запускает in-process interval, а `system_prevent_sleep` — detached/unref скрытый PowerShell-процесс. Код MCP не останавливает второй helper при завершении сервера; есть отдельный `system_allow_sleep`, но автоматическая очистка не подтверждена. Независимый `ayu-supervisor.ps1` также работает отдельным бесконечным циклом. Эти функции специфичны Windows, не portable plugin recipes.
9. **Декларация безопасных удалений расходится.** `README.md`/`SECURITY.md` утверждают, что destructive tools нет и `tg_delete_my_messages` удаляет только сообщения владельца; однако `TOOLS.md` также объявляет `tg_delete_messages(chat, ids, revoke=true)` как общий вызов удаления, а `src/tg.js` делегирует переданный список ID в GramJS `deleteMessages` без видимой здесь проверки владельца. Поэтому широкое утверждение «инструмент вообще не может удалить чужое сообщение» не подтверждено этим снимком; проверить фактические Telegram permission rules и runtime не пытались.
10. **Числа из README — документационный инвентарь, не аудит эффектов.** Статическая сверка имён нашла точное соответствие: 200 пунктов `TOOLS.md` и 200 уникальных core/domain registrations; каталог маркирует 146 read и 54 write. Генератор, self-test, CI и MCP server не запускались, поэтому count остаётся статическим. `TOOLS.md` печатает только `inputSchema.required`, поэтому полный контракт необязательных параметров нужно читать в `src/tools.js` и `src/tg-*.js`.
11. **Сопроводительная документация содержит несверенные контракты.** `README.md` и `AGENT-INSTALL.md` обещают автоматический backoff для `FLOOD_WAIT`, но статический код только форматирует серверную ошибку для сообщения и не ждёт/не повторяет запрос. `src/tg.js` также упоминает `tg_logout` как способ сбросить pending login, однако зарегистрированного инструмента с таким именем нет; включённый `test-ayu.mjs` вызывает его без защиты, и поэтому по статике прервётся на неизвестном tool до проверок AyuGram DB. `package-lock.json` всё ещё указывает root version `0.1.0`, license `MIT` и engines `>=22.5`, тогда как `package.json` — version `1.0.0`, `Apache-2.0`, `>=18`; lockfile metadata stale, хотя прямые зависимости совпадают.
12. **Маркетинговое описание live tests шире их фактических гарантий.** `CONTRIBUTING.md` говорит, что `test-*.mjs` пишут только в Saved Messages с marker и очищают за собой. Это справедливо не для всех сценариев: `test-mutating.mjs` трогает папки, список контактов, sticker installation, emoji status, drafts и все pinned messages в Saved Messages; оно не восстанавливает исходные status/draft/pins или прежнее состояние sticker set. Эти live-тесты не запускались; нельзя обещать полную обратимость их эффектов.

## Ограничения переноса и неразрешённые вопросы

- Это серверный Node.js/MCP userbot, использующий Telegram MTProto, а не Android plugin; его методы нельзя импортировать в Python/Dex-плагин ExteraGram.
- `tg_*` требует собственный `api_id/api_hash`, логин телефона/кода/2FA и локальную session. `ayu_*` архив требует Windows AyuGram и Node SQLite (README: Node 24+, либо Node 22.5+ с экспериментальным флагом); Telegram-only слой заявлен кроссплатформенным на Node >=18.
- Поддержка операций определяется Telegram API, правами аккаунта, наличием данных, локальной схемой DB и версией клиента; документация содержит caveats (например, участники крупных каналов — только admin, читатели доступны лишь при видимости).
- Метаданные радара (оценка пользы 10/10, перечень сценариев, дата создания) — вторичный контекст. Подтверждается первичным README/TOOLS.md по набору функций, но не рекомендация «портировать» и не ExteraGram API.
- `npm test`, live `test-*.mjs`, self-test, generator, CI, импорт сессии, AyuGram desktop проверки и Telegram calls не выполнялись. Статус `runtime-verified` отсутствует.
- Заявленные setup/поддерживаемые версии противоречат root metadata в lockfile, backoff и тестовой cleanup документации; см. findings 11–12 и review. Для переноса следует брать API только из конкретного сохранённого SHA и отдельно проверять runtime/права аккаунта.
