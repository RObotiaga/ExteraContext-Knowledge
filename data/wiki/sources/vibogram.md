# ViboGram: встроенная Python-система плагинов для iOS

Источник: [vibeDN/ViboGram](https://github.com/vibeDN/ViboGram), личный экспериментальный форк Swiftgram/Telegram-iOS с отдельной системой однофайловых Python-плагинов. Это не SDK ExteraGram/AyuGram и не подтверждение совместимости Android-плагинов. ## Роль и границы

Полезен как пример архитектуры iOS-хоста, который встраивает CPython, предоставляет небольшой API через объект `vibo`, передаёт плагину данные в JSON и сам готовит то, чего Python-среде не хватает (например, декодирование изображения). Переносимы общие приёмы разделения вычисления и платформенной подготовки данных; Swift API, UIKit, CPython embedding и детали Telegram-iOS специфичны для этого клиента. Сходство Python-языка не делает `.vibo` совместимым с BasePlugin, Chaquopy или `.marp`.

## Факты реализации

### Контракт файла и исполнения

Плагин — один текстовый Python-файл. Собственное расширение проекта `.vibo`; импорт также принимает `.plugin` и `.py`. Файлы лежат в `Documents/Plugins`, перечень фильтрует только эти расширения и сортирует имена лексикографически. Импорт копирует локальный файл; если целевое имя уже занято, реализация удаляет прежний файл и копирует новый. Поэтому подтверждение импорта/обновления — ответственность UI вызывающего кода, а безопасного журнала версий store не создаёт ([store](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPython/Sources/SGPythonRuntime.swift#L720-L768)).

`SGPythonRuntime.start()` использует `PyPreConfig_InitIsolatedConfig` и `PyConfig_InitIsolatedConfig`, явно задаёт пути поиска модулей в bundled stdlib, `lib-dynload` под устройство/симулятор и `app`, отключает запись `.pyc`, а интерпретатор после успешной инициализации не завершает. Повторный вызов после успеха возвращает `true`; неудачный путь оставляет `didStart == false`, поэтому повторная попытка может снова пройти pre-initialization, а безопасность такого сценария в снимке не подтверждена. Если `python.bundle` отсутствует, `start()` завершается с `false` и пишет причину в `lastError`. Это embedded CPython, а не Chaquopy и не Android runtime ([runtime](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPython/Sources/SGPythonRuntime.swift#L39-L175)). Smoke test существует как отдельный debug-row, но этот review не выполнял app build или запуск.

Публичный простой вызов `callFunction(scriptPath:functionName:argumentsJSON:)` сериализует аргументы во временный JSON-файл, через `PyRun_SimpleString` исполняет файл плагина и wrapper, затем читает ответ из JSON-файла. В этом простом методе ответ ожидается строкой. `callFunctionRich` тем же путём JSON-файлов поддерживает JSON-результат, очередь событий `vibo`, состояние и traceback исключения, возникшего внутри вызванной функции. Синтаксическая ошибка или исключение при исполнении верхнеуровневого кода файла происходят до wrapper `try/except`; в таких случаях rich call может вернуть `nil`, а UI ограничится общей ошибкой/логом консоли. Это обходной путь вокруг прямых вызовов низкоуровневого `PyObject` API; он синхронный и расходует временные файлы ([вызовы](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPython/Sources/SGPythonRuntime.swift#L187-L263), [rich call](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPython/Sources/SGPythonRuntime.swift#L310-L500), [UI error path](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPluginsUI/Sources/SGPluginsController.swift#L138-L186)).

Обычная функция верхнего уровня вызывается по имени, выбранному вызывающей стороной, с одним словарём аргументов. Документация задаёт границу JSON-совместимыми строками, числами, bool, `None`, списками и вложенными словарями. Результат может быть любым JSON-совместимым значением в rich-пути; при показе нестроковый результат форматируется как JSON ([контракт](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/docs/plugin-authoring.md#L20-L43), [преобразование результата](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPython/Sources/SGPythonRuntime.swift#L560-L577)).

### Hook и host API

Для исходящего текста документация требует первой строкой точный marker `# vibo-hook: on_send`; реализация также проверяет первую строку, но перед сравнением удаляет пробелы по её краям. Хост вызывает `transform({"text": текущий_текст})` для установленного файла; несколько плагинов идут в алфавитном порядке и каждый получает результат предыдущего. Неудача, отсутствие строкового результата или неизменённый текст пропускаются, отправка не отменяется. Call-site находится в `ChatControllerNode.sendCurrentMessage`; преобразования допускаются для plain text, общий plugin output пересоздаёт `NSAttributedString` с одним набором атрибутов, а mixed formatting заранее заставляет пропустить transforms ([runtime](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPython/Sources/SGPythonRuntime.swift#L580-L613), [call-site](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/submodules/TelegramUI/Sources/ChatControllerNode.swift#L5115-L5195)).

`.ascii` reply-to-photo — отдельная команда с асинхронной загрузкой изображения и прямым вызовом `ascii_art.vibo`: host подаёт Python `text`, `grid` и `invert`, затем заменяет composer-текст готовым ASCII-art для просмотра/отправки. Эту ветку не обслуживает generic on-send loop, потому что он не поставляет изображение. Anime-ify тоже имеет отдельный feature toggle и dedicated `callFunction` с options; установленный встроенный файл не получает generic hook marker. Эти два call-site показывают, что plugin не запускается автоматически просто от наличия файла: обработчик должен быть подключён конкретной функцией клиента ([`.ascii` reply](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/submodules/TelegramUI/Sources/ChatControllerNode.swift#L4874-L4919), [Anime-ify и hook loop](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/submodules/TelegramUI/Sources/ChatControllerNode.swift#L5115-L5194)).

`# vibo-hook: on_receive` запускает `on_receive({"text": ..., "peer_title": ...})` на входящем сообщении. Caller в `ApplicationContext` применяет тот же фильтр уведомления: реальное, не заглушённое сообщение, когда устройство не заблокировано. Возврат функции не переписывает сообщение. Одно специальное событие `vibo.delete_this_message()` может попросить caller локально скрыть это сообщение через `.forLocalPeer`; это не удаляет сообщение у собеседника и не блокирует его. В runtime возвращается только bool для этой операции; остальные UI-события из receive-hook не показываются ([runtime](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPython/Sources/SGPythonRuntime.swift#L615-L667), [call-site](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/submodules/TelegramUI/Sources/ApplicationContext.swift#L398-L415)).

Глобальный `vibo` — небольшой заявленный host API: уведомления `log`/`toast`/`alert`, системный share sheet, чтение/запись clipboard, haptic, открытие только `http`/`https` URL, короткий звук, настройки плагина, его `data_dir`, информация об устройстве, список установленных файлов и локальное скрытие текущего сообщения. Это не API объекта Telegram, аккаунта или сырых TL-запросов. Некоторые действия ставятся в очередь до завершения функции; clipboard/device-info/plugins/data-dir передаются как заранее вычисленные значения. Вызовы в текущем code path синхронны; явная модель потоков или таймаут плагина в изученных файлах не описана ([документация](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/docs/plugin-authoring.md#L80-L159), [host prelude](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPython/Sources/SGPythonRuntime.swift#L337-L448)).

`settings(args)` возвращает JSON-описание фиксированного набора строк: `header`, `text`, `switch`, `selector`, `action`, `input`. Settings UI вызывает `settings({})`; сохранённые значения можно читать через `vibo.get_setting`. `action` вызывает `on_action({"id": ...})`, затем экран повторно получает widgets и состояние. UI обнаруживает наличие `settings()` простым поиском подстроки `def settings(`, поэтому кнопка может появиться и у синтаксически некорректного/неподходящего файла ([гайд](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/docs/plugin-authoring.md#L207-L285), [реализация](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPluginsUI/Sources/SGPluginSettingsController.swift#L66-L163)).

Состояние одно на имя файла плагина: JSON в `Documents/Plugins/.state/<filename>.json`; файлы не попадают в список установленных плагинов. Для крупных локальных данных предоставляется каталог `Documents/Plugins/.data/<filename>/` ([реализация](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPython/Sources/SGPythonRuntime.swift#L772-L836)). В примерах можно читать/писать в `data_dir` обычным Python `open()`. Отдельной песочницы CPython в просмотренном коде не видно; наличие каталога данных само по себе не доказывает изоляцию от остальных доступных процессу ресурсов.

### Подготовка данных хостом

Для плагина, содержащего `# vibo-needs: image`, экран предлагает **Run on Photo…**. Хост декодирует изображение через UIKit/CoreGraphics, downsample-ит и передаёт `transform` числовую матрицу яркости, а не `UIImage`/bitmap/PIL image. `SGAsciiArtBridge` вычисляет BT.601 luminance 0–255, берёт aspect ratio, ограничивает ширину 16–120 колонками, высоту 200 рядами и старается уложиться в 3600 символов. Python выполняет рендеринг текста по этой матрице. В Git tree это расширяемый static marker: UI проверяет его поиском подстроки и без запуска Python добавляет photo action. Принцип — сложную платформенную операцию оставить в приложении, а пользовательское преобразование вести над простыми данными ([bridge](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPython/Sources/SGAsciiArtBridge.swift#L13-L116), [контракт UI](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPluginsUI/Sources/SGPluginsController.swift#L237-L315), [гайд](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/docs/plugin-authoring.md#L45-L77)).

### Импорт, ошибки и распространение

Plugins screen предоставляет импорт из Files, URL и **Plugin Store**; экран поддерживает запуск `transform`, передачу текста и удаление файла. Store читает публичный `https://api.github.com/repos/vibeDN/ViboGram/contents/plugins`, отображает принятые расширения и загружает выбранный `download_url`, после чего использует файловый импорт. Это простой каталог репозитория, без отдельного backend и без закрепления версий или схемы обновления ([store controller](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPluginsUI/Sources/SGPluginStoreController.swift#L14-L147), [загрузка и импорт](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPluginsUI/Sources/SGPluginStoreController.swift#L181-L234)).

Для ручного запуска UI показывает traceback исключений из вызванной функции. Если файл не разбирается или его top-level код падает до wrapper, rich-вызов может вернуть `nil`, и action sheet сообщает смотреть device console. Автоматический hook ошибку пропускает, чтобы она не блокировала обычное действие пользователя; для `on_send` это означает отсутствие результата/пользовательского уведомления из exception path. У Python-кода нет отдельного разрешения для каждого API: не импортируйте Android API как «почти совместимый» вариант — `java.*`, `android.*`, `org.telegram.*` и `com.exteragram.*` в iOS-хосте не существуют ([ограничения импорта](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/docs/plugin-authoring.md#L80-L96), [UI error path](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGPluginsUI/Sources/SGPluginsController.swift#L138-L186)).

## Практические приёмы

1. **Отделяйте вычисление от доступа к платформе.** Определите узкий JSON-контракт функции; если плагину нужна системная возможность (например, декодирование медиа), выполните её на стороне хоста и передайте только необходимую примитивную структуру.
2. **Делайте трансформ чистой функцией текста, если доступ к клиенту не нужен.** Встройте команду в первый-line `on_send` hook и сохраняйте цепочку композиции; ошибку пропускайте, чтобы сбой плагина не уничтожал исходное сообщение.
3. **Для простых опций используйте `settings()` и `vibo.get_setting()`**, а для больших файлов `vibo.data_dir()`. Учитывайте, что state зависит от filename: переименование файла создаёт другой ключ/каталог состояния.
4. **Портируйте идею и вычисление, а не ABI/API.** Android imports, BasePlugin hooks, доступ к Java-классам и модели объектов Telegram заменяются только теми параметрами и функциями, которые конкретный iOS-хост действительно передаёт.

## Противоречия и открытые пробелы

- `README.md` описывает систему как встроенную и работающую (`README.md:289-319`), а `docs/plugin-system-tier4.md` со статусом 2026-08-26 говорит, что реальная сборка ещё не проверена. Pinned BUILD-граф уже содержит зависимости `SGPluginsUI`/`SGPython`, app target явно включает Python resource bundles, а debug меню содержит Python Smoke Test. Комментарии `Telegram/BUILD:1995-2004` сообщают о прежней неудаче smoke test с `isBundled=false` при library `data` wiring и о переносе ресурсов в app target. Коммит не включает результат smoke test после переноса. Поэтому наличие актуальной wiring подтверждено source-кодом, успешная работа текущей конфигурации — нет ([app resources](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Telegram/BUILD#L1992-L2009), [debug row](https://github.com/vibeDN/ViboGram/blob/5f51b6befb2ce9370ea9acf40759d71053db2776/Swiftgram/SGDebugUI/Sources/SGDebugUI.swift#L85-L89)).
- `docs/plugin-authoring.md:296-299` всё ещё утверждает, что кроме `on_send` hooks нет, хотя выше в том же документе описан `on_receive` и текущий runtime/caller реализуют его. Ранние комментарии `SGPluginsController.swift:14-16,79`, `SGPython/BUILD` и `submodules/TelegramUI/BUILD:32-36` также говорят об отсутствии hook API или call-sites и расходятся с кодом в том же SHA. Эти comment/doc passages устарели; контракт определялся по сигнатурам и call-sites.
- `callFunctionRich` ловит исключение внутри вызванной функции и передаёт traceback в result, однако разбор/исполнение top-level кода плагина находится вне `try/except`. Для синтаксических ошибок и исключений при импорте rich call может вернуть `nil`, а UI показывает общую ошибку с рекомендацией смотреть device console; утверждение о доступном traceback сужено до вызовов функций.
- Реализация on-send сравнивает первую строку после `trimmingCharacters(in: .whitespaces)`: leading/trailing spaces принимаются, хотя authoring guide и примеры описывают буквально точную строку. Факт и описание различают заявленный формат docs и фактический matcher.
- `docs/plugin-system-tier4.md` описывает старые этапы и будущие designs, поэтому не является актуальной картой текущей интеграции. В этом review **не запускались Bazel, Xcode, чужие исходники, импорт, приложение, симулятор или устройство**. Комментарий о прошлом `isBundled=false` smoke test не подтверждает исправленный resource layout.
- Из дерева 36 750 entries сохранены и независимо сверены 23 целевых документа/исходника и BUILD-файла; остальной Telegram-iOS upstream и вложенные third-party/submodule реализации не читались. CPython xcframework, bundled stdlib/lib-dynload payload и все плагины/игровые сети не проверялись построчно. Приоритетные call-sites и выбранные пять `.vibo` examples изучены статически.
- Реальные OS sandbox/entitlements в готовом приложении, эксплуатационная изоляция отдельных Python-файлов, влияние медленного hook на UI/notification, thread-safety и конкурентный доступ к CPython не проверялись. `vibo.data_dir()` — отдельный каталог данных, это не доказательство sandbox boundary.
- В доке tier-4 есть отдельный раздел с эскизом **будущего** дизайна, портированного концептуально с ExteraGram API (`docs/plugin-system-tier4.md:397-471`). Примеры `BasePlugin`, `HookResult`, `pre_request_hook`, raw TL requests и `client_utils` из этого раздела не являются API ViboGram.

### Связь с радаром

Радар верно выделил узкий JSON-контракт, переносимость чистого Python, platform-prepared image data и отсутствие Android internals на iOS (`raw/vibogram/radar-context.md`, строки 25–36). Его раннее утверждение об отсутствии hooks устарело: pinned commit содержит marker-based on-send, отдельный incoming-message on_receive и ещё feature-specific plugin call-sites. Радар рассматривал ViboGram как архитектурную аналогию; сам ViboGram не демонстрирует API ExteraGram/AyuGram.

Проверено **31 уникальное факт-запись** в `work/vibogram-facts.json`; внутренние дубли не найдены. Повторяющиеся приёмы (JSON plugin contract, hook dispatch, host-assisted media, settings/state) допустимы как отдельный provenance и в дальнейшем объединяются через `requests`, `hooks`, `media`, `ui`, `storage` и `portability`; build/debug/security сведения остаются привязанными к этому iOS fork.
