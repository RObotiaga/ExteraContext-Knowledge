## Роль и границы источника

Это один Python-плагин exteraGram, `CustomNFTPlugin(BasePlugin)`, который читает каталог Telegram Stars, собирает UI-конструктор моделей/узоров/фонов, строит локальный объект `TL_starGiftUnique`/`TL_savedStarGift` и подмешивает сохранённые объекты в локальный ответ списка подарков профиля и в живой кэш клиента. Это пример интеграции конкретного Android-клиента через Chaquopy, Java-классы Telegram и reflection; он не описывает публичный стабильный SDK и не подтверждает совместимость этих приватных точек на произвольной сборке.

Надпись «NFT» здесь не означает выпуск подарка или изменение сервера. В коде нет запроса создания подарка: выбранные атрибуты сериализуются в настройку плагина, затем добавляются в ответ/кэш на устройстве. README прямо говорит, что такой подарок видит только локальный клиент и его нет на серверах Telegram. Это локальная визуальная подмена, а не переносимый NFT или объект, который увидят другие пользователи.

## Практические приёмы, подтверждённые в коде

1. **Делайте optional imports по отдельности, если целитесь в урезанные SDK.** Здесь каждый тип `ui.settings` импортируется в собственном `try/except`; `_ui` удаляет поддерживаемые как необязательные параметры при ошибке конструктора, а `Input`/`Switch` получают fallback через диалог/кликабельный ряд. Это снижает число ошибок импорта, но не доказывает поддержку UI API на неизвестной версии.
2. **Различайте Java TL-атрибут и пользовательский option dict.** Плагин проводит custom `dict` через общие рендер/selection методы, сохраняет ему `custom`/`id`, а для нативной сетки создаёт TL-клон от реального donor attribute. Такой адаптер требует реального donor того же kind и проверки семантики приватных полей.
3. **При reflection читайте приватное поле через иерархию классов.** `_jfield`/`_jset` сначала пробуют Python-доступ, затем `getDeclaredField` и superclass chain. Код многократно глотает исключения ради fallback, поэтому неуспех может выглядеть как отсутствие данных; добавляйте диагностические сообщения и сверяйте имена с конкретной сборкой.
4. **Сохраняйте стабильный ключ выбора отдельно от display name.** TL-опции записывают id, name и rarity; восстановление сперва сравнивает id, затем имя. Для фоновых цветов есть дополнительный fallback на сериализованный dict, чтобы выбор переживал изменение каталога атрибутов.
5. **Используйте документ, а не только картинку, когда атрибут должен попасть в TL gift.** Стикер/emoji pattern хранится как `doc_id`, разрешается в настоящий Telegram document и добавляется в clone pattern TL-attribute. Фото с диска рисуется в UI, но `_pattern_attr` возвращает `None`, если документ отсутствует.
6. **Для локального profile augmentation учитывайте и загрузку, и уже открытый экран.** В этом исходнике отдельны response hook и mutation live cache плюс уведомление; также есть удаление из settings/cache/live list. Это техника для локального UI-state, не серверное сохранение.
7. **Храните приватные hooks в явных списках и снимайте на unload.** Плагин сохраняет refs от `hook_method` и удаляет их в `on_plugin_unload`. Метод `add_hook` saved-gifts отдельно устанавливается базовой схемой и в этом файле явного `unhook` нет.
8. **Тесты с Java stubs полезны только для чистой логики и формата compatibility.** В репозитории есть три набора заглушек для state, response/cache injection и урезанных imports, но `run_tests.sh` также запускает Python и не был выполнен при ingest; такие тесты не валидируют клиентскую reflection-совместимость.

## Ограничения, противоречия и пробелы

- **Клиентская совместимость не доказана.** Код использует `ResaleGiftsFragment`, `StarGiftPreviewSheet`, `StarGiftSheet`, `StarsController`, `MediaDataController`, `LaunchActivity`, имена полей и TL-конструкторы через Java/reflection. Все это может меняться. Авторский handoff отдельно называет проверенными только stub fallback для нативного каталога и image-result path и просит подтвердить их на устройстве (`CLAUDE.md:202-218`). Никакой Android build/client runtime в этой работе не проверялся; `runtime-verified` нет.
- **SDK compatibility — только заявленная цель.** Код декларирует app `>=12.5.1`, SDK `>=1.4.3.3`; README повторяет Python 3.11/Chaquopy v16. В `EXTERAGRAM_SDK_REFERENCE.md` описан SDK 1.4.3.10 и приложение `>=12.8.1`, а старый `plugins/README_custom_nft.md` также говорит app `>=12.8.1` и имеет заголовок v1.2. Это не согласованное и не независимо проверенное требование; для текущего кода каноничными являются только его буквальные metadata fields.
- **Заявление об отсутствии мутации donor не гарантировано кодом.** `_clone_attr` пытается `newInstance()` и копирует поля, но при неудаче выбирает `target = attr`. Вызывающий код далее может менять имя/цвета/документ у такого объекта. Документация проекта утверждает, что живой объект не мутируется, а реализации оставляет fallback на исходный объект; без runtime и проверки результата reflection это остаточный риск.
- **Определение своего/чужого запроса хранится в одном поле экземпляра.** `pre_request_hook` записывает `_last_request_self`, `account` игнорируется, а `post_request_hook` использует это поле позже. Если несколько аккаунтных/параллельных запросов пересекутся, контекст может быть перезаписан. Это статический вывод из структуры кода, не доказанный runtime-сценарий.
- **Reflection-fallback для списков профиля эвристический.** Если у response или `GiftsList` нет доступного ожидаемого поля `gifts`, код берёт первый найденный `ArrayList`, не проверяя его тип/содержимое. `_inject_live` также вставляет объект во все найденные списки `GiftsList` без дедупликации, поэтому повторное добавление или несколько подходящих кэшей могут дать повторы; поведение зависит от внутренних полей конкретной клиентской сборки.
- **`only_self` — локальный фильтр UI, не настройка видимости серверного профиля.** Когда настройка выключена, подмена применяется и к ответам чужого профиля на этом устройстве. Она не создаёт общедоступную запись.
- **Некоторые path зависят от singleton выбранного аккаунта.** Каталог, sticker packs, уведомления и `_my_uid()` используют `UserConfig.selectedAccount`; единообразная работа при переключении аккаунтов/фоновой загрузке не подтверждена. `_fetch_attrs` берёт connection manager отдельно, а собственные `account` параметры request hooks не сохраняет.
- **Своё фото и sticker pattern имеют разные возможности.** Фото импортируется как путь в приватной папке и отображается собственным renderer-ом. В профиль оно не сериализуется в TL pattern, и в native constructor не вставляется. Авторская документация это поясняет; кодовая причина — `_pattern_attr` требует document.
- **Тестовые числа остаются утверждением документации.** README и CLAUDE.md перечисляют 70 + 11 + 13 offline checks; сами тест-файлы показывают stubbed cases, а `run_tests.sh` запускает их и `py_compile`. Здесь ничего не запускалось, поэтому «зелёные» результаты не подтверждены.
- **Покрытие ограничено репозиторием и выборочными code paths.** Нет исходника заявленного `eblanNFT`, официального SDK checkout, устройства, реальных серверных ответов или клиентских сборок. Большую часть renderer/preview/editor UI не прослеживали построчно; выводы об этих областях ограничены README и авторским handoff. `radar-urls.json` пуст; зафиксированный SHA является существующим старым commit из July project history, а не новостью о новой сентябрьской функции. Радарный контекст сам отмечает, что проект повторно индексировался и новый commit после прежнего анализа в сентябре не заявлялся.
