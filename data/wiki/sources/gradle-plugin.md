# exteraStuff/gradle-plugin

Источник: [репозиторий exteraStuff/gradle-plugin](https://github.com/exteraStuff/gradle-plugin), снимок зафиксирован на `290bb3bc34e8cc8e8126a880a464a77bfa572d80` (ветка `master`, snapshot date 2026-09-27). Лицензия в снимке — MIT. Это Gradle-инструмент для превращения Android library-модуля с Kotlin/Java-кодом в DEX и, при включённом `bundle`, в JAR-пакет ExteraGram с metadata, optional service jars и optional подписью.

Уровень доказательств: поведение пайплайна, DSL-реализация и задачи ниже исследованы по исходному коду; инструкции настройки и описания свойств README помечены как docs, а не как проверка на клиенте. Клиент ExteraGram/AyuGram на устройстве не запускался, созданный `.jar` не устанавливался. Сборка этого инструмента и пользовательского проекта не запускалась. README сообщает проверку Gradle 9.7.1 и AGP 9.x, это заявление документации.

## Установка и границы проекта

В снимке Gradle-плагин не опубликован как обычная зависимость. README предлагает клонировать репозиторий и подключить его как composite build через `pluginManagement { includeBuild(...) }`, а затем применить `id("io.github.exterastuff.plugin")` рядом с `com.android.library` ([README, строки 16–48](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/README.md#L16-L48)). Плагин в коде создаёт расширение `extera` сразу, но конфигурацию и задачи включает через `pluginManager.withPlugin("com.android.library")`; следовательно, без AGP library plugin задачи не появляются ([ExteraPlugin.kt, строки 54–64](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/ExteraPlugin.kt#L54-L64)).

Нужны JDK 21, Android SDK и пользовательский `Telegram.jar`, полученный `dex2jar`, согласно README. Toolchain самого репозитория также закреплён на Java 21; Kotlin Gradle plugin — 2.2.0, Gradle wrapper/docs указывают 9.2.1, AGP — 9.x, R8 — 9.4.17. В `build.gradle.kts` API AGP и R8 объявлены `compileOnly`, тогда как Shadow 9.6.1 и ASM 9.8 являются implementation dependencies ([build.gradle.kts, строки 1–24](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/build.gradle.kts#L1-L24)).

## Реальный build pipeline

Внутри каждого Android variant плагин строит Shadow fat JAR из результата `compile<Variant>Kotlin`, `compile<Variant>JavaWithJavac` и runtime classpath. Затем Shadow переносит пакеты из `relocate(...)` под `targetPackage`, исключая заданные relocation patterns. Для совпадающих `META-INF/*.kotlin_module` и `META-INF/services/**` выставлен `DuplicatesStrategy.INCLUDE`, а service-файлы сливаются ([ExteraPlugin.kt, строки 129–179](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/ExteraPlugin.kt#L129-L179)).

Перед этим `processTelegramJar` берёт `telegram.jar`, делает ASM-проход по class-файлам и пишет нормализованный `Telegram.stripped.jar`. Этим результатом пополняется `compileOnly`; он не включается в fat JAR плагина. Обработка сначала строит map `class name → access flags`, затем для каждого class-файла определяет вложенные типы из class/superclass/interfaces, field/method descriptors и generic signatures, а также exceptions. Недостающие `InnerClasses` entries добавляются по map; если родительский класс не найден, берётся fallback public+static. Необычные бинарные имена без простого имени или начинающиеся с цифры получают `outerName=null` и `innerName=null`. Код не ремонтирует произвольные ошибки `dex2jar`, а именно восстанавливает `InnerClasses` metadata, нужную компилятору ([ProcessTelegramJarTask.kt, строки 130–230](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/tasks/ProcessTelegramJarTask.kt#L130-L230)).

Исключения из клиентского classpath состоят из жёстких префиксов `java/` и `com/android/tools/r8/` плюс `telegram.conflictingPackages`, чьи точки переводятся в слеши. DSL default для пользовательского списка: `kotlin/`, `kotlinx/coroutines/`, `com/android/tools/r8/`; фильтр использует `startsWith`, поэтому это префиксы ZIP entry, а не glob-паттерны. Обратите внимание, `java/` и R8 всегда удаляются даже при перенастройке DSL ([TelegramExtension.kt, строки 6–33](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/extensions/TelegramExtension.kt#L6-L33), [ProcessTelegramJarTask.kt, строки 38–40 и 98–110](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/tasks/ProcessTelegramJarTask.kt#L38-L40)). Если `Telegram.jar` отсутствует или не файл, задача завершается с указанием запустить `dex2jar` на Telegram APK ([там же, строки 87–94](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/tasks/ProcessTelegramJarTask.kt#L87-L94)).

R8 получает fat JAR как program input; очищенный `Telegram.jar` и compile classpath без runtime dependencies формируют R8 classpath, а Android boot classpath приходит из SDK. `minSdk` берётся из `extera.r8.minSdk`, иначе из variant `android.minSdk`. На classpath перед запуском R8 сливаются только `.class`; дублирующиеся entry отбрасываются по первому встретившемуся имени. Код всегда задаёт `-ignorewarnings` для unresolved-ссылок в Telegram jar и `-dontwarn <relocated package>.**` для каждого перемещённого исходного пакета ([ExteraPlugin.kt, строки 181–209](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/ExteraPlugin.kt#L181-L209), [R8WorkAction.kt, строки 70–92 и 95–119](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/actions/R8WorkAction.kt#L70-L119)). Это значит, что пользовательские ProGuard rules дополняются автоматическими подавлениями; успешная сборка сама по себе не доказывает, что все host API ссылки разрешились корректно.

Release variant запускает R8 в `CompilationMode.RELEASE`; остальные варианты идут как DEBUG, что сохраняет более читаемые stack trace и отключает часть оптимизаций по заявлению README. Выход R8 — indexed DEX каталог под `build/outputs/dex/<variant>/`. Самостоятельная команда `buildDex` агрегирует DEX-задачи всех variants ([BuildDexTask.kt, строки 22–77](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/tasks/BuildDexTask.kt#L22-L77), [R8WorkAction.kt, строки 72–92](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/actions/R8WorkAction.kt#L72-L92)).

### Relocation и compile-only зависимости

`extera.shadow.targetPackage` — обязательный parent package, под который переносит классы Shadow. Реальный call-site строит destination как `"$targetPackage.$sourcePackage."`; source package очищается от конечной точки. Например `relocate("org.example.lib")` плюс target `dev.plugin.shaded` ведёт к `dev.plugin.shaded.org.example.lib`. Имеются два объявления: `relocate(vararg packages: String)` без настроек на каждую группу и `relocate(pkg: String, Action<RelocationSpec>)`, где доступны `exclude(vararg patterns)`. Они на самом деле реализованы, а не только нарисованы в README ([ShadowExtension.kt, строки 9–41](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/extensions/ShadowExtension.kt#L9-L41), [ExteraPlugin.kt, строки 170–178](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/ExteraPlugin.kt#L170-L178)).

Практически `compileOnly` подходит для классов, предоставляемых клиентом: они доступны компиляции/R8 как classpath, но не попадают в Shadow runtime JAR. Это важно для host-owned AndroidX и Telegram classes: relocation может изменить символические имена так, что ожидаемые runtime classes пропадут. README предлагает явно исключать host-provided packages из relocation ([README, строки 58–69, 111–119 и 298–314](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/README.md#L58-L69)).

## Bundle, manifest и plugin metadata

Блок `extera { bundle { ... } }` включает упаковку. Без него aggregate и variant `packagePluginJar*` задачи не регистрируются; без настройки signing-variant не регистрируются `signPluginJar*`. Сам DEX build доступен отдельно, без bundle ([ExteraPlugin.kt, строки 103–127 и 213–315](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/ExteraPlugin.kt#L103-L127)). JAR содержит `classes.dex`/`classesN.dex` из output directory и `services/*.jar`, если услуги объявлены. `Plugin-Id`, Name, Description, Icon, Author, Version, Minimum Client Version, Entry Class, Update Sources, Dependencies, Provided Services, Required Services записываются как атрибуты manifest ([ExteraPlugin.kt, строки 248–307](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/ExteraPlugin.kt#L248-L307)).

Файл `id-version.jar` для release; debug имеет classifier variant, то есть `<id>-<version>-debug.jar`. Путь по умолчанию `build/outputs/jar/`. Archive сохраняет file timestamps, но использует reproducible file order. Manifest extension в коде имеет `Property<String>` для `id`, `name`, `description`, `icon`, `author`, `version`, `minClientVersion`, `entryClass`; `updateSources` — MapProperty, dependencies — internal ListProperty, доступный через `dependency(id) {}`. Для строковых полей нет конвенций/значений по умолчанию: package task вызывает `.get()` для каждого, включая icon. Значит, `id`, `name`, `description`, `icon`, `author`, `version`, `minClientVersion`, `entryClass` необходимо задать перед packaging, несмотря на некоторые поля как «optional» во вводном DSL примере. У `updateSources` есть пустое значение при незадании благодаря property convention Gradle/объявленному empty в README; в реализации специальная convention не задаётся явно, поэтому перед использованием полагаться на пустое значение не следует без проверки Gradle managed-property behavior ([ManifestExtension.kt, строки 34–75](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/extensions/bundle/ManifestExtension.kt#L34-L75), [ExteraPlugin.kt, строки 266–284](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/ExteraPlugin.kt#L266-L284)).

Иконка реализована лишь как строковое поле `icon`, записанное в `Plugin-Icon`; проверка синтаксиса вроде `pack/name` или наличие ресурса отсутствуют в этом Gradle-коде. `entryClass` аналогично идёт в `Plugin-Class`, но плагин не проверяет, что класс существует или реализует контракт runtime. Список permissions в extension/task/manifest отсутствует, несмотря на возможную пользу permissions в других типах ExteraGram-плагинов.

`dependency("streaks")` добавляет plugin dependency declaration: обязателен `minVersion`, принимается только regex `major.minor.patch`; минимальная версия и provider sources/SHA записываются как provider-specific manifest attrs, а общий список сортируется и сериализуется по `id:version`. Отдельный major bump считается incompatible по комментариям кода и docs, сам Gradle tool эту совместимость не вычисляет. Рекомендуется указывать immutable provider URL для конкретной версии и SHA-1 по примеру README; README отдельно предупреждает, что `latest` меняет hash ([ManifestExtension.kt, строки 10–32 и 69–75](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/extensions/bundle/ManifestExtension.kt#L10-L32), [ExteraPlugin.kt, строки 484–507](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/ExteraPlugin.kt#L484-L507), [README, строки 149–168](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/README.md#L149-L168)).

## `providedService` и `requiredService`

`providedService` и `requiredService` — Gradle dependency scope configurations, добавленные в `compileOnly`; транзитивные зависимости для module dependencies отключаются, потому что service трактуется как самодостаточный artifact. `providedService` артефакт отдельно проходит D8 и встраивается в `services/<group>.<artifact>-<version>.jar`. Вложенный jar сохраняет ресурсы исходного artifact, заменяет JVM `.class` байткод на `classes.dex`/другие indexed DEX и получает `Service-Id`/`Service-Version` в своём manifest. Имя/координаты должны разрешиться как Maven coordinates; project dependency записывается по фактическим `group:name:version`, а не как project path ([ExteraPlugin.kt, строки 371–481](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/ExteraPlugin.kt#L371-L481), [D8WorkAction.kt, строки 68–141](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/actions/D8WorkAction.kt#L68-L141)).

`requiredService` только добавляет зависимость к compile classpath и manifest `Plugin-Required-Services`; он не D8-ится и не упаковывается. Сервисные классы не relocate-ятся: consumer должен ссылаться на те же имена классов, которыми service API был скомпилирован. Manifest списки сериализуются в стабильном сортированном порядке; один `providedService` jar строится на координату, D8 выполняется worker-ом с изолированным R8 classloader ([README, строки 199–259](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/README.md#L199-L259), [DexProvidedServicesTask.kt, строки 64–99](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/tasks/DexProvidedServicesTask.kt#L64-L99)).

## Подпись, build variants и публикация

Для подписи существует `bundle.signing.debug {}` и `bundle.signing.release {}`. Код создаёт signing task только для каждого variant, чей конфигурационный block был вызван; пустой блок тоже включает регистрацию, но потребует заполнить keystore fields. Для release default TSA URLs: DigiCert, Sectigo и `rfc3161.ai.moda`; debug default empty, значит JAR подписывается без timestamp. Если задали список TSA, но каждый endpoint недоступен, task завершается ошибкой. Private key alias должен соответствовать `PrivateKeyEntry`, иначе будет GradleException. Подпись использует SHA-256 digest и `SHA256withRSA`, signerName `EXTERA`. Key passwords помечены как `@Internal`; их нельзя публиковать/хранить в репозитории, и сам task выключен из build cache, потому что подпись/TSA недетерминированы и пароль не входит в cache key ([SigningExtension.kt, строки 8–39](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/extensions/bundle/SigningExtension.kt#L8-L39), [SignJarTask.kt, строки 19–80](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/tasks/SignJarTask.kt#L19-L80)).

`buildDexDebug` / `buildDexRelease` пишут debug/release DEX; `buildDex` агрегирует variants. При наличии bundle доступны `packagePluginJarDebug/Release` и агрегат `packagePluginJar`; signing-задачи строятся лишь при соответствующем signing DSL и выводят суффикс `-signed.jar`. Это имена Gradle tasks внутри consuming Android library, а не Gradle tasks публикации исходника на Portal. Корневой build включает `com.gradle.plugin-publish` plugin, но README явно утверждает, что plugin нигде не опубликован; в снимке отсутствуют release/workflow/tests. CI и Gradle Portal публикация не подтверждены. Веб/manifest payload DevServer reload здесь не реализуется: tool лишь создаёт output JAR. Доставка, обнаружение файла dev server и live reload принадлежат внешним инструментам/шаблонам и данным источником не подтверждаются.

README называет Configuration Cache и parallel execution поддержанными, но это только заявление документации: тестов в репозитории нет. В таблице README сказано, что `buildDex*` использует только up-to-date checks; этому противоречит код `BuildDexTask`, помеченный `@CacheableTask`. `packagePluginJar*`/`signPluginJar*` в README также описаны как up-to-date-only; signing task действительно отключён от build cache, а packaging зарегистрирован как Gradle `Jar` task. Реальное поведение этих задач с build cache и configuration cache в потребительском проекте не проверялось ([README, строки 288–296](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/README.md#L288-L296), [BuildDexTask.kt, строки 20–24](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/tasks/BuildDexTask.kt#L20-L24), [ExteraPlugin.kt, строки 248–259](https://github.com/exteraStuff/gradle-plugin/blob/290bb3bc34e8cc8e8126a880a464a77bfa572d80/src/main/kotlin/io/github/exterastuff/plugin/ExteraPlugin.kt#L248-L259)).

## DSL: объявлено в README и реализовано в коде

| Объявление | Состояние в снимке |
|---|---|
| `telegram { jar; conflictingPackages }` | Объявлено и реализовано; default package prefixes заданы в extension. |
| `shadow { targetPackage; relocate(...) { exclude(...) } }` | Оба overload `relocate` и exclude реализованы. `targetPackage` в коде не имеет default, используется при конфигурации variant Shadow task. |
| `r8 { proguardFiles; version; minSdk }` | Все properties реализованы. `version` defaults на `9.4.17`; `minSdk` явной convention не имеет и fallback на Android variant. |
| `bundle { manifest { id/name/...; dependency(...) }; signing { debug/release } }` | Реализовано. Каждый manifest String property реально требуется packaging call-site; README table показывает «—», не гарантирует дефолт. |
| `updateSources` | Реализовано как `MapProperty<String,String>` и сериализуется как `name=url`, записи упорядочиваются по ключу. |
| `providedService(project(...))`, `requiredService("group:artifact:version")` | Реализовано через конфигурации `providedService`/`requiredService`, compileOnly scopes, variant resolver и манифест. |
| `packagePluginJar*`, `signPluginJar*` | Реальные Gradle tasks, но условно регистрируются, см. раздел об условиях. |
| `publishPlugin`, `reloadPlugin`, `DevServer` payload, permission DSL | Не найдены в коде/README этого source. Не следует выдумывать эти API на основании соседнего template, SDK или радара. |

Важное различие между документацией и поведением: intro README говорит, что `bundle` metadata включает минимальные поля и описывает bundle block как optional; код packaging записывает все 8 ключевых string metadata attrs без пропусков и не задаёт их defaults. Также `bundle` означает регистрацию package tasks при любом вызове блока; подпись зависит от отдельного вызова debug/release блока. `id`, `icon`, `entryClass` и остальные значения не валидируются по правилам runtime-клиента, только передаются в manifest.

## Практические рецепты

### Подключить tool к plugin module

1. В `settings.gradle.kts` клиента использовать `pluginManagement { includeBuild("<path-to-gradle-plugin>") }`.
2. В plugin module применить оба id: `com.android.library` и `io.github.exterastuff.plugin`.
3. Получить `Telegram.jar` из нужного APK своим `dex2jar` процессом и задать `extera.telegram.jar`; не переиспользовать jar другой версии клиента без проверки совместимости.
4. Указать `shadow.targetPackage`; объявить только runtime-зависимости для shading; host classes держать как `compileOnly` и при необходимости исключать соответствующие под-пакеты из relocation.
5. Сверить `r8.minSdk` с Android `minSdk`, и включить ProGuard keep правила для reflection/entry points, если они нужны плагину.

Это рецепт, выведенный из README и wiring кода; здесь он не был выполнен на реальном Gradle-проекте.

### Собрать unsigned или signed plugin JAR

Для JAR задать все manifest fields: `id`, `name`, `description`, `icon`, `author`, `version`, `minClientVersion`, `entryClass`. Затем вызвать `packagePluginJarRelease` или `packagePluginJarDebug`. Для подписи настроить нужный variant `keyStore.path`, `alias`, `storePassword`; `keyPassword` опционален и при отсутствии берётся из store password. Передать секреты из environment variable/provider. Запускать соответствующий `signPluginJarRelease` или `signPluginJarDebug`; release имеет TSA fallback-список, debug без timestamp по умолчанию.

### Предоставить API другому plugin

Вынести service API в отдельный self-contained artifact, добавить зависимость `providedService(project(":api"))`, чтобы API компилировался с plugin, но классы service не попали в основной dex. Для consumer записать `requiredService("group:api:version")`. Не relocate service API package. Проверить координаты и согласовать version/build compatibility отдельно: данный plugin упаковывает/декларирует contract, но не валидирует реальный client service loader.

## Противоречия с радаром и ограничения

Радар описывал stage September 6 pipeline и называл инструмент неопубликованным composite build. Это подтверждается README snapshot для composite-build onboarding, но зафиксированный код уже содержит развитые bundle metadata, icon, dependency declarations, provided/required services и signing; нельзя ограничивать знания первой версией из дня объявления. Claim радара Kotlin→fat JAR→relocation→R8→DEX верен с уточнением: `Telegram.jar` preprocessing идёт для compile/R8 classpath, а plugin JAR packaging — опциональный последующий этап; provided service artifacts независимо проходят D8.

Claims о Telegram.jar `InnerClasses` repair и compile-classpath exclusions подтверждаются `ProcessTelegramJarTask`, но `InnerClasses` repair не переписывает сам Telegram bytecode/поведение и не доказывает совместимость с произвольной версией клиента. `classes.dex` результат не эквивалентен проверенному/подписанному клиентом plugin. README и build metadata подтверждают инструментальную сборку, а не runtime проверку.

README указывает icon как текстовое plugin emoji icon, implementation только копирует строку в manifest. Нет подтверждённой проверки icon encoding. Нет permission manifest/model/API. Нет исходников самого plugin template и `dev_watch.py`, следовательно, DevServer hot reload, payload format, installation protocol и watcher lifecycle остаются за границей этой страницы. В snapshot отсутствуют tests и CI workflows; никакие CI status claims здесь не делаются.
