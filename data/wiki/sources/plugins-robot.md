## Практический контур приёма плагина

Для обычного `.plugin` бот парсит Python AST и извлекает только присваивания известных magic-полей в верхнем уровне модуля. Значения должны быть литералами; submitted Python не импортируется и не исполняется. Обязательны непустые `__id__`, `__name__`, `__author__`, `__version__`; кроме них нужно указать строковый `__min_version__` или `__app_version__`. BOM отвергается. Это серверная проверка формата заявки, не проверка совместимости или безопасности кода плагина.

Обычная новая plugin-заявка проходит quiz до загрузки файла: в коде задано три вопроса за прогон; неправильный ответ начинает quiz заново. Это gate потока подачи, а не проверка самого файла. Для iconpacks в README указан только каталог; код имеет отдельный внутренний путь публикации `publish_icon` через userbot в настроенный icons channel. Это не подтверждает публичную загрузку `.icons` пользователями.

Набор принимаемых расширений задаётся централизованно: `.plugin` до 8 MiB; `.elyx`, `.eaf`, `.elyx.zip`, `.eaf.zip` до 100 MiB. Elyx parser читает `refmap.yaml|yml|json`, если он есть, чтобы определить `main` и `metainfo`; без refmap ищет стандартный `main.py` и `metainfo.yaml|yml|json`. Точка входа должна быть `.py` или `.pyc`. Parser проверяет пути, дубликаты, symlink/encrypted entries, общий раскрытый размер, число файлов, размеры метаданных и Python source; ограничивает YAML aliases и nodes, locale metadata и общий объём проверяемого исходника. Если в архиве есть `.pyc`, принимается magic для Python 3.11 и минимальная длина заголовка, но байткод не декомпилируется. Эти пределы уменьшают поверхность архива при рассмотрении и не доказывают, что плагин безопасен при исполнении клиентом.

Upload flow предварительно проверяет расширение и размер Telegram document, скачивает в отдельный временный каталог, повторно проверяет размер на диске, запускает metadata parsing через `asyncio.to_thread`, затем переносит принятый файл в uploads с уникальным суффиксом. Некоторые крупные файлы проходят через MTProto file client/transfer chat; `.plugin` при ошибке Bot API fallback не получает, Elyx может получить. Порог передачи и серверные лимиты дополнительно заданы в `bot/limits.py` и helpers.

`validate_new_submission` проверяет blocklist, минимальную поддерживаемую версию, имя-slug против уже опубликованных внутренних плагинов и ID против индекса официальных опубликованных ID. `check_duplicate_pending` дополнительно ищет тот же ID или slug имени среди `pending`/`draft`, с исключением собственного черновика автора. Обновление должно сохранять plugin ID и увеличивать версию; версии нормализуются извлечением цифровой последовательности и сравниваются через `packaging.version.Version`, при недоступном/непригодном значении — по числовым компонентам. Операторные префиксы `>=`, `<`, `==` и подобные при нормализации удаляются; проверки не являются полным интерпретатором спецификаторов PEP 440.

## Заявка, модерация и публикация

Заявка хранит plugin payload вместе с русскими и английскими описаниями/инструкциями и выбранной категорией. Required draft fields проверяются отдельным сервисом. `submission_fingerprint` хэширует нормализованный набор полей заявки и plugin metadata для распознавания изменений. Уникальный callback token создаётся от request ID через BLAKE2s; это компактный маршрутизатор Telegram callback data с разрешением обратно на request, а не секрет для аутентификации.

Moderation service допускает голоса по заявкам в статусах `pending`, `error` и `scheduled`, кроме удаления. Сначала vote/reason записывается в отдельную pending структуру на модератора, затем фиксируется в журнале `moderation_votes`; конфигурация по умолчанию требует причину и разрешает отправлять её автору. Принять голос можно из настроенного forum chat либо администратору. `vote_threshold` ограничен снизу единицей. Авторская апелляция доступна владельцу отклонённой заявки один раз, требует минимальную длину комментария, очищает прежние голоса и возвращает заявку в `pending`; при этом уведомления модераторам и audit event выполняются раздельно.

Публикация нового plugin постит metadata и файл в канал через Bot API, затем обновляет статус и catalog entry, сбрасывает хранилище и удаляет локальную копию upload. Обновление редактирует сохранённое сообщение канала через Telegram userbot и может сохранить прежние usage/category при пустых полях новой заявки. Catalog entry хранит plugin ID, format, требования SDK/Elyx, версию, file ID/name, языковые описания и channel message pointer. Каталог ищется по двум языкам, описанию, usage, slug, category и источнику; результаты поиска перемешиваются перед применением `limit`.

Отдельный Telethon userbot нужен для channel publishing/sync и части передачи больших файлов/иконпаков. Он использует persistent session и отключается при `AuthKeyDuplicatedError`; README требует отдельной авторизации для каждого работающего экземпляра. `full_sync` читает сообщения каналов, группирует media album, парсит channel post и избегает повторного импорта уже учтённых message ID. Это механизм восстановления каталога из публикаций, а не runtime sync внутри ExteraGram.

Подписка ведётся на slug отдельного plugin или общий ключ `all`; при обновлении plugin admin flow отправляет подписчикам личное сообщение с версией, changelog и ссылкой-кнопкой. Ошибки Telegram send в этом fan-out подавляются, поэтому кодовый путь не доказывает доставку каждому адресату. Отдельный poster flow поддерживает расписание, повтор и автоудаление постов; README описывает его как функцию канального постинга, отдельную от выпуска новой версии plugin.

Requests и каталог живут в SQLite. База включает item-таблицы и JSON payload, WAL и вторичные индексы; часть document state кэшируется и пишется с задержкой через asyncio worker, а вызов без event loop пишет синхронно. `request_store` перемещает прикреплённые файлы при смене статуса и удаляет файлы отклонённых заявок по истечении семи дней. `audit.py` хранит последние 1000 событий, поэтому это ограниченный прикладной журнал, не неизменяемый compliance log. Startup проверяет целостность БД, прогревает storage/cache и запускает фоновые worker-циклы; shutdown ожидает остановки worker и flush хранилища.

Отдельный `moderation_stats` проецирует голоса и решения по новым/обновлённым plugin-заявкам в недельные отчёты (неделя определяется в UTC+05), с числом уникальных проверенных заявок, yes/no голосами, решениями и деталями модератора; выбор недели и карточка модератора доступны super-admin. Icon-заявки в этой статистике исключаются. README также описывает самостоятельный poster с расписанием, повтором и автоудалением; кодовый `poster_flow`/`poster` относится к общим публикациям канала, а не к расписанию выпусков plugin. Не запускалось.

## Что следует и чего не следует переносить в плагины

- Полезен как reference для собственного каталога/магазина: приём заявок, безисполнительный разбор metadata, отдельные очереди pending и draft, дедупликация ID/slug, проверка увеличения версии, staged vote с обязательной причиной, повторная модерация апелляций, channel-backed публикации, сохраняемый audit trail и кэш-инвалидация.
- Не является источником Android plugin API, Java/Chaquopy hook signatures, клиентского UI API или install contract. Его `PluginMetadata`, `parse_plugin_file` и `publish_plugin` — внутренние серверные контракты этого бота.
- README заявляет живой bot, размерные пределы, quiz, подписки, poster features и настройку Python 3.12; это документация, живая работа не подтверждалась. Заявленный минимум клиента 12.1.1 — default конкретной реализации versioning с возможностью настройки в SQLite, а не универсальное требование ExteraGram.
- Противоречие радара: radar называет репозиторий лучшим reference для будущего магазина/CI, но это оценка автора радара; код демонстрирует каталог с Telegram-взаимодействием, а не CI runner, воспроизводимую сборку, подпись или sandbox выполнения plugin. Проверка metadata не равна проверке доверия.
- Неизвестны live-конфигурация/доступы forum и каналов, работоспособность Bot API/Telethon на целевой инфраструктуре, восстановление резервной копии, поведение на враждебных Elyx-пакетах и совместимость правил в будущих версиях plugin/client.
