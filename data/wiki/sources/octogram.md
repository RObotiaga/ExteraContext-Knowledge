## Что здесь можно перенести в разработку плагинов

### Это не SDK и не plugin runtime

В прочитанном дереве нет отдельного описания plugin API, зависимости ExteraGram SDK или `BasePlugin`-контракта. OctoGram строится как Android application и библиотечный модуль Telegram (`settings.gradle`); его функции подключены импортами и прямыми изменениями `org.telegram.*` call-sites. Это вывод из границ просмотренной выборки, а не доказательство, что нигде в полном дереве нет экспериментального интерфейса. Портируя идею в exteraGram, нужно найти host SDK API для той функции; ссылки на OctoGram-класс сами по себе не дают совместимого вызова.

Заметные точки, где собственная логика врезана в клиент: `DrawerLayoutAdapter` читает `OctoConfig` при построении drawer и скрывает заблокированные аккаунты; `ChatActivity` применяет пользовательские double-tap/header/search настройки к сообщениям и шапке; `ChatActivityEnterView` меняет запись/подтверждение отправки, клавиатуру emoji и перевод. Это полезная карта поведения для поиска эквивалентных hooks в другом клиенте, но сами точки — кодовая модификация OctoGram.

### Настройки и UI

`ConfigProperty<T>` хранит ключ, начальное значение и локальное текущее значение. `updateValue(T)` игнорирует равное значение, иначе обновляет поле и, только при непустом ключе, сохраняет `String`, `Int`, `Boolean`, `Float` или `Long` через AndroidX `SharedPreferences.edit`; неподдержанный тип с непустым ключом приводит к `IllegalArgumentException`. С null-ключом значение остаётся неперсистентным, а неподдержанный тип не проверяется и остаётся только в памяти. При непустом ключе `clear()` удаляет его и сбрасывает поле к default; с null-ключом тело метода не выполняется. Для keyed unsupported типа `_value` меняется до исключения — учитывайте это при переносе.

`OctoConfig.INSTANCE` создаёт типизированные properties, складывает их в список и при инициализации один раз грузит значения из приватного `octoconfig` store; в `loadConfig()` чтение Boolean/String/Integer/Long выполняется под `synchronized(this)`. Хотя `ConfigProperty.updateValue()` умеет записать `Float`, у `OctoConfig.loadConfig()` нет ветки Float; при этом среди объявлений properties в `OctoConfig` float-значение не используется. Миграции старых ключей встроены в загрузку: пример `drawerItems` переименовывает набор старых булевых ключей в JSON-массив и удаляет их. `resetConfig()` проходит по зарегистрированным свойствам; ключевой практический паттерн — централизовать миграцию рядом с чтением, а не разбрасывать переименование по UI.

`OctoPreferences.builder(title)` собирает `OctoPreferences`: deep link, необязательный save button, список `BaseRow` и actions контекстного меню. `category(...)` добавляет header и shadow, умеет передать `ConfigProperty<Boolean>` для условного показа; `.row(...)` принимает готовый row; `build()` фиксирует списки через `List.copyOf`. `OctoContextMenuElement` — подпись, иконка, `Runnable`, признак danger. Это конкретная внутренняя схема построения preference UI, а не способ зарегистрировать страницу внешнему плагину.

`PreferencesFragment` оборачивает `PreferencesEntry`: при создании вызывает `entry.onFragmentCreate()`, при уничтожении удаляет Bulletin delegate и вызывает `entry.onFragmentDestroy()`, а activity-result передаёт entry. Реализация `updatePreferences()` получает новый `OctoPreferences`, разворачивает expandable rows и обновляет текущий список. Для своего экрана это хороший lifecycle-шаблон: подписки и временные ресурсы связывать с fragment create/destroy, список строк обновлять через владельца UI.

У fragment есть операции `insertRow(BaseRow, BaseRow, boolean)` и `deleteRow(BaseRow)`: вставка существует, только если anchor уже присутствует, затем ставит reload на UI thread с задержкой 100 мс; удаление строки также удаляет дочерние элементы expandable row. Это поведение нельзя воспринимать как произвольный межпоточный API: класс — UI Fragment и механизм явно обновляет RecyclerView.

### Account, потоки и сеть

Часть помощников адресует данные к `UserConfig.selectedAccount`: например, drawer читает `MessagesController` выбранного аккаунта, а media helper использует соответствующий `FileLoader`. Запросы deep-link авторизации используют переданный `currentAccount` для `ConnectionsManager`, а callback переключает UI-операцию на `AndroidUtilities.runOnUIThread`. При переносе в multi-account клиент захватывайте account id из конкретного экрана/события и передавайте явно; `selectedAccount` может смениться между созданием async operation и callback. Это практический риск, выведенный из наблюдаемого разделения двух способов адресации.

`OctoLogging` отбрасывает пользовательские записи, если `BuildVars.DEBUG_PRIVATE_VERSION == false`, затем записывает их асинхронно через собственный `DispatchQueue("logQueue")` в файл `_debug_log.txt` каталога логов. Такой паттерн отделяет disk I/O от вызывающего UI потока; private build flag является гейтом, поэтому не считайте этот логгер общедоступным диагностическим каналом в release.

`StandardHTTPRequest.Builder(url)` по умолчанию задаёт `GET` и connect/read timeout по 10 секунд; fluent методы меняют timeout, headers, строковое тело UTF-8 и HTTP method. Конструктор непосредственно открывает `HttpURLConnection` и, если задано тело, пишет его сразу; `request()` выполняет I/O синхронно, отдаёт response/error stream, отдельно выбрасывает `Http429Exception`, логирует и пробрасывает прочие `IOException`, отключает соединение в `finally`. Поэтому весь путь `build()` и `request()` следует выполнять с фонового контекста: `build()` сам открывает output stream и пишет тело, если оно задано, а `request()` затем выполняет запрос и читает ответ. Результат нужно самостоятельно вернуть в UI dispatcher; у helper нет собственного executor/HTTP callback.

### Сборка, диагностика и ограничения

В snapshot заданы compile SDK 36, target SDK 35, min SDK 21, Java source/target 21; `settings.gradle` включает `:TMessagesProj` и `:TMessagesProj_App`. Версии из `gradle.properties` относятся именно к этому snapshot; это не текущие версии всех Telegram-derived клиентов.

README для воспроизведения сборки просит указать собственный Telegram `api_id` в `BuildVars.java`, добавить Google Services конфигурацию и signing file/passwords через локальные Gradle properties; рекомендует не выдавать fork за Telegram, сменить логотип, изучить MTProto security guidance и публиковать исходный код согласно лицензиям. Это документационные инструкции, они не были проверены сборкой. В репозитории есть файл `TMessagesProj/config/release.keystore` по дереву, но его содержимое не изучалось и в wiki не копируется; не используйте встроенный signing material при собственной публикации.

Из README берётся только то, что он утверждает наличие ccache (папка `Tools` или Homebrew на macOS) как требования сборки. Конкретный CI и варианты flavor не исследованы; сборка, тесты и runtime на Android не запускались. Radar указывал, что ветка заметно отстаёт и свежих самостоятельных изменений не найдено; это secondary observation, а не вывод из одного pinned snapshot. Точные отличия от upstream и commit history в этом проходе не сравнивались.

## Практические рецепты и gotchas

1. **Добавить настройку в собственный клиент:** сначала определить её тип/default; для persistent state дать уникальный ключ и хранить через подходящее persistent API host-плагина. OctoGram регистрирует properties централизованно, поддерживает только пять простых типов в `ConfigProperty`, а сложные значения сериализует в JSON string. Не брать `OctoConfig.INSTANCE` как контракт внешнего плагина.
2. **Собрать экран списка:** описать модель rows отдельно от Fragment; задавать условное отображение через state property, context action держать в `Runnable`, а временные подписки убирать в destroy lifecycle. Убедиться, что все UI mutations идут через main dispatcher.
3. **Отследить multi-account ошибку:** проследить исходный `currentAccount` от UI action до request/service; не подменять его поздним чтением глобального `selectedAccount`. Проверить смену аккаунта во время async callback и пересоздания фрагмента.
4. **Сделать HTTP вызов:** выставить method/content type/body и таймауты до `build()`, выполнить и `build()`, и блокирующий `request()` в рабочей очереди, отдельно обработать HTTP 429 и остальные IOException, затем вернуть результат на UI dispatcher. Helper возвращает тело, а не унифицированную структуру со status/header.
5. **Подготовить собственную сборку форка:** использовать собственный app id/credentials, отдельно настроить Google Services и подпись в локальных файлах, сверить `APP_VERSION_*`/`TELEGRAM_VERSION_*`, проверить SDK/JDK/toolchain и лицензии. README этого snapshot — инструкция, не зелёный CI или воспроизводимый результат.

Изменённые call-sites OctoGram следует читать как ориентиры поиска аналогичных событий/hook в ExteraGram. Факт наличия точки в форке не подтверждает, что hook доступен внешнему plugin runtime или переживёт обновление host.
