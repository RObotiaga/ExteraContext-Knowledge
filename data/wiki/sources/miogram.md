# Miogram / Amegram — клиент-донор и экспериментальная plugin runtime

Источник: [fuckramochka/miogram](https://github.com/fuckramochka/miogram). README в этом снимке уже называет проект **Amegram**, тогда как URL и metadata остаются `miogram`; ссылки Forge/patch manager также используют имя `amegram`.

Код и зависимости не запускались, пакеты не устанавливались; выводы ниже относятся к статическому снимку. `docs` — заявления документации, `code` — реализация, попавшая в дерево; выполнение приложения на устройстве не проверялось.

## Роль и границы

Это большой Android-клиент-донор, а не ExteraGram SDK. Наиболее полезны его Python plugin manager и hook-слои; Rust/WASM SDK, Kotlin trust/engine и Plugin Forge существуют как раздельные компоненты с неподтверждённым общим execution path. README и `docs/PLUGINS_DEV_GUIDE.md` описывают более широкий WASM/Python/Java API, чем подтверждается фактическим glue-кодом. Отдельные подсистемы AntiBlock, Cloud Vault, hotpatch и radar-feature paths изучены только в релевантном объёме; Telegram upstream целиком не разбирался.

## Технические факты

### Plugin manager и точки вмешательства

- В текущем дереве `MiogramPluginsActivity` — compatibility alias к `app.exteraless.plugins.ui.PluginsActivity`, чей активный manager — Chaquopy/Python. Комментарий alias утверждает, что прежний WASM manager «не поставлялся в этом дереве», однако в том же pinned tree физически присутствуют Kotlin `app.miogram.core.plugins.*` и `WamrWasmRuntime`; это утверждение комментария устарело или противоречит snapshot. Наличие этих классов, в свою очередь, не доказывает, что они соединены с активным экраном/manager.
- `PythonPluginsEngine.ensureStarted(Context, StartCallback)` стартует Chaquopy и импортирует `extera_utils.plugin_loader` на выделенном single-thread executor `plugins-engine`; callback запуска приходит с этого executor. Сам метод объявляет lifecycle load/unload синхронным, а методы событий прямо говорят, что вызываются синхронно из вызывающего потока. Не переносите это на все вызовы как обещание одного потока.
- Текущая Python интеграция передаёт account и payload через `callSendMessageHook`, `callPreRequestHook`, `callPostRequestHook`, `callUpdateHook` и `callUpdatesHook`. `PluginsController` маршрутизирует регистрацию запросов по имени: `TL_updates*`/`TL_updateShort*` — контейнеры, `TL_update*` — одиночные updates, остальные — request hooks; исходящие hooks требуют `messages.send`, request/update hooks — `messages.read`. `CANCEL`, `MODIFY` и `MODIFY_FINAL` обрабатываются менеджером как стратегии, а `FINAL` прекращает дальнейший проход.
- У `MioHook` есть отдельная Java-шина для pre-send, received message, feed item, AI result/tool, audio, preset, vault, dialog visibility и UI-container. Handle умеет pause/resume/unregister, регистрация несёт owner/priority; три последовательных исключения выключают запись в quarantine. Это внутренняя шина клиента, а не подтверждённый публичный интерфейс Python-плагина.
- Плагинная модель в коде читает Python-метаданные через `readMetadataJson`; модель `Plugin` содержит `id`, `path`, engine, settings/requirements и permissions. Документационная схема `plugin.json` из `PLUGINS_DEV_GUIDE.md` не подтверждена как фактический формат установки в текущем manager.
- Установочный путь `PluginInstallHelper.confirmAndInstall(...)` служит общим consent gate для установки: capability scan выполняется до consent sheet, выбранные разрешения сохраняются до установки. По комментарию manager, все галочки по умолчанию сняты; пустой выбор даёт isolated trust level, hooks/native — trusted.
- Набор permission ключей: `ui`, `messages.read`, `messages.send`, `network`, `files`, `intents`, `settings`, `hooks`, `native`; `hooks` и `native` помечены опасными. Код прямо оговаривает, что плагины работают в том же процессе и могут обращаться к Java через Chaquopy напрямую: модель ограничивает обычные вызовы через SDK и делает намерения видимыми, но не является границей безопасности против враждебного кода.
- Обратная совместимость имеет широкое исключение: без записи permissions и без объявленного `__permissions__` уже установленный плагин получает `ALL`; неизвестный plugin id получает только `ui`. Это следует учитывать при анализе старых установок и не трактовать пустую запись как эквивалент отсутствующей.
- `MioForge` генерирует Python/Lua/Go/Rust варианты. Python-файл Forge уходит и в `PluginsController.installPlugin`, и в `MiogramHerokuManager.installModuleFromCode`; Lua сохраняется через Heroku manager, а в текущем коде экран прямо предупреждает, что без Lua engine работают только текстовые фильтры. Поэтому общий экран генератора не означает общий plugin runtime для каждого выбранного языка.

### WASM SDK и сборка

- Реальный текущий SDK-контракт Rust — `Plugin::handle(&mut self, op: &str, payload: &[u8]) -> Result<Vec<u8>, i32>` и `register!(Type)`. SDK экспортирует ABI v1 `miogram_abi_version`, `miogram_alloc`, `miogram_guest_free`, `miogram_call`; фабрика экземпляра откладывается до первого вызова, а документированный режим хоста — один instance и сериализованные вызовы. Это более узкий API, чем Python hooks из guide.
- Host и guest используют allocator самого guest для буферов запроса/ответа; не смешивайте эти указатели с `WAMR module_malloc`. `miogram_call` возвращает упакованную пару ptr/len для ответа или отрицательный код ошибки.
- Wire format фактического Rust `envelope.rs` в v1 — `MIOG`, version byte, три нулевых reserved bytes, little-endian `op_len`, UTF-8 operation и оставшиеся bytes как payload. При этом SDK README и `docs/ARCHITECTURE.md` всё ещё называют magic `HYPR`; `WasmRuntime` KDoc ожидает FlatBuffers. `host_api.fbs` — целевой формат без используемых generated bindings, а `SendAction` помечен placeholder.
- В `envelope::decode` есть `MAX_TOTAL = 4 MiB`, но текущий `payload_len_hint()` возвращает `0`; проверка размера считает только header+operation и не учитывает оставшийся payload. Это ограничение фактического кода, не гарантия лимита на сообщение; хостовой `MAX_PAYLOAD` нужно анализировать отдельно.
- В snapshot есть отдельный Kotlin core `MiogramPluginEngine`: install проверяет подписанный manifest/trust anchor/размер/hash кода, dispatch применяет `OpPolicy`/capability gate, а три trap приводят к quarantine. Это code-level реализация отдельного слоя, не runtime verification. В проверенном Forge/manager пути `.wasm` отправляется в Exteraless `PluginsController`, который создаёт метаданные плагина и помечает его загруженным; call-site, связывающего эту операцию с `MiogramPluginEngine`/`WamrWasmRuntime`, в изученном пути не найден.
- Реализации host/guest пока не демонстрируют единый контракт: `MiogramPluginEngine.dispatch(pluginId, op, payload)` проверяет `op`, но вызывает `miogram_call` только с `payload`; явное кодирование `MIOG` operation frame не найдено, а core runtime описывает FlatBuffers. Kotlin `WamrWasmRuntime.loadModule` также не передаёт `SandboxConfig` JNI-загрузчику и возвращает `0` для fuel accounting. JNI-комментарий требует trusted signed modules и отмечает отсутствие preemption, но сам JNI loader не принимает manifest/signature; нельзя считать подпись/лимиты enforced этим bridge без связанного проверенного call path.
- Scaffold Rust-проекта прописывает dependency как Git `https://github.com/fuckramochka/mioplugin`, package `miogram-plugin-sdk`, branch `main`, хотя SDK в снимке лежит внутри `miogram/sdk/rust/miogram-plugin-sdk`. Это отдельное место для проверки при сборке/воспроизводимости.
- `MioForgeBuilder.probeAndBuild(...)` проверяет Cargo/TinyGo и запускает сборку в background queue; при отсутствии toolchain выдаёт desktop-команду. Таймаут компиляции — 300 секунд; Rust output копируется в `plugin.wasm` рядом с `manifest.json`. Код не подтверждает, что Android-устройство обычно поставляется с этими toolchains.

### Radar-подсистемы

- `AmegramPatchManager` раз в шесть часов планирует чтение `hotfix/patches.json`; config patch складывает rules в prefs, bytecode patch скачивает DEX и вызывает публичный static `apply(Context)` через `DexClassLoader`. В изученном классе не видна проверка подписи или хеша перед загрузкой, хотя радар ранее описывал signed manifest; эту функцию нельзя считать безопасным образцом обновления кода без отдельной проверки manifest/transport/integrity.
- `MiogramAntiBlockEngine` слушает состояния Telegram-соединений, по умолчанию имеет 3.5-секундный порог зависания и может вызвать deep probe: сначала тестирует общую сеть, затем TCP-доступность нескольких Telegram DC на 443; только после блокировки вызывает выбор обходного Fake-TLS proxy. Это конкретный алгоритм клиента, не готовый plugin API и не проверенная оценка качества этих endpoints.
- `MiogramLrcModel` разбирает стандартные LRC строки и word-timed данные, группирует слова в karaoke lines; `MiogramLyricsEngine` имеет источники LRCLib, NetEase и Genius с кэшированием. `AudioPlayerAlert` создаёт собственные `MiogramLyricsView` и `MiogramModernPlayerLayout`, то есть это форкнутый клиентский экран и UI-подсистема, а не переносимый plugin API.
- Online halo реализован как отдельная отрисовка вокруг online-индикатора: `MiogramUiEngine` рассчитывает импульс по elapsed time (отключая halo в power-save), а `DialogCell` вызывает её только при текущем online status пользователя. Это полезный локальный draw pattern; он привязан к Telegram `DialogCell` и не доказывает plugin integration.
- В `MiogramUiEngine` есть `processVoiceWaveHaptic(view, amplitude)`: при включённой настройке helper ограничивает частоту 60 ms и вызывает tick при amplitude выше 0.65. В изученных call-sites вызов этого helper из playback waveform не найден, поэтому pinned code подтверждает helper, но не работающий end-to-end waveform feedback.
- Радар-кандидат Smart Feed имеет отдельные `MiogramSmartFeedService`/`MiogramSmartFeedActivity`: код читает 7 дней из tracked channels, ограничивает выборку 25 постами на канал/1500 символами на пост и 12 000 символами prompt, просит Gemini отфильтровать рекламу/сжать контекст, кэширует карточки и сохраняет raw fallback при ошибке AI. В `LaunchActivity`, `ChatActivity` и `DialogsActivity` отдельный launcher `MiogramSmartFeedActivity` не найден; пункт `News Feed` в проверенном `DialogsActivity` ведёт в другой `app.exteraless.feed.ui.FeedActivity`, поэтому доступность именно Smart Feed из UI не утверждается.
- Kanban реализован как `BaseFragment` с локальным JSON в app-private `SharedPreferences`; карточка хранит `dialogId`/`messageId`, контекстное действие `ChatActivity` создаёт запись из сообщения, а `DialogsActivity` и chat menu открывают Kanban. Split-chat создаёт два `ChatActivity` внутри split layout и вызывается из chat/dialog menus. Отдельный floating-chat service использует `TYPE_APPLICATION_OVERLAY`, имеет manifest declaration и запускается из split-chat; это source-level UI implementation, не подтверждение стабильности Android window/lifecycle на устройстве.
- Cloud Vault шифрует данные AES-256-GCM отдельными IV; потоки режутся на части по 100 MiB, буфер обработки — 1 MiB, затем документы отправляются через штатный `SendMessagesHelper.prepareSendingDocument` в привязанный чат/аккаунт. Синхронизация ищет историю и подпись `#MVLT`, сначала восстанавливает manifest, затем части и их порядок.
- Vault master key создаётся случайным 32-байтовым значением, но сохраняется как hex в `SharedPreferences` (`MODE_PRIVATE`); по этому коду это локальное app-private prefs-хранилище, а не StrongBox/AndroidKeyStore. Общие утверждения README о StrongBox нельзя автоматически переносить на ключ именно Cloud Vault.
- Vault вызывает `MioHook.dispatchVault` для регистрации/удаления файла, однако это доказывает событие внутренней Java-шины, не доступность Vault event третьесторонним Python-плагинам.

## Практические приёмы и границы переноса

1. При переносе hook-архитектуры сначала отделите контракты регистрации, account-aware dispatch и отмены/замены от конкретной реализации Python. В Miogram это разные слои: `PluginsController` выбирает владельцев, `PythonPluginsEngine` вызывает loader, а `MioHook` — отдельная Java-шина.
2. Для потока отправки/запросов сохраняйте порядок по priority, проверяйте каждый плагин `loaded`, определите семантику `CANCEL`/`FINAL`, и удаляйте hooks вместе с plugin lifecycle. Это наблюдаемый pattern в code; он не устанавливает совместимость имён или сигнатур с ExteraGram.
3. Относитесь к permissions как к UI/SDK-gating и аудиту, а не к sandbox boundary для in-process Python; особенно явно предупреждайте о `hooks`/`native` и старых установках с legacy `ALL`.
4. Rust WASM плагину нужен точный guest-owned ABI. Не реализуйте отдельный FlatBuffers payload, пока SDK использует `MIOG` envelope; сначала сопоставьте ABI, magic/version, op и buffer ownership.
5. Для удалённых bytecode updates проверяйте происхождение и целостность до `DexClassLoader`; в изученном patch manager этого gate не видно.
6. Vault-перенос требует пересмотреть key custody отдельно от chunk format: AES/GCM наличие не компенсирует хранение master key в незашифрованных приложенческих prefs.

## Расхождения радара и пробелы

- Радар отмечал `MiogramPluginsActivity` как пример близкого к встроенной среде разработки plugin Forge/runtime. Head-снимок уточняет границу: Forge есть, но менеджер с этим именем лишь перенаправляет к Python-based `app.exteraless` manager; native WAMR остаётся каркасом.
- Радар называл WASM Rust/Python/Java runtimes и подписанные hotpatch более зрелыми. `PLUGINS_DEV_GUIDE.md` также заявляет Python `plugin.json`, Ed25519-подпись и sandbox; текущий Forge генерирует другой `manifest.json`, Python manager читает метаданные из Python, а hotpatch code не показывает signature/hash validation. Это именно расхождение docs/radar и кода, а не утверждение, что криптографической проверки нигде в репозитории нет.
- Радаровые описания Smart Feed, Kanban, Split-screen и floating chat не следует обобщать как готовые UI-поверхности: в head есть код и некоторые menu call-sites; для Smart Feed конкретный launcher не найден в просмотренных entrypoints, а `docs/ARCHITECTURE.md` помечает multi-panel/foldable как следующую итерацию/дизайн.
- Radar-context от 18 сентября сообщает об отключении ряда ранних экспериментальных функций. В текущем закреплённом дереве соответствующие классы/engine ещё присутствуют; их наличие не доказывает включение экранов, регистрацию lifecycle или доступность в релизной сборке. Для подтверждения включённости нужны точные call-sites, build/runtime evidence и проверка итоговой сборки.
- AntiBlock endpoint-ы, proxy pool, Cloud Vault пользовательский поток, подпись hotpatch manifest, все AI/agent hooks и production sandbox поведение не проверялись на устройстве. `docs/BUILD.md` и `docs/ARCHITECTURE.md` содержат и статусные оговорки, и планы; их нельзя сводить к одному статусу «готово».
- Не проверялись работа WASM на устройстве, реальная схема подписания/доверенных ключей в продуктовой установке, порядок/формат байтов между Forge, Python manager, Kotlin engine, JNI и Rust SDK, а также UI/permission/overlay/network поведение radar-фич. Эти gaps отделены от наличия source-файлов и документационных заявлений.
