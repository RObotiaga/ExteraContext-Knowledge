# Ettacent/NimarkoGram

NimarkoGram — самостоятельный Android-клиент на исходниках Telegram for Android, а его дерево содержит полноценный host runtime плагинов. Поэтому это прежде всего референс реализации движка, мостов, загрузки и lifecycle, а не пример одного готового стороннего плагина. README заявляет Python и DEX плагины, hooks, зависимости и compatibility API; комментарии в самом коде уточняют, что `com.exteragram` и Python aliases служат совместимости. Это не доказывает полную совместимость со всеми версиями ExteraGram.

Исследован pinned snapshot `main`, SHA `881d0ea1ce5f6a3a234f46d0e928bb0d95305f6b`, зафиксированный 2026-09-27T15:49:43Z. README маркирует NimarkoGram и Telegram как `12.10.5`; GitHub metadata указывает GPL-2.0. Источник и приложение не собирались и не запускались, поэтому ниже только `code` и `docs`, без `runtime-verified`. Все ссылки на код закреплены за этим SHA.

## Архитектура и факты кода

### Контракт Python-плагина и hooks

`base_plugin.BasePlugin` задаёт lifecycle `on_plugin_load()` / `on_plugin_unload()`, `create_settings()`, `on_app_event(event_type)`, request hooks с `account`, update hooks с `account` и `on_send_message_hook(account, params)`. По умолчанию callbacks ничего не меняют: request/update callbacks возвращают `HookResult()`. Java движок при загрузке обнаруживает и bind-ит реализованные hooks, затем Controller маршрутизирует callbacks к активному плагину.

Для прямого Pine/Xposed-style вмешательства доступны `hook_method(Member, xposed_hook=None, priority=None, before=None, after=None)`, `hook_all_methods(...)`, `hook_all_constructors(...)` и `unhook_method(unhook)`. Можно передать callback `before`/`after` вместо экземпляра `MethodHook`; фильтры `@hook_filters(...)` и `HookFilter` позволяют ограничить вызов по аргументам, результату или условию. Хост сохраняет unhook handles по ID плагина и снимает hooks при cleanup. В safe mode добавление method hook возвращает `None`; доступность Pine зависит от инициализации runtime.

У request/update/send hooks account — индекс аккаунта клиента, а не ID чата. Это подтверждено и интерфейсом `PluginsHooks`, и call-site: `ConnectionsManager` передаёт `requestName` и `currentAccount` до выполнения запроса и после ответа; `MessagesController` передаёт account при обработке `Updates` и одиночного `Update`; `SendMessagesHelper` вызывает outgoing-message hook с `currentAccount`. В самом Python API `client_utils` отдельные helpers также принимают `account=None`; для переносимого кода выбирай аккаунт явно, когда действие должно быть привязано к конкретному профилю.

`AppEvent` включает `app_pause`, `app_resume`, `app_start`, `app_stop`; `LaunchActivity` отправляет pause/stop/resume из соответствующих lifecycle call-site. `add_hook(name, match_substring=False, priority=0)` регистрирует request/update/send event по имени, а `add_on_send_message_hook(priority=0)` — сокращённый помощник для send hook. Это события движка NimarkoGram; сигнатуры не следует автоматически переносить на другой host.

### Runtime ownership, потоки и teardown

`PluginsController.PluginRuntimeToken` содержит plugin ID, generation и instance ID. Engine получает токен до импорта модуля и размещает его в plugin instance. Каждая callback/worker операция должна проходить проверку текущего runtime; состояние `PREPARING` допускает только разрешённый initialization scope. Перезапуск или отзыв поколения блокирует старые callbacks, а `releasePluginRuntime` отказывается освобождать слот, пока `activeCalls != 0`.

`plugin_runtime` переносит owner token через Python `Thread`/`Timer` и executor задачи, а `make_interface_proxy` создаёт Java-owned proxy для callback interfaces, чтобы Android не удерживал Chaquopy proxy после выгрузки Python модуля. `BasePlugin._cleanup()` вызывает token-specific `cleanupPlugin(id, token)` и не очищает `initialized`: Java lifecycle остаётся ответственным за ровно один `on_plugin_unload`. Не меняй lifecycle flags вручную как замену unload.

Загрузка исполняется на `Utilities.pluginsQueue`; до импорта движок bootstrap-ит runtime-зависимости и устанавливает импортёр, затем импортирует `.py`, находит `BasePlugin` subclass, создаёт instance и выполняет `on_plugin_load` с timeout. После callback runtime коммитится и settings UI загружаются отдельно. Startup enumeration в snapshot ищет `.py`, а константа `.plugin` используется как расширение для экспортируемого plugin-файла/MIME — не путай эти два пути без проверки конкретного install flow.

### Состояние, intent handlers и developer install

`get_setting`, `set_setting`, `export_settings`, `import_settings` и `reload_settings` — API `BasePlugin`. Файл настроек — `plugin_settings.json` в директории плагинов; writer работает в отдельном потоке, пишет snapshot во временный файл, делает `fsync` и атомарно заменяет целевой JSON. Низкоуровневый `plugin_settings.set_setting` возвращает completion, а `flush_settings(timeout)` ждёт bounded durability barrier. Обёртка `BasePlugin.set_setting` completion отбрасывает и возвращает `None`, поэтому она не обещает, что запись уже завершилась. Мутации от callback принимаются только при валидном runtime token, принадлежащем той же корзине plugin ID.

`add_intent_hook(filters, callback, priority=0, name=None)` передаёт callback `IntentContext`; обработчик может вызвать `consume()` либо вернуть значение, останавливающее дальнейший default handling. Возвращаемый handle снимается через `remove_intent_hook(handle)` или `handle.unhandle()`. Host cleanup снимает зарегистрированные intent handlers по plugin ID/runtime.

Install-кандидат копируется в host-owned stage, отклоняется при symlink source, разбирается AST без выполнения кода, сверяется с ожидаемым plugin ID и хешируется. Host ticket одноразовый, имеет срок действия и принимается только на `pluginsQueue`; перед установкой SHA файла повторно сверяется. Метаданные `__requirements__` парсятся отдельно. В изученном коде не найдено декларативной модели plugin permissions, поэтому радарное «permission prompt» к этому источнику не относится. Dev install bridge требует активный текущий bridge, команду с auth token и generation authority; при отзыве install отклоняется.

### Сборка и диагностика

README маркирует клиент как Android 7.0+; инструкция сборки задаёт JDK 17, Android SDK/Build Tools 36, NDK 26.3.11579264, CMake 3.22.1 и Python 3.11 для Chaquopy. Standalone APK по умолчанию собирается для `arm64-v8a` и `armeabi-v7a`; `-PngArm64Only` — быстрый локальный ARM64 вариант. Pine подключается submodule-ом, host-specific diff описан как `patches/pine-nimarkogram.patch`.

Для plugin-side диагностики есть `BasePlugin.log(message)` и `android_utils.log(data)`. `PluginDebugLog.ENABLED` в snapshot равен `false`, а обе перегрузки `PluginDebugLog.log` — no-op; не рассчитывай на эти debug statements в production log. Ошибки загрузки, timeout и безопасного отказа видны через host `FileLog`/plugin state, но их поведение на устройстве здесь не проверялось.

## Практические рецепты и ограничения

1. Для request/update logic наследуй `BasePlugin`, override нужный callback и возвращай `HookResult()` при отсутствии изменения. Используй переданный `account`, особенно в multi-account сценариях; host call-site действительно прокидывает текущий account.
2. Для точечного Java method hook сначала попробуй `hook_method(member, before=..., after=...)`, сохрани вернувшийся unhook и проверь его на `None`. При safe mode или недоступном Pine hook может не установиться.
3. Держи собственные worker/callback привязанными к lifecycle плагина и вызывай `on_plugin_unload` для освобождения ресурсов. Runtime token блокирует устаревшие callbacks, но не является изоляцией процесса и не отменяет произвольные системные побочные эффекты.
4. Для долговременного состояния используй `BasePlugin.set_setting`, но помни, что он не возвращает completion. Код хоста, которому нужна гарантия записи, может использовать низкоуровневый completion/barrier из `plugin_settings`; обычный возврат SDK метода не является синхронным flush.
5. Плагин, распространяемый через установщик, должен иметь статические литеральные `__...__` метаданные: install validator разбирает ограниченный набор assignment-ов через AST до import, затем отдельно проверяет содержимое и plugin ID.

Для UI-интеграции также доступны `add_menu_item(MenuItemData)` и `add_file_hook(...)` с удалением через handle. Это основные точки регистрации меню и обработчиков файлов чата; конкретные menu call-sites и полный смысл параметров `place`/`condition` здесь не перечислены.

Радар приписывает NimarkoGram обновление Telegram до 12.10.1 на 7 сентября и изменения Quote/QR UI, plugin security, media. Pinned snapshot уже маркирован `12.10.5`, то есть заявление о версии из радара устарело относительно snapshot. В изученном README/коде не нашлось подтверждения, что NimarkoGram реализует ExteraGram-подобные пользовательские grants для плагинов; факты этого источника подтверждают lifecycle/runtime validation, но не permission prompt. `docs/releases/75553.md` (12.10.5) описывает navigation, camera, media и animated stickers, не новые plugin API.

README заявляет DEX loading, однако полный путь загрузки стороннего DEX/JAR/APK в просмотренном plugin runtime не установлен. `PluginDexTracking` и `PluginDexRegistry` учитывают уже созданные DEX class loaders/classes для crash attribution; эти классы сами по себе не подтверждают механизм загрузки артефакта. Это оставлено как документированное заявление и явный gap реализации.

Открытые пробелы: фактическая совместимость стороннего ExteraGram-плагина на устройстве; полный surface клиентских utility/API; реализация и lifecycle сторонних DEX/JAR/APK artifact types; все UI menu call-sites; независимый аудит parser boundary и host install; подробная проверка wheel resolver/ownership схемы PipController; и точное сравнение исторических Quote/QR изменений. Проверены только перечисленные call-sites и выборочные тесты; сборка, тесты и runtime не запускались.
