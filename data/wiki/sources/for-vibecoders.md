## Что именно содержит репозиторий

README перечисляет структуру: папки плагинов с `.plugin` и разбором; индекс; сравнение repo + AI с Context7. Его полезные ссылки ведут на официальные plugin docs, Telegram Android source revision `009e973...` и декомпиляцию ExteraGram 12.5.1 через JADX ([README, строки 16–38](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/README.md#L16-L38)). Это указатели на дополнительные первоисточники, сами они в этом репозитории не зеркалируются.

На commit main индекс описывает три плагина: animtou 2.3.0 (touch ripple), LodraBu 1.0.3.1 (кнопка выхода из профиля), muztep downloader 1.2.0 (помечен abandoned) ([plugins-index.md, строки 1–5](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/plugins-index.md#L1-L5)). Файлы jaxtools есть в дереве, но практически пусты: анализ и `.plugin` по 35 байт, badge note по 155 байт; это не cookbook знаний.

`repo-vs-context7.md` объясняет, что автор считает особенностью ExteraGram/AyuGram: BasePlugin/MethodHook, hook_utils, client internals и Android/Telegram классы не покрываются библиотечными справочниками Context7; standard Python/Android API отнесены к подходящей области Context7 ([строки 17–29, 38–62, 66–78](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/repo-vs-context7.md#L17-L29)). Это мнение автора, не измерительный тест документационных систем.

## Практические знания по animtou

### Контракт, точка входа и lifecycle

Версия 2.1.0 задаёт `__id__ = "animtou"`, версию и `__min_version__ = "12.5.1"`; импортирует BasePlugin/MethodHook, Android UI helpers, Telegram SuperRipple и reflection helpers ([исторический `.plugin`, строки 1–25](https://github.com/corerudo/for-vibecoders/blob/ebdb543a6819915baa0ce62c3e5e15852d3a3fa0/allpg/animtou/animtou%20v2.1.0.plugin#L1-L25)). Версия 2.3.0 сохраняет минимальную версию 12.5.1 и использует те же семейства API ([`.plugin`, строки 4–24](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou%20v2.3.0.plugin#L4-L24)). Это manifest-level min version, не доказательство запуска на каждом AyuGram/ExteraGram build с таким номером.

`on_plugin_load(self)` загружает необязательную библиотеку zwylib/autoupdater (ошибка импорта не прекращает базовую работу), считывает настройки в память, находит `android.view.View.dispatchTouchEvent(android.view.MotionEvent)` через `Class.forName`, регистрирует `self.hook_method(method, _animtouHook(self), priority=5)` и добавляет пункт настроек через PluginsController ([2.1.0, строки 154–227](https://github.com/corerudo/for-vibecoders/blob/ebdb543a6819915baa0ce62c3e5e15852d3a3fa0/allpg/animtou/animtou%20v2.1.0.plugin#L154-L227); [2.3.0, строки 259–317](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou%20v2.3.0.plugin#L259-L317)). Ошибки поиска класса/метода сообщаются, но многие ошибки при `setAccessible` проглатываются и регистрация продолжается; это стоит учитывать при диагностике.

`on_plugin_unload(self)` удаляет updater task, снимает hook по сохранённому handle, обнуляет handle и очищает кэш; 2.3 также деактивирует echo polling ([2.1.0, строки 229–245](https://github.com/corerudo/for-vibecoders/blob/ebdb543a6819915baa0ce62c3e5e15852d3a3fa0/allpg/animtou/animtou%20v2.1.0.plugin#L229-L245); [2.3.0, строки 319–334](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou%20v2.3.0.plugin#L319-L334)). Анализ 2.3 прямо рекомендует явное снятие handle для прозрачного повторного load и очистку Java references из Python-кэша ([анализ, строки 460–473](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L460-L473)). В коде нет отдельных enable/disable callbacks; только load/unload видны в этих примерах.

### Hook API и обработка касания

Ключевая сигнатура Java метода: `View.dispatchTouchEvent(MotionEvent) -> boolean`; получение через `getDeclaredMethod("dispatchTouchEvent", motion_event_cls)` показывает важность полного списка типов аргументов. Hook class наследует `MethodHook`, хранит plugin reference, реализует `before_hooked_method(self, param)`, читает `param.args[0]` и `param.thisObject`, затем зовёт Python handler. `after_hooked_method` в 2.1 пустой и в 2.3 удалён как ненужный ([2.1.0, строки 81–107, 179–202](https://github.com/corerudo/for-vibecoders/blob/ebdb543a6819915baa0ce62c3e5e15852d3a3fa0/allpg/animtou/animtou%20v2.1.0.plugin#L81-L107); [2.3.0, строки 276–299](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou%20v2.3.0.plugin#L276-L299)). Анализ объясняет выбор before тем, что анимация должна стартовать на ACTION_DOWN до обычной обработки касания, а доступ к thisObject защищён отдельно для непредставимых Chaquopy-объектов ([анализ, строки 36–62](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L36-L62)). Последняя причина — авторское объяснение, не runtime тест в данном исследовании.

Обработчик пропускает события кроме `getActionMasked() == 0` (ACTION_DOWN) и дедуплицирует повторные вызовы одним токеном `(getDownTime(), actionMasked)`, поскольку событие проходит по View-цепочке; анализ это обосновывает ([анализ, строки 64–82](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L64-L82)). Экранные координаты берутся `getRawX/getRawY()`, при ошибке — `getX/getY()`; затем переводятся в локальные через `getLocationOnScreen` ([анализ, строки 83–99, 191–203](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L83-L99); [2.3 source, строки 336–377](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou%20v2.3.0.plugin#L336-L377)). Важно: 2.1 держит ещё `_last_up_token`, но 2.3 удаляет его как неиспользуемый ([анализ, строки 693–716](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L693-L716)).

### Multi-window и polling

Для нескольких окон берётся `WindowManagerGlobal.getInstance().mViews` — список decor roots. В 2.1 приватное поле находится reflection путём, а анализ отмечает кэширование `Field`; 2.3 помещает чтение поля в `_read_mviews`, кэширует Field и обходит все decor views ([анализ, строки 100–137](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L100-L137); [2.3 source, строки 138–162](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou%20v2.3.0.plugin#L138-L162)). Новые окна во время ripple получают короткий echo-poll: анализ указывает окно 300 ms и интервал 80 ms, обнаружение изменения количества views и пропуск уже встреченных hashCode ([анализ, строки 139–189](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L139-L189); [2.3 source, строки 201–237](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou%20v2.3.0.plugin#L201-L237)). В том же анализе прямо указано, что ripple не срабатывает при закрытии некоторых контекстных меню; предполагается отдельное окно/outside-touch path, но причина не подтверждена ([строки 852–860](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L852-L860)). Значит, глобальный View hook не даёт гарантии охвата каждого окна/события.

### SuperRipple, RuntimeShader, reflection и кэш

Плагин создаёт `SuperRipple(view)` сам и меняет только свои экземпляры; анализ версии 2.1 отмечает отказ от глобального constructor hook как способ не затрагивать родные Stars-анимации ([история 2.1, строки 898–904](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L898-L904)). Метод `setupSizeUniforms(boolean)` получается с точной primitive сигнатурой `Boolean.TYPE`; 2.1 получает приватные shader/effect через `set_private_field`; в 2.3 находит и кэширует Field `shader`, кэширует Method, вызывает `invoke(ripple, True)`, а `effect` присваивает напрямую ([2.1 source, строки 66–78](https://github.com/corerudo/for-vibecoders/blob/ebdb543a6819915baa0ce62c3e5e15852d3a3fa0/allpg/animtou/animtou%20v2.1.0.plugin#L66-L78); [2.3 source, строки 72–101](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou%20v2.3.0.plugin#L72-L101)). Анализ 2.3 указывает, что прежний доступ `ripple.JA.shader` давал AttributeError и заменён на reflection Field; это конкретный anti-pattern ([анализ, строки 338–385](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L338-L385)).

AGSL patch читает встроенный ресурс `R.raw.superripple_effect`, сохраняет уже обработанный текст, заменяет участки shader; созданный `RuntimeShader` используется в `RenderEffect.createRuntimeShaderEffect(shader, "img")` ([анализ, строки 243–337](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L243-L337); [2.3 source, строки 50–69, 90–101](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou%20v2.3.0.plugin#L50-L69)). Кэш ripple привязан к `view.hashCode()`, ограничен FIFO-подобным удалением первого ключа; версия 2.1 ограничивает размер 10, 2.3 — 30. Изменение dose очищает ripple cache, так как uniform задаётся при создании shader ([2.1 source, строки 28–32, 135–152](https://github.com/corerudo/for-vibecoders/blob/ebdb543a6819915baa0ce62c3e5e15852d3a3fa0/allpg/animtou/animtou%20v2.1.0.plugin#L28-L32); [2.3 source, строки 31–35, 104–108, 172–185](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou%20v2.3.0.plugin#L31-L35)). Само объяснение что создание shader/RenderEffect дорого — вывод автора анализа, не benchmark.

### Потоки, UI, настройки, compatibility

`make_ripple` помещает операции с View/SuperRipple в `run_on_ui_thread(_internal)`; 2.3 также использует `run_on_ui_thread(callback, delay_ms)` для polling, без собственного Python thread/sleep ([2.1 source, строки 135–152](https://github.com/corerudo/for-vibecoders/blob/ebdb543a6819915baa0ce62c3e5e15852d3a3fa0/allpg/animtou/animtou%20v2.1.0.plugin#L135-L152); [анализ, строки 413–428, 653–674](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L413-L428)). Это пример UI-thread boundary; отдельной схемы фоновых задач в animtou нет. Для настройки используется `AltSeekbar` через `dynamic_proxy(AltSeekbar.OnDrag)`, listener удерживается в `_seekbar_refs`; значения парсятся с запятой/точкой и clamp-ятся в заданные диапазоны ([2.3 source, строки 422–450, 471–520](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou%20v2.3.0.plugin#L422-L450)). Паттерны UI: BulletinHelper для ошибок и `PluginsController.openPluginSettings(__id__)` для открытия настроек ([анализ, строки 653–689](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L653-L689)).

Анализ 2.3 говорит, что локальную проверку `Build.VERSION.SDK_INT` удалили, так как целевой клиент содержит нужный SuperRipple; версия плагина при этом заявляет min 12.5.1. Автор перечисляет это как обоснование реализации ([анализ, строки 430–442](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/animtou/animtou-analysis.md#L430-L442)). Это не означает, что API level shader совместим повсеместно: repo не содержит runtime matrix Android/AyuGram. Наличие `Build` import в 2.1, отсутствие в 2.3 видно при сравнении исходников. Поля `mViews`, `SuperRipple.shader`, `setupSizeUniforms`, `PluginsController`, resource `superripple_effect` — не стабильный публичный контракт; перенос требует сверки с декомпиляцией конкретной сборки.

## Другие плагины: переносимые инженерные паттерны и оговорки

### LodraBu: hook-и меню и расхождения SDK/runtime

LodraBu разбирает добавление кнопки выхода и секции управления аккаунтами. Код получает Java `Class` через `jclass("java.lang.Class").forName(...)`, ищет точные сигнатуры вроде `ProfileActivity.createActionBarMenu(boolean)`, `SettingsActivity.fillItems(ArrayList, UniversalAdapter)`, `onClick(UItem, View, int, float, float)`, делает `setAccessible(True)` и передаёт Method в `self.hook_method(method, Hook(...))` ([LodraBu.plugin, строки 167–200](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/LodraBu/LodraBu.plugin#L167-L200)). Это полезный образец точной reflection сигнатуры и базовой plugin lifecycle регистрации.

Анализ различает `hook_method` для произвольных Java методов и `add_hook` для TL запросов/обновлений; также уточняет, что functional before/after callbacks передаются в `hook_method`, а `MethodHook(after=...)` в показанном виде неверен ([анализ, строки 89–134](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/LodraBu/LodraBu-analysis.md#L89-L134)). Автор сообщает, что в его установленном окружении `find_class("ProfileActivity").getDeclaredMethod(...)` приводит к AttributeError, хотя документация обещает Java Class; практическое правило разбора — получать reflection объект через `jclass("java.lang.Class").forName(...)`, а `find_class(...)` оставить для статических вызовов/конструирования ([анализ, строки 138–201](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/LodraBu/LodraBu-analysis.md#L138-L201)). Это runtime observation автора; конкретный SDK/build/version не привязан к воспроизводимому логу в репозитории и не должен считаться универсальным законом.

Lifecycle отдельно заслуживает проверки: `on_plugin_load` ставит три постоянных hooks без хранения handles и явного `on_plugin_unload`; при каждом создании меню `CreateMenuHook` дополнительно ставит hook на класс listener-а. Это наблюдение по коду; возможное накопление одинаковых listener hooks зависит от поведения host и здесь не подтверждено. Переносимый рецепт должен сохранять все handles и снимать их при unload либо дедуплицировать регистрацию ([LodraBu source, строки 47–58, 167–194](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/LodraBu/LodraBu.plugin#L47-L58)).

Для анонимного click listener анализ предлагает получить listener из Activity getter, затем `listener.getClass()` и reflection method, вместо поиска метода в ProfileActivity, потому что `onItemClick` расположен на listener-классе ([анализ, строки 234–254, 450–471](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/LodraBu/LodraBu-analysis.md#L234-L254)). UI-пункты аккаунтов собираются единым блоком и вставляются `addAll`, потому что несколько вставок в один индекс перемешивали пункты; обработчик использует отдельный диапазон собственных ID ([анализ, строки 473–568](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/LodraBu/LodraBu-analysis.md#L473-L568)). Ошибки выводятся через BulletinHelper с кнопкой копирования вместо безмолвного `except: return` ([анализ, строки 569–610](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/LodraBu/LodraBu-analysis.md#L569-L610)).

### muztep: background queue, temporary hooks, persistence, local inline UI

muztep показывает вход через `add_on_send_message_hook()` и `on_send_message_hook(self, account, params)`. Командный ввод валидируется, затем через `run_on_queue(lambda: ..., PLUGINS_QUEUE)` запускается network/parsing work; `HookResult` с `HookStrategy.CANCEL` блокирует отправку команды как обычного сообщения ([анализ, строки 17–42](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep-analysis.md#L17-L42); [source, строки 102–189](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep.plugin#L102-L189)). Сетевую работу не выполнять в синхронном UI render/hook пути — это прямо подчёркнуто для `_CellSetupHook`; там используется только уже закэшированная metadata ([анализ, строки 253–292](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep-analysis.md#L253-L292)). Обратный переход к UI делается `run_on_ui_thread(...)` ([analysis, строки 232–250](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep-analysis.md#L232-L250)).

Временный `MethodReplacement` для `AndroidUtilities.isInternalUri(Uri)` устанавливается только вокруг `send_audio` и снимается в `finally`, чтобы глобальная подмена не оставалась активной при исключении ([анализ, строки 45–73, 430–438](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep-analysis.md#L45-L73)). Это сильный пример ограничения scope hook-ов, хотя изменение глобального поведения метода всё равно требует тестирования конфликтов с параллельной отправкой.

Плагин сохраняет inline sessions и загружает их в `on_plugin_load`; для привязки markup к server-backed message использует маркер в тексте, а `ChatMessageCell.setMessageObject` hook на before строит markup из локального кэша и вызывает `measureInlineBotButtons()` до отрисовки ([анализ, строки 232–292, 352–381](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep-analysis.md#L232-L292); [source, строки 102–123](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep.plugin#L102-L123)). Локальный callback на inline button перехватывается `ChatActivity$ChatMessageCellDelegate.didPressBotButton`, проверяет префикс payload и делает `param.setResult(None)` чтобы погасить штатный callback ([анализ, строки 296–312](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep-analysis.md#L296-L312)). Перерисовка шлёт `NotificationCenter.postNotificationName(228, dialog_id)` с fallback на notifyDataSetChanged ([анализ, строки 383–395](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep-analysis.md#L383-L395)). Все Java hooks перечисляются из `getDeclaredMethods()` по имени; этот путь стоит дополнительно сверять на перегрузки, чтобы случайно не поставить hook на каждый overload ([анализ, строки 399–412](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep-analysis.md#L399-L412)).

Lifecycle и reflection требуют отдельной оговорки. `muztep.on_plugin_load` регистрирует send-message hook, загружает сессии и устанавливает три Java-hook группы; unload снимает URI replacement, затем проходит по `_btn_unhooks`, но список инициализируется пустым и код нигде не добавляет туда hook handles; `_CellSetupHook` и `_ChatOpenHook` handles также не сохраняются для явной очистки ([source, строки 102–123, 193–220](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep.plugin#L102-L123)). В тех же установщиках используется `find_class("java.lang.Class").forName(...)`, а URI hook также получает классы через `find_class` перед `getDeclaredMethod`; это расходится с вышеописанным author-reported наблюдением, что wrapper из `find_class` не имел `getDeclaredMethod`. Ошибки целиком подавляются через `except: pass`, поэтому source даёт основание ожидать, что эти hooks могут не установиться в таком окружении, но без точной сборки и runtime-повтора результат не подтверждён ([source, строки 125–141, 193–220](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep.plugin#L125-L141); [LodraBu analysis, строки 138–201](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/LodraBu/LodraBu-analysis.md#L138-L201)). Это inference о риске, не доказанный failure. Metadata muztep задаёт `__requirements__ = ["mutagen"]`; без выполнения упаковки/установки нельзя подтвердить, как target host предоставляет зависимость ([source, строки 1–8](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep.plugin#L1-L8)).

Сетевой downloader парсит сайт, временно сохраняет файлы в `get_cache_dir()`, определяет формат и добавляет аудио метаданные; file cleanup заявлен через finally/except ([анализ, строки 113–160, 188–207](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep-analysis.md#L113-L160); [source, строки 753–795](https://github.com/corerudo/for-vibecoders/blob/01cb2bfee889da331d348ad190862a03093c592d/allpg/muztep/muztep.plugin#L753-L795)). Важно, что индекс прямо помечает muztep abandoned; сетевой парсинг, сайт и endpoint-предпосылки устареваемы и не рекомендуются как текущая зависимость без повторной проверки.

## Сводка рецептов и anti-patterns

- Java reflection: получить `Class` через `jclass("java.lang.Class").forName(class_name)`; `getDeclaredMethod(name, exact_parameter_types...)`; `setAccessible(True)`; `self.hook_method(method, MethodHook(...))`; сохранить hook handle и снять при unload. Локальные образцы: animtou load, LodraBu load.
- Для интерфейсной сигнатуры выбирать `before_hooked_method` только когда надо изменить вход/состояние до оригинального кода; `after_hooked_method` — когда нужен завершённый результат. Проверять, на каком объекте реально объявлен метод (Activity vs anonymous listener).
- Синхронные UI hook-и должны быть короткими: чтение готового cache допустимо, сеть/парсинг/download отправлять на `run_on_queue(..., PLUGINS_QUEUE)`. Java View/Telegram navigation операции явно отправлять через `run_on_ui_thread`.
- Reflection Field/Method, тяжёлый shader text и per-view ripple держать в cache только с ограничением жизненного цикла и явной очисткой. Обновление конфигурации сбрасывает производный cache.
- Не путать Java `Class` reflection object с Chaquopy class wrapper от `find_class`; не использовать `ripple.JA`; не считать `add_hook` универсальным Java-method hook; не ставить global constructor hook, когда допустимо обработать собственный объект; не оставлять временный MethodReplacement без `finally`; не глотать ошибки молча.
- Перепроверять точные сигнатуры и внутренние поля по декомпиляции конкретного клиента: приватные `mViews`, shader, `setupSizeUniforms`, `PluginsController`, внутренние delegate классы и numeric notification IDs — потенциально version-fragile.
- Не переносить заявление о runtime working в «проверено»: в этой ревизии нет device-test report, APK/device matrix, SDK lock или воспроизводимого CI. LodraBu-анализ приводит конкретные ошибки и заявленные успешные паттерны автора; это полезное evidence уровня author-reported, но независимо здесь не повторено.
